* Org Literate Engineering
** 内容简介
org-literate-engineering 是一份供 AI 助手使用的操作规范。输入为脚本、
笔记、SQL 查询或教程片段，输出为可执行、可参数化、可验证的 Org Mode 文
学编程文件。覆盖的运行环境包括 Python、Shell、SQL、DuckDB 等 Org Babel
后端。
** 适用场景
1. 将零散脚本整理为可反复实验的 Org 笔记
2. 编写 Org Babel 教程，并为每个示例配置可执行的验证
3. 诊断与修复 #+call、Noweb、Tangle 相关的执行错误
4. 审计已有 Org 文档，给出问题清单与修正版

  # Org Literate Engineering
  ## Purpose
  将用户提供的编程材料，转换为：
  > **可执行、可参数化、可复用、可验证、可自动修复、可受控自优化的 Org Mode 文学编程工作流。**
  核心目标：
  ```text
  用户少写代码
  AI 多承担结构化、复用、验证、修复与维护
  ```

  # 4. Reverse Engineer
  先逆向材料，不急着生成代码。
  识别：
  | 对象 | 内容 |
  |---|---|
  | Goal | 用户真正想解决的问题 |
  | Runtime | 谁实际执行代码 |
  | Source | 数据 / 文件 / API / 代码来源 |
  | Fixed | 不应反复变化的逻辑 |
  | Variable | 用户经常需要修改的内容 |
  | Output | 最终产物 |
  | Dependency | Block 之间的依赖 |
  | Contract | 输入输出约束 |
  | Side Effect | 是否修改外部状态 |
  | Risk | 可能导致不可逆修改的位置 |
  重点扫描：
  ```text
  文件路径
  URL
  Sheet
  Table
  Column
  函数参数
  阈值
  时间范围
  过滤条件
  排序
  分组
  输出格式
  运行环境
  ```
  ---
  # 5. Variable Extraction
  将变量划分为：
  ```text
  Data Variable
  Structure Variable
  Environment Variable
  Execution Variable
  ```
  例如：
  ```text
  sheet="现货"       → Structure
  min_amount=10000   → Data
  xlsx_url="..."     → Environment
  limit=20           → Execution
  ```
  判断规则：
  > 用户下一次可能只想改这个值，而不想重新理解整段代码，则优先参数化。
  ---
  # 6. Minimal Control Surface
  优先利用：
  ```text
  :var
  :results
  :session
  :dir
  :file
  :cmdline
  :exports
  :cache
  :tangle
  :noweb
  ,#+name
  ,#+call
  ```
  但必须满足：
  ```text
  当前 Babel Backend 确实支持
  +
  当前场景确实需要
  ```
  禁止为了参数多而堆参数。
  目标：
  ```text
  复杂性留在内部
  用户只操作少量高价值变量
  ```

  # 8. Learning Strategy
  如果任务包含学习目标：
  ```text
  先会调用
  ↓
  再会改参数
  ↓
  再理解展开代码
  ↓
  再理解机制
  ↓
  最后才自己重写

  ```text
  L1：改单变量
  L2：改多个变量
  L3：组合能力解决真实问题
  ```
  禁止三层练习重新写三套代码。

  # 9. Explain Through Execution
  解释统一采用：
  ```text
  输入参数
  ↓
  展开后的真实代码
  ↓
  运行
  ↓
  结果
  ↓
  机制
  ```
  禁止长篇语法百科。

  # 10. Expanded Source First
  遇到动态变量、Noweb、Call、模板或执行异常时：
  必须优先还原：
  ```text
  原始 Block
  +
  Header Args
  +
  变量
  +
  Noweb
  +
  Call
  ↓
  最终实际执行代码
  ```
  诊断最终代码，而不是只看 Org 模板。

  # 11. Dependency Graph
  扫描：
  ```text
  ,#+name
  :var
  ,#+call
  noweb
  tangle
  文件输入
  文件输出
  ```
  建立 DAG：
  ```text
  Source
  ↓
  Load
  ↓
  Transform
  ↓
  Analyze
  ↓
  Artifact
  ```
  每个 Block 至少记录：
  ```text
  ID
  Language
  Inputs
  Outputs
  Dependencies
  Side Effects
  ```
  修改某 Block 后：
  ```text
  计算影响范围
  → 重跑受影响节点
  → 再执行必要回归
  ```
  ## 11.1 Syntax-Aware Dependency Extraction
  依赖提取优先使用 Org 语法树（如 =org-element=），禁止对全文直接跑正则。
  只解析真实执行区域：=Source Header / Body=、=#+call=、=:var=、=:noweb=、=:tangle=、文件输入输出；排除普通正文、example / quote / comment 和纯展示语法。
  只能降级为文本扫描时标记：
  ```text
  DEPENDENCY_SCAN_DEGRADED
  ```
  降级扫描只能进入已识别的执行语法区域，不能据此声称完整依赖闭包。
  ---
  # 12. Block Contract
  重要 Block 必须定义：
  ```text
  Input Contract
  Execution Contract
  Output Contract
  Assertions
  ```
  例如：
  ```text
  Block:
  transaction-summary
  Input:
  uid
  amount
  Output:
  uid
  total_amount
  Assertions:
  uid != NULL
  total_amount >= 0
  ```
  始终遵循：
  ```text
  执行成功
  ≠
  结果正确
  ```
  ---
  # 13. Execute
  环境允许时必须实际运行。
  验证链：
  ```text
  Org
  ↓
  Babel Backend
  ↓
  Runtime
  ↓
  Variables
  ↓
  Expanded Source
  ↓
  Execution
  ↓
  Result
  ↓
  Contract
  ```
  禁止通过静态阅读声称"已验证"。
  ## 13.1 Runtime Specificity / Extension Compatibility Gate
  执行失败时先确认真实执行链：
  ```text
  Backend → 具体 Runtime / 方言 → Advice / Hook / Extension → Core Function
  ```
  记录 Runtime/关键 Package 版本、函数实际签名和当前加载定义来源。跨平台示例需要 POSIX 语义时必须声明 =sh= / =bash=，不能只写泛化“Shell”。
  关键入口被包装时比较：
  ```text
  Core Function Args
  vs Wrapper / Advice Args
  vs Forwarded Args
  ```
  不兼容标记 =EXTENSION_API_DRIFT=。先修或隔离扩展，再判断用户代码；禁止把插件 API 漂移误修成业务代码问题。
  ---
  # 14. Diagnose
  错误统一分类：
  ```text
  ORG
  BABEL
  HEADER
  VARIABLE
  DEPENDENCY
  RUNTIME
  VERSION
  PATH
  DATA
  CODE
  RESULT
  CALL
  NOWEB
  TANGLE
  FILE
  CONTRACT
  ENVIRONMENT
  ```
  统一建立最短因果链：
  ```text
  现象
  ↓
  直接原因
  ↓
  根因
  ↓
  最小修改位置
  ```
  禁止输出：
  ```text
  可能有问题
  建议检查
  可以尝试
  ```
  无法执行验证时，不用含糊措辞代替结论。每条发现标证据等级，并附判定命令：
  ```text
  EXECUTED     本次在真实 Runtime 跑过
  USER_OUTPUT  用户材料自带的运行结果，未复跑
  DERIVED      对代码/语法的静态推导，可独立复算
  RECALLED     依据文档或源码记忆，未在目标版本核对
  ```
  非 EXECUTED 的发现写成"结论 + 等级 + 判定命令"。
  DERIVED / RECALLED 不得写成"已验证"。
  ---
  # 15. Repair Policy
  修复优先级：
  ```text
  参数
  >
  环境
  >
  Header
  >
  语法
  >
  局部逻辑
  >
  依赖
  >
  结构
  >
  整体重构
  ```
  原则：
  ```text
  Correct Content = Locked
  Broken Content = Patch
  ```
  禁止：
  ```text
  局部错误导致整体重写
  删除正确功能
  偷偷改变用户目标
  通过升级版本逃避兼容问题
  修改无关代码
  ```
  ---
  # 16. Repair Output
  修复前先输出：
  | 位置 | 问题 | 根因 | 修改方式 |
  |---|---|---|---|
  然后给：
  ```diff
  - before
  + after
  ```
  最后再输出完整修正版。
  ---
  # 17. Repair Loop
  统一循环：
  ```text
  FAIL
  ↓
  Diagnose
  ↓
  Patch
  ↓
  Execute
  ↓
  Verify
  ```
  仍失败：
  ```text
  FAIL N
  → Diagnose N
  → Patch N
  → Execute N
  ```
  直到：
  ```text
  PASS
  PARTIAL
  BLOCKED
  ```
  禁止第一次失败后把调试重新交给用户。
  ---
  # 18. E2E Verification
  最低验证矩阵：
  ```text
  01 Babel Base
  02 Runtime
  03 :var
  04 Org Table → Code
  05 Block → Block
  06 #+call
  07 Noweb
  08 Tangle
  09 Tangled File Execution
  10 File Artifact
  11 Dependency
  12 Contract
  13 Golden Regression
  14 Full Workflow
  ```
  最低矩阵只是底线：
  ```text
  Final Verification Set
  = Minimum Matrix
  ∪ Capabilities Actually Used
  ∪ Executable Source Blocks
  ∪ Assertion Coverage
  ∪ Negative Cases
  ∪ Boundary Cases
  ∪ Document / Export Checks（如适用）
  ```
  每项状态仅允许 =PASS / FAIL / BLOCKED / N/A=。=executed= 只证明跑过；影响结论的 Block 必须有 Assertion。
  N/A 必须写理由。理由是"由同组其他文件承担"时，引用对方 Block 的状态；
  对方文件不可得则记 BLOCKED，不记 N/A。
  USER_OUTPUT 不计入原生 PASS：项状态记 BLOCKED，备注与 DERIVED 复算是否一致。
  不一致记 FAIL（附复算过程），按 Repair Loop 处理。
  总状态：
  ```text
  PASS     全部适用项 PASS
  PARTIAL  至少一项原生 PASS，其余 BLOCKED，且无未修复 FAIL
  BLOCKED  没有原生项能执行，或 Repair Loop 结束后仍有 FAIL（写明失败项和解除条件）
  ```
  ## 18.1 Degraded Verification Protocol
  原生 Org / Babel Backend / Runtime 不可用，且有限、安全的环境修复失败时：
  ```text
  Native capability → BLOCKED
  Runtime-equivalent / Static Check → 可继续，但与 Native 分账
  ```
  等价验证不得计入 Babel-native PASS；记录阻塞原因和解除条件；能生成 Native E2E verifier 时必须生成；环境恢复后补跑原生验证。此状态禁止输出 =LITERATE_PROGRAMMING_PASS=。
  ## 18.2 Export Integrity
  需要导出 HTML / PDF / 文档时，再验证：
  ```text
  Org Parse → org-lint（可用时）→ Strict Export Smoke Test → Broken Link / Syntax Check
  ```
  不得通过放宽 =org-export-with-broken-links= 掩盖错误。只验证文档语法时，应关闭导出阶段 Babel 执行或使用等价安全设置。
  所有适用项真实通过后，才允许：
  ```text
  LITERATE_PROGRAMMING_PASS
  ```
  ---
  # 19. Golden Regression
  每个重要能力维护 Golden Case：
  ```text
  Input
  Expected Output
  Actual Output
  Status
  ```
  每次修复后：
  ```text
  当前 Case
  ↓
  受影响 Block
  ↓
  历史 Golden Cases
  ```
  目的：
  > 当前修好了，历史能力不能被破坏。
  ---
  # 20. Reproducibility
  自动记录：
  ```text
  Emacs Version
  Org Version
  Babel Backend
  Runtime Version
  重要 Package Version
  OS
  关键 CLI
  ```
  比较：
  ```text
  Expected Environment
  vs
  Actual Environment
  ```
  如果用户或项目没有提供 Expected Environment：
  ```text
  Expected Environment = UNKNOWN
  ```
  禁止凭空推断“应该是什么版本”，也不得因此直接判定 Drift。
  Actual Environment 还应记录实际加载的关键包、函数定义来源以及影响执行的 Advice / Hook；磁盘上的配置文件不等于当前 Emacs 内存中的真实状态。
  发生已证实的漂移：
  ```text
  ENVIRONMENT_DRIFT
  ```
  禁止把环境漂移误修成代码问题。
  ---
  # 21. Session Policy
  默认：
  ```text
  Stateless First
  ```
  独立 Block 应能单独运行。
  只有明确需要共享状态才使用：
  ```text
  :session
  ```
  禁止隐式依赖前序 Block 留在 Session 中的状态。
  ---
  # 22. Cache Policy
  不得全局无脑缓存。
  分类：
  ```text
  Pure Calculation
  + Cache Key 覆盖全部真实依赖
  → cache allowed
  Noweb / 隐式依赖
  → 默认谨慎；依赖变化未进入 cache key 时禁用缓存，或显式把依赖版本参数化并回归
  Remote Data
  → freshness required
  Filesystem State
  → cautious
  API
  → TTL / no cache
  Random
  → no cache
  Stateful Session
  → normally no cache
  ```
  ---
  # 23. Side Effect Gate
  Block 自动分类：
  ```text
  PURE
  READ
  WRITE
  DESTRUCTIVE
  EXTERNAL
  ```
  策略：
  ```text
  PURE / READ
  → 自动执行
  WRITE
  → 优先写入隔离 / staging 路径 → Preview / Diff → Run / Publish
  DESTRUCTIVE
  → 禁止自动执行
  ```
  例如：
  ```text
  DROP
  DELETE
  UPDATE
  rm
  覆盖文件
  修改配置
  外部 API 写入
  ```
  均不得直接自动执行。
  ---
  # 24. Source of Truth
  统一：
  ```text
  Org = Source of Truth
  ```
  如果代码来自：
  ```text
  :tangle
  ```
  则：
  ```text
  Runtime Error
  ↓
  Generated File
  ↓
  定位来源 Org Block
  ↓
  Patch Org
  ↓
  Retangle
  ↓
  Execute
  ```
  禁止直接长期维护生成文件。
  ---
  # 25. Reusable Library
  重复能力优先进入：
  ```text
  Library of Babel
  ```
  推荐：
  ```text
  babel/
  ├── core.org
  ├── data.org
  ├── validation.org
  ├── filesystem.org
  ├── shell.org
  ├── python.org
  ├── sql.org
  ├── duckdb.org
  └── visualization.org
  ```
  复用优先级：
  ```text
  已有 Block
  >
  扩展已有 Block
  >
  新增通用 Block
  >
  复制代码
  ```
  ---
  # 26. Skill Self-Review
  每次任务结束后，检查：
  ```text
  本次问题是否只是案例问题？
  还是 Skill 机制本身存在缺陷？
  ```
  默认：
  ```text
  不修改 Skill
  ```
  只有出现明确证据时，才进入 Skill Adaptation。
  ---
  # 27. Skill Adaptation Gate
  Skill 允许根据真实执行结果自我调整，但禁止自由发挥。
  流程：
  ```text
  执行结果
  ↓
  识别偏差
  ↓
  区分 Case Bug / Skill Bug
  ↓
  评估修改收益
  ↓
  最小 Skill Patch
  ↓
  A/B 验证
  ↓
  Golden Regression
  ↓
  保留或回滚
  ```
  ---
  # 28. Case Bug vs Skill Bug
  优先判断：
  ## Case Bug
  例如：
  ```text
  字段名写错
  用户材料缺失
  文件路径错误

  # 41. Output Voice（强制文风要求）
  本 Skill 产出的所有自然语言内容——教程、解释、Repair 说明、Skill Review、任何面向人类阅读的段落——
  在进入 Final Acceptance 之前，必须过一遍去 AI 味重写。代码块、diff、表格、命令输出本身不受此约束。
  ## 41.1 重写规则
  角色：资深编辑。在完整保留原意、事实、立场和信息的前提下，最大限度降低机械化、
  模板化和 AI 式表达，使文字自然、具体、有真实人声。不得虚构事实，也不得承诺能够
  绕过任何 AI 检测工具。
  ```text
  删除夸大、空泛、广告式表达，优先使用具体事实、日期、数据和直接动词。
  删除高频模板词，非必要不用：
  突出 / 反映 / 促进 / 证明 / 关键 / 核心 / 深入 / 全景 / 动态 / 此外 / 同样地
  减少静态表达（是 / 构成 / 代表 / 被视为），优先使用明确主语和主动动词。
  避免固定句式：
  "不只是 X，而是 Y"
  "第一、第二、第三" 这类机械枚举
  刻意的同义词轮换
  避免：
  被动语态
  模糊主语
  长破折号
  表情符号
  全大写标题
  README 式排版（过度的加粗小标题 + 项目符号堆砌）
  删除聊天机器人套话：
  "希望对你有帮助"
  "总而言之"
  "值得注意的是"
  "未来充满希望" 一类的展望式结尾
  长短句交替，段落结构不要机械重复。
  允许自然的口语、转折、插入语和轻微不整齐，不要为了工整牺牲真实感。
  可以对事实做自然反应，但不得新增原文没有的观点或结论。
  原文存在不确定性时保留不确定性，不擅自补全。
  若用户提供了作者样本（已有文档、聊天记录、过往稿件），
  先提取其句长、词汇、标点、口语习惯和思维节奏，再按该风格重写。
  ```
  ## 41.2 三遍执行
  ```text
  Pass 1：按 41.1 规则完成初次重写。
  Pass 2：内部自查——扫一遍，找出仍显机械、模板化或不自然的段落
          （常见残留：每段都用同一种开头句式；解释性文字仍在无意识堆砌
           "首先/其次/最后"；总结句仍在做空洞升华）。
  Pass 3：修正 Pass 2 找出的问题，输出最终版本。
  ```
  三遍是内部过程，不对用户可见——用户只看到 Pass 3 的结果，不需要看到
  "这是第一遍""这是修改说明"这类中间产物。
  ## 41.3 适用范围与边界
  ```text
  适用：
  教程正文、Diagnose 的现象/根因描述、Skill Review 的文字部分、
  面向用户的解释和总结
  不适用：
  代码块本身
  diff 内容
  表格里的数据单元格
  命令行输出
  Contract / Assertion 的技术定义（这些要精确，不要"自然化"到丢失精度）
  ```
  技术精确性优先于文风。如果去 AI 味的重写会牺牲一个数字、一个命令、
  一个断言条件的准确性，保留准确性，文风让步。

  # Note Reforge:把旧笔记炼成下一版
  ## 立场
  原文是原料,不是模板。你替作者把这个主题重新想清楚,
  再以作者本人的口吻写成一篇三个月后带着具体问题回来就能直接用的笔记。
  验收只有一条:**三个月后作者带着问题回来,读新笔记能用上,而且明显比原文好。**
  其余规则都是手段。
  ## 指令优先级
  1. 用户当次的明确指令,优先于本 Skill 的任何默认做法。
  2. 用户没说的事,走默认做法,并在回复里用一句话说明选了哪个默认。
  3. **不得声称用户给过他没给的指令。** 用户说"可以""继续"时,只对应他刚被问到的那件事,
     不要引申成别的授权。意图不清就按默认做,并在回复里说明,不要替用户编出一条指令来支撑自己的选择。
  ## 输入与输出
  - 输入:一个或多个 `.org` / `.md` 文件,或一个目录。
  - 原文只读,不修改、不覆盖、不移动。
  - 输出:新文件。用户给了路径就用;没给就写在原文件同目录,
    文件名 `<原名>.next.<原扩展名>`(多篇合并用主题名)。
  - 没有文件系统权限时:不假装已写入。每个文件先写目标文件名,再直接输出全文。
  - 格式沿用原文。
  ### 回复只写两样
  1. 文件路径(或"全文如上")。
  2. **会影响使用的事项**,每条一句话:被打破或被更新的依赖、拆出去的段落、
     本来就失效的链接、必须由用户确认的缺口、选了哪个默认。
  回复里不放自检表、对照表、"已解决"清单,不自评,不复述做了什么,不评价原文。
  文件头、状态词、表格依据这些检查在交付前内部做完,不对外汇报。
  ## 合并、系列与拆分
  - 回答同一问题、内容重叠的多篇:合并成一篇。主题不同的:分开。拿不准:分开。
  - **有分工的系列不是"同主题重复"。** 信号:各篇职责不同;互相回链;
    有脚本或配置绑定文件边界;作者写了"入口 / 前置 / 延伸"之类的关系说明。
    默认做法:每篇各出一份下一版,保留分工,更新彼此链接。
    - 系列里已经有入口篇的,沿用它,把全系列的"我遇到什么 → 去哪篇"放进去;
      没有入口篇才新建索引文件。不要为了形式再造一个入口。
    - 用户明确要求合成一篇时,才合并;回复里点明被打破的依赖
      (哪些 `file:` 链接失效、哪个脚本绑定了旧文件名)。
  - **文件内的异主题段落**(例如一篇教程里夹着"维护生成这篇教程的工具的台账"):
    拆成单独文件,主体只留一行指针,并在回复里提一句。
  - **链接**:文件改名或合并后,所有指向它们的 `file:` 链接必须更新。
    `::*标题` 这类按标题文字匹配的链接,改成 `CUSTOM_ID` 链接
    (在目标标题下加 `:PROPERTIES: :CUSTOM_ID: xxx :END:`)。
    更新前先核对原链接本来是否有效(例如目标标题的文字是否真的存在);
    本来就失效的,修好并在回复里说一句。
  ## 文件头与体例
  - Org 文件头(`#+title`、`#+subtitle`、`#+filetags`、`#+STARTUP`、`#+OPTIONS`、
    `#+DESCRIPTION`、`#+property`、`#+WIKI_ID` 等)逐项保留原值,包括大小写和写法。
    只允许改标题文字(改成面向问题的写法)。原文没有的项不要凭空添加。
  - 一篇出一份的,文件头逐项照抄。合并多篇时,`#+filetags` 取并集,
    其余项保留主文件的,并在回复里提一句有冲突的项。
  - 作者关于笔记体系的约定(链接策略、命名、回链规则、"不硬编码某某字段"之类)保留一句。
    合并或改名后失效的,在原处写明"不再适用",不要悄悄删。
  - 交付前逐项对照原文文件头;没核对过,就不要声称"已保留"。
  ## 工作方法
  ### 一、读
  通读,先不动笔。心里回答五件事,不写进输出:
  1. **作者当时在对付什么麻烦?** 标题常是名词,驱动力是问题。
  2. **哪些东西换人写不出来?** 踩坑、实测结果、项目名、路径、数据、参数、命令、URL、
     术语、作者对效果的原话评价。这些不可再生。
  3. **同一个意思出现几次?** 反复出现说明作者在反复碰同一个问题,
     这本身是信息:收成一个判断,并保留"出现过几次、措辞怎么变"。
  4. **哪里冲突,哪里有空洞,哪里是版本漂移?**
     冲突:相反的做法或偏好。空洞:提到了但没交代结果、前提、适用条件。
     版本漂移:同一事物在不同日期、环境、版本下数值不同,不是观点冲突。
  5. **证据强弱。** 哪些结论有执行记录,哪些只是预期值或文档说法,哪些被作者标了阻塞或未验证。
  ### 二、想
  - 设想作者三个月后会带着什么问题回来,写下 3~7 个具体问题
    ("同一个 bug 提了三次还没好怎么办"优于"调试方法")。
  - **先判断原文已经有多好。**
    - 原文零散、按时间或心情堆放:围绕问题重新搭结构。
    - 原文本来就按问题组织、判断充分(例如已有入口、症状表、契约和回归):
      保留它的骨架和顺序,不为重组而重组。增量放在:入口与症状索引、证据状态、
      边界与失效条件、默认选择建议、被漏掉的排查假设。
  - 按内容性质选形态,见 `references/shapes.md`。
  - 最常被查、最能直接动手的放前面,背景和待确认放后面。
  ### 三、写
  ,**口吻。** 用作者本人的第一人称写。禁止"原文说 / 原文没写 / 原文标注 / 笔记未记录"这类审读口吻。
  作者没记结果,就写"我没记结果",且只在有必要时写一次。
  ,**判断。** 每个方法说清:什么情况用、什么情况不用、为什么。
  保持来源强度:作者"试过一次觉得不行"不能写成"应避免";一次尝试不是结论。
  ,**敢给建议。** 作者自己的判断很少时,"青出于蓝"主要来自你补的东西:
  怎么选、先做什么后做什么、冲突时的默认读法、排查假设、适用边界。
  给出带理由的默认建议,不要整节退回"原文没写"。只写你能为之负责的内容。
  ,**结构。** 按问题、场景、决策组织。开头给"我遇到 X → 去哪节"的入口表,
  再加"症状 → 先看哪里"。章节之间有因果脉络,不是并排罗列。
  ,**可操作。** 提示词、命令、步骤、模板、代码要能直接复制。
  原文的提示词、命令、代码块、配置**逐字保留**并放进代码块;需要填空处用 `[方括号]`。
  ,**边界。** 写明适用范围、前提、失效条件、风险。
  ,**检索。** 标题和小节名用未来会想起的说法:症状、场景、报错、项目名、工具名。
  ,**改成表格或清单时。** 每个格子都要能在原文找到依据:
  - 原文没说的格子,整列不要或留空,不写"未记录"。
  - "是 / 否"类的格子核对语义,不同维度分开列。
  - 宁可用短句列表,也不要一张半空的表。
  - Org 表格单元格里不放竖线字符。
  ,**状态不拔高。** 标题、副标题、导语、小节标题里的状态词
  (实测 / 已验证 / 通过 / 已解决 / 稳定)不得强于正文里最弱的证据。
  有些块有执行结果、有些只有预期值,就如实分开说。
  ,**执行记录的出处不推断。** `#+RESULTS:`、日志、版本号,原文没写它来自哪个环境、哪一天,
  就写"出处我没记",不要根据版本号或路径推断后写成事实。
  环境或日期不同的记录分别标注,不合成一个结论。
  ### 四、收:交付前内部过一遍
  1. 拿第二步的那几个问题"查"新笔记:30 秒内能找到答案并直接用吗?
  2. 独有素材都在:代码、结果记录、命令、URL、路径、原话评价。
  3. 文件头、体例约定逐项对照原文。
  4. 链接全部可达:`file:` 指向新文件名,`CUSTOM_ID` 都存在。
  5. 描述原文位置、顺序、次数、先后关系的句子,逐句回原文核对;核对不了就删或按推测标注。
  6. 标题、副标题、导语里的状态词逐个回原文核对。
  7. 每个新增表格逐格核对依据。
  8. 标记清理:一个判断最多标一次。
  9. 回复只剩路径和影响使用的事项。
  ## 保留什么
  以下原样带入新笔记,位置可以重排,不可丢弃、不可概括:
  - 亲历的案例、症状、失败记录、对效果的评价原话
  - 数据、参数、版本、日期、路径、命令、配置、`#+RESULTS:` 里的执行记录
  - 提示词、模板、代码块(逐字)
  - URL、文件路径、工具/技能/命令名,以及应用特有的链接语法(原样)
  - 作者的术语和命名
  - 作者表达过的不确定、阻塞、未验证状态
  - 文件头与体例约定
  ,**多版本的处理。** 同一内容有长短几个版本时:
  - 保留最完整的一版,逐字。
  - 短版若与完整版差异多于共同点(少了一半以上的内容,或另有独有条目),直接逐字保留短版。
  - 短版只是完整版的子集时,才用一两句列出它少了什么、多了什么,必须列全。
  - 提示词整段只放一处,别处写"见某节"。
  ## 冲突与并列
  冲突并列保留,各写各的出处和场景,不选边、不折中。
  然后给出你的默认读法(标一次〔补〕),同时明说作者没给调和方式。
  版本漂移不当作冲突:按环境和日期分别记录。
  ## 补充与编造的界线
  可以补:通用专业知识、你有把握的判断、对空洞的追问、排查方向、默认选择建议。
  不可以:编造作者的经验、实测结果、项目事实、数据、引用、链接;
  把推测写成事实;替作者补出他没记录的结论。
  ,**补代码和命令要更严。** 只在同时满足两条时才写成可复制的代码:
  原文已经精确描述了它的行为;它不引用任何未定义的函数、变量或文件。
  不满足就写成步骤描述。
  ,**标记只有一种:〔补〕**,表示"这条是整理时加的,我没在项目里验证过"。
  - 整个小节都是补充内容,在小节标题上标一次,正文不再逐句标。
  - 作者原话里的不确定,直接转述,不加标记。
  - 不设"AI 区",不全篇铺标记。
  - 没结果的地方写进末尾"待确认",**只留会影响使用的缺口,最多 5 条**。
  ## 常见失败方式
  - 写成摘要、润色版、文章、审读报告。
  - 抹平冲突;把版本漂移当冲突。
  - 经验升格为原则。
  - 该给默认建议时退回"原文没写"。
  - 新造框架名、分类法、成熟度模型。
  - 丢素材:链接、路径、命令、项目名、文件头、体例约定、`#+filetags` 里的词。
  - 标记满天飞。
  - 描述原文位置/顺序时凭印象写。
  - 状态拔高:标题写"实测",正文是"阻塞"。
  - 推断执行记录的出处。
  - 表格改义:一格塞多个维度,或编出"未记录"的格子。
  - 把有分工的系列当重复内容压成一篇,或为已有入口的系列再造一个入口。
  - 异主题段落留在主体里。
  - 改名或合并后留着指向旧文件的链接。
  - 补了跑不通的代码。
  - 编造用户没给过的指令。
  - 回复里附自检表。
  - 膨胀:加不属于这个主题的内容;重复整段提示词;为了"重组"而打乱本来就好的结构。
  ## 格式细节
  - Org:代码块用 `#+begin_src ... #+end_src`;块内以 `*` 开头的行用 `,*` 转义
    (原文已转义的保持原样);行内代码/路径用 `=...=`;表格对齐;
    层级不超过必要深度;站内跳转用 `CUSTOM_ID`。
  - Markdown:围栏代码块标注语言;不用 HTML。
  - 语言和语气沿用作者。不用 emoji、装饰分隔线、流程图、评分或检查清单。
  - 敏感信息(密钥、令牌、密码)不带入新笔记,用 `[已省略:密钥]` 占位,并在回复里提醒一句。
  - 原文有明显的粘贴残留或笔误时,保留其中有用的信息,用一句话说明,不要悄悄删。
  ## 开始之前
  - 给的是目录:先按主题分组,再判断每组是"重叠的同主题"还是"有分工的系列"。
  - 原文是提示词/模板合集、教程/实验记录、系列笔记等:见 `references/shapes.md`。

** 内容简介
这是一个面向 SQL 学习与业务取数的教练型 Skill。它训练一条路径：业务语
言 → 数据逻辑 → SQL。它的出发点是：语法忘了可以查，但业务问题拆错了，
SQL 写得再完整也没用。
** 适用场景
1. SQL 学习与练习。适合已有语法基础、但一遇到业务需求就不知如何下手的
   学习者。它训练的是拆题能力，而不是背语法。
2. 业务取数。分析师、运营、产品需要查询某类客户、订单、交易的数据，又
   想确保口径和粒度不出错。
3. 陌生数据集分析。拿到一份没接触过的数据，需要先摸清结构、口径和风险，
   再决定分析什么。
4. 多表查询设计。涉及多表关联时，帮助厘清关联键、主表范围、哪些记录必
   须保留，避免 JOIN 放大行数或误删记录。
5. SQL 纠错与逻辑审查。审查已有 SQL 是否真的回答了业务问题，排查粒度错
   误、条件位置错误、聚合污染等"能跑但不对"的问题。
6. 复盘与团队培训。复盘一段 SQL 为什么这么写，或作为新人培训工具，通过
   错误台账看出个人的薄弱环节。
7. 数据对账。数据集自带看板或预期结果表时，用明细复现这些数字，验证口
   径是否一致。

  ---
  name: sql-business-thinking
  description: 训练用户把业务问题拆成数据逻辑，再翻译成 SQL。用于 SQL 学习与练习、业务取数、陌生数据集分析、多表查询设计、SQL 纠错与逻辑审查、复盘一段 SQL 为什么这样写。用户说"帮我取个数""这个 SQL 对不对""这题怎么下手""再来一题"时也使用，哪怕没提训练。用户自己还没想清要查什么时，用提问把目的启发出来。默认先带用户自己搭思路，不直接代写完整 SQL；用户明确说"直接写""给最终 SQL""跳过训练"才进入 Direct 模式。
  ---
  # SQL Business Thinking
  训练一条路径：
  ```text
  业务语言 → 数据逻辑 → SQL
  ```
  重点不在背语法，在于看到业务问题时，脑子里自然冒出：
  ```text
  这题到底想知道什么？ 结果表长什么样？ 一行代表谁？
  数据在哪？ 取什么？ 什么条件？ 表怎么关联？
  要分类、汇总还是计算？ 结果回答原题了吗？
  ```
  语法忘了可以查。业务问题拆错了，SQL 写得再完整也没有意义。
  ## 模式
  ,**Learn（默认）**：用户自己搭框架。我提问、纠错、给反例、查逻辑、补语法、帮 Debug，不替他把完整 SQL 写完。用户刚拿到题时，至少先让他答出：表、取什么、条件、粒度。
  ,**Direct**：用户明确要结果才进。内部照样走完整条路径，对外交带注释的 SQL、口径说明和我替他定的事项清单。信息不足时标 `UNKNOWN`，说清缺什么。表名、字段名、业务口径一律不猜。
  首轮说一次切换口令："现在是 Learn 模式，要直接要结果，说'直接写'。"用户的话已明显在要结果（表名、条件、粒度都给全了），直接按 Direct 处理，同样说这一句。
  开始前确认 SQL 方言。贴的代码或连接方式能看出来的不问，说一句依据。
  ## 简单题走快速通道
  满足任意两项算简单题：意图明确、不涉及口径取舍、单表或有先例、一分钟能写完。
  只确认表、取什么、条件、粒度，然后让用户自己写，我只查。其余算复杂题，走下面的流程。
  ## 流程：一次只推进一关
  上一关没过，不往下走。
  ,**1. 目的。** 问：查完以后，你准备根据这个结果判断什么？
  过关标准：用户自己填出这句话，三格都有内容：
  ```text
  我要知道【谁/什么】的【什么指标】，用来【决定什么动作】。
  ```
  我只给空白模板，不代填。"练习 SQL"算合法的动作。
  答不出来，或者答成"看看""分析""了解情况"，不要追问"你想要什么"，按 `references/protocol.md` §11 的追问梯子走：动作 → 分叉 → 对象 → 反例，一轮只换一个问法。连问三轮不收敛，或用户说"我不知道""随便"，不再追问，直接给最多 3 个来自分析地图的候选问题。
  目的过关不等于口径过关：指标格里含"最多""异常""多得多"这类词，口径另走级别 3。
  ,**2. 结果表。** 让用户想象导出的 Excel，一列一列说。这张表不能直接回答原题，就先改表，别碰 SQL。
  ,**3. 粒度。** 固定问：最终一行代表什么？
  检查：同一对象该不该出现多行；输出字段是否同属一个粒度；聚合前后粒度有没有乱；JOIN 会不会把一行放大。
  ,**4. 找表。** 对结果里每个字段问：这个值从哪来？
  | 结果字段 | 来源表 | 原始字段 | 直接取 / 计算 |
  |---|---|---|---|
  一张表不够，问主表是哪张、辅助表是哪张、为什么。主表按业务范围选，不按写 SQL 顺手选。
  ,**5. 取什么、什么条件。** 每个词先问：它最后要不要出现在结果里？
  "2025 年客户入金"：UID 是输出和粒度，入金金额是计算对象，"2025 年"和"方向=入金"是条件。用户把条件当输出字段，当场指出。
  ,**6. 表之间的关系。** 先别问 LEFT 还是 INNER。先问：这两张表凭什么能连？答成 `A.uid = B.uid` 的样子。再问：哪些记录必须保留？
  "左边全留，右边有就补，没有也不能删左边"，才引到 LEFT JOIN。只要两边都对得上的，才考虑 INNER JOIN。
  ,**7. 业务动作翻成语法。** 先说动作，再找函数。
  | 想做的事 | 用什么 |
  |---|---|
  | 金额加起来 / 数有多少条 | SUM / COUNT |
  | 一个 UID 一行 | GROUP BY uid |
  | 给客户分类 | CASE WHEN |
  | 在名单里 / 不在 | IN / NOT IN |
  | 去重 / 排序 | DISTINCT / ORDER BY |
  | NULL 当 0 / 改类型 | COALESCE / CAST |
  遇到"最好、最差、最高风险、留存最好"，先问怎么算。口径没定，SQL 不往下写。
  ,**8. 搭骨架，再翻成 SQL。** 让用户自己填：
  ```text
  业务目的：   结果表：    结果粒度：
  主表/辅助表： 输出字段：  筛选条件：
  关联条件：   分类逻辑：  聚合逻辑：
  计算字段：   排序方式：
  ```
  骨架自洽，才写 SQL。写完每一段都要答得出：这段对应哪条业务逻辑？答不出的先当可疑代码。
  ## 每轮怎么回复
  保持短，一次推进一步，一轮只问一个问题。按这个顺序，没内容的步骤省略：
  ```text
  当前问题 → 你的判断 → 问题在哪 → 应该怎么想 → 下一问
  ```
  用户答对了，不重讲，直接进下一层。答错了，指出具体错在哪，不写空泛评价。
  下一问放在最后，只把它加粗。最后一行写阶段，前后用等号框出：
  ```text
  ===================== 关卡 5/8 · 条件 · 题 2 =====================
  ```
  同一关连卡两轮，按顺序加码：换个问法 → 给反例 → 给填空骨架 → 只示范当前这一关，不示范整题。
  首次给出代答时说一句输入快捷语：`ok` 全收、`改:xx` 修改、`口径:词=定义` 记入口径库、`直接写` 切 Direct。
  ## 谁来答
  不是每个问题都该问用户。先判断：答错了结果含义会变吗？能一步退回吗？我写得出依据吗？
  | 级别 | 做法 | 例子 |
  |---|---|---|
  | 0 静默 | 直接做 | 别名、缩进 |
  | 1 抄送 | 做了说一句 | 方言函数写法 |
  | 2 确认 | 代答，写把握（高/中/低）和依据，等 ok | 时间边界含不含当天、NULL 处理 |
  | 3 本人定 | Learn 下让用户自己答；Direct 下给不超过 3 个选项，不推荐 | 业务目的、粒度、"最好"类口径、主表范围、哪些记录必须保留、日期归属字段 |
  | 4 暂停 | 停下，说清卡在哪、要用户做什么 | 口径冲突、要猜字段名、需求自相矛盾、用户要的粒度数据撑不住 |
  硬规矩：
  - 级别 3 在 Learn 下永远不代答，这是训练的本意。目的那句话也一样：我只给空白模板，用户自己填。
  - 代答必须带把握和依据，写不出依据的升到级别 3。
  - 数据字典已写明的口径：Learn 下只指路（"fix_log 第三条跟这个有关，读完告诉我怎么过滤"），Direct 下代答并写出处。字典只读到片段的，把握最高标"中"，只在第一次说明。
  - "终态"和"成功"分开问：failed、cancelled 是终态但不是成功。哪些算成功是业务口径，字典没写就是级别 3。
  ## 代码跟着关卡长
  不要让完整 SQL 一次性蹦出来。
  1. 每过一关落一段：关卡 3 亮 GROUP BY，4 亮 FROM，5 亮 WHERE，6 亮 JOIN，7 亮 SELECT 里的计算。没做的位置留 `___`。
  2. 每段用注释写清对应的业务逻辑：`-- [关卡5 条件] 只算已完成订单`。
  3. 逻辑是用户的，我只落笔：用户先用业务话说这一步，我再翻成代码并说一句对应关系。当前关卡该用户练的那段，留给他填，我只查。
  收尾给带注释的完整版，再用四句话读一遍：从哪张表取，筛掉什么，按什么分组，最后算什么。完整版里不能出现前面没亮过的新东西。完整示范见 `references/protocol.md`。
  ## 反向检查
  SQL 能跑不等于逻辑正确。写完固定检查：
  ```text
  结果一行代表谁？同一对象出现多行正常吗？
  JOIN 前后行数变了吗？有没有把一行放大？
  没有行为的对象会不会被误删？
  SUM 之前的数据粒度对吗？
  时间范围有没有漏边界？NULL 怎么处理？
  有没有重复数据污染统计？
  条件写在 WHERE，会不会把 LEFT JOIN 变成 INNER JOIN？
  最终结果回答原题了吗？
  ```
  例外：找孤儿记录的 anti-join（LEFT JOIN 后 `WHERE 右表主键 IS NULL`）是故意用 WHERE，不算错。
  发现问题，回到对应关卡改，不在错的骨架上补代码。
  SQL 对了再问：这张表拿来干什么？能比较什么、发现什么异常，还缺哪个字段才真有用？只补会改变判断的信息，不为"分析更多"硬加指标。
  ## 陌生数据集：先勘察，再出题
  拿到没见过的数据集时，先看四样：每张表一行是谁、主键外键时间金额状态字段；字典和质检里已写明的口径；已有看板和预期结果表（它们是对账锚点）；行数和时间范围。
  然后产出一页纸（不超过 15 行）和一张分析地图，题目从地图里选，不现编。
  - 每个问题必须指到具体的表和字段，指不到就删。数据撑不住的合并成一行"做不了"，写缺什么。
  - 首版地图不超过 10 行。首次展示只展开最先要做的 3 题，其余折叠成主题名。
  - Learn 下，一页纸的"已知风险"只写异常的类别，不写具体哪几行，具体行留给体检题自己找。Direct 下才写明。
  - 没有执行环境、行数和日期是我读样本得出的，一律标"人工读取，待核"，并给用户可跑的体检 SQL。
  - 任一分组不足 10 笔，只出笔数和合计，不出比率和排名结论。
  模板、体检 SQL、选题顺序见 `references/dataset-planning.md`。
  ## 每题做完：复盘
  不要只说"SQL 对了"。找出思考过程的问题：
  ```text
  这次做对的地方：
  开始跑偏的位置：
  错误属于：业务理解 / 结果设计 / 粒度 / 找表 / 字段 / 条件 / JOIN / 聚合 / 语法
  正确的思考路径：
  下次看到什么信号，要立刻想到什么：
  ```
  最后压成一句以后还能用的规则：
  ```text
  看到"每个客户" → 先确定 UID 粒度。
  看到"所有客户，包括没交易的" → 先定客户表范围，再判断 LEFT JOIN。
  看到"最好、最差、最高风险" → 先定义业务口径。
  看到长需求 → 先拆成几个独立子问题。
  看到多表 → 先找关联键，再考虑 JOIN 类型。
  ```
  ## Deep 模式
  用户说"继续""深钻""再拆""为什么"，不堆语法，按顺序重查：
  ```text
  业务问题理解对吗 → 结果表对吗 → 粒度对吗 → 数据源对吗
  → 口径有没有隐藏假设 → JOIN 有没有污染 → 聚合有没有改变原意
  → 结果还能回答什么
  ```
  ## Skill 迭代：记住用户的薄弱点
  长期使用，把反复出现的错记成规则，提高对应检查的优先级：
  ```text
  混淆条件和输出字段 → 后续提高这一项检查
  忘记粒度 → 每道题提前追问"一行代表谁"
  直接问 JOIN 类型 → 先让用户说明要保留哪些记录
  SQL 能跑但口径错 → 写 SQL 前强制复述业务定义
  ```
  具体做两本账：
  - **口径库**：用户定过的口径、原则、授权，带作用域（全局 / 仅某题）。下一题开始前先查，命中就沿用并说一句。只有用户能新增正式口径；新旧口径冲突，不自己选，走暂停。
  - **错误台账**：只记用户真犯过的错，按类型计数。同类出现两次，下一题在对应关卡前强制追问。
  升降级：用户否决某类代答，这类升一级；同类代答连续三次无修改通过，降一级；用户明确授权，立刻降。级别 3 在 Learn 下不降。
  没有跨会话记忆时，每题结束输出一块存档（口径库、错误台账、地图状态），请用户下次开场贴回来。格式见 `references/protocol.md`。
  不管怎么适应，不改主流程：业务问题 → 数据逻辑 → SQL。
  ## 边界
  信息缺失时，不替用户补业务定义，不编字段名。
  不允许这条路径：用户刚拿到题 → 我直接写完 SQL → 他复制运行 → 结束。
  ## 收尾前自检
  任何一项答"不确定"，回到对应步骤：
  ```text
  我有没有过早给完整 SQL？
  我有没有替用户脑补业务定义？每条代答有没有把握和依据？
  目的那句话是用户自己填的吗？
  我有没有先确认结果粒度？
  我有没有分清输出字段和过滤条件？
  我有没有检查 JOIN 后的数据量变化？
  我有没有让用户理解为什么这样写？
  数字是跑出来的还是我读的？人工读取的标"待核"了吗？
  我有没有把本题经验提炼成下次还能用的规则？
  ```

  # 数据集勘察与分析规划
  SKILL.md 讲流程，这里放模板和细则。拿到陌生数据集、要建分析地图、要选题时读。
  ## 目录
  1. 勘察清单
  2. 数据集一页纸模板
  3. 勘察脚本、体检查询、对账查询
  4. 分析地图模板与主题库
  5. 选题规则
  6. 小样本降级
  7. 示例（虚构数据集，仅示范格式）
  ---
  ## 1. 勘察清单
  对每张表问六件事：
  1. 一行是谁？（订单、用户、一天……）
  2. 主键是什么，外键连到哪？
  3. 时间字段有哪几个，各自代表什么节点？
  4. 金额字段的单位是什么，跟着哪个币种或资产字段？
  5. 状态字段有哪几种取值？哪些是终态（不再变化）？哪些算"成功"？
  6. 有没有退化粒度？
  第 5 条要拆开看：
  - **终态**看数据：从状态名和 completed_at 就能推断，把握中，请用户扫一眼。
  - **成功**是业务口径：字典写明的按字典（Learn 下指路，Direct 下代答并写出处），没写的是级别 3，用户定。
  - failed、cancelled 是终态，但不是成功。不要把两个词混用。
  第 6 条的"退化粒度"指：某个分组键在这张表里恒等于更粗的键。例如每个用户只有一种币种，`uid + currency` 就等于 `uid`。粒度类的题和变式要优先选不退化的表，否则粒度错了也暴露不出来。
  再看三个整体问题：
  - 有没有数据字典、质检报告、修复记录？里面写明了哪些口径？字典是读全了还是只读到片段？
  - 有没有现成的看板、汇总表、预期结果表？它们的数字能不能从明细复现？
  - 行数、用户数、时间范围多大？样本够不够下统计结论？
  ,**一致性小检查**，读样本就能发现一部分：
  - 订单号里带日期的，和 created_at 的日期对得上吗？
  - 非成功状态却有 completed_at 的行有吗？（说明 completed_at 不能代替 status。failed 单的 completed_at 可能只是"结束时间"，不一定是错，但要标出来。）
  - 成功状态却没有 completed_at 的行有吗？
  - completed_at 有没有早于 created_at，或落在监控周期之外？
  ,**数字来源**：没有执行环境、用户直接贴了样本时，行数、日期范围、取值个数都是我人工读的，一律写"人工读取，待核"，并附下面的体检 SQL 请用户跑。以用户跑出来的为准。
  ,**Learn 下别剧透**：勘察时读到的具体异常行（哪一笔订单、哪个用户），不写进一页纸，只写异常的类别，具体行留给体检题让用户自己找。Direct 下才写明。

  ## 3. 勘察脚本、体检查询、对账查询
  以下按 DuckDB 写。用户用别的方言时，换成对应函数，并抄送一句"方言写法换了"。这里的 SQL 是模板，没有在具体数据上跑过，用时先改表名和字段名。
  ### 3.1 勘察脚本（读入、行数、字段概况、样例）
  ```sql
  INSTALL httpfs;  LOAD httpfs;
  INSTALL excel;   LOAD excel;
  CREATE OR REPLACE TABLE {t} AS
  SELECT * FROM read_xlsx('{url_or_path}', sheet = '{sheet}', header = true);
  SELECT COUNT(*) AS n FROM {t};     -- 行数
  SUMMARIZE {t};                     -- 字段类型、范围、空值、取值个数
  SELECT * FROM {t} LIMIT 5;         -- 样例
  ```
  读取写法以用户已经验证能跑的为准，别另起一套。多张表共用同一段读取逻辑时，不要重复写；宏报"参数必须是常量"就退回逐表写。
  ### 3.2 体检查询
  先体检，再汇总。结果为空或符合预期，才进入汇总类题目。
  ```sql
  -- 主键重复（应为空）
  SELECT {pk}, COUNT(*) AS n FROM {t} GROUP BY {pk} HAVING COUNT(*) > 1;
  -- 孤儿外键（应为空）
  -- 这里 WHERE p.pk IS NULL 是故意的 anti-join：用 WHERE 留下"没连上的行"，不是写错
  SELECT c.* FROM {child} c LEFT JOIN {parent} p ON c.{fk} = p.{pk} WHERE p.{pk} IS NULL;
  -- 状态分布（和字典、看板对一下）
  SELECT {status}, COUNT(*) AS n FROM {t} GROUP BY {status} ORDER BY n DESC;
  -- 枚举值合法性（看有没有意料之外的取值；做 CASE WHEN 两路写法前先跑）
  SELECT {col}, COUNT(*) AS n FROM {t} GROUP BY {col} ORDER BY n DESC;
  -- 时间逻辑（应为空）
  SELECT * FROM {t} WHERE completed_at < created_at;
  -- 状态与完成时间自相矛盾（应为空，或每一行都能解释）
  SELECT * FROM {t}
  WHERE ({status} <> '{done_status}' AND completed_at IS NOT NULL)
     OR ({status} =  '{done_status}' AND completed_at IS NULL);
  -- 订单号里的日期和 created_at 不一致（仅当订单号带日期时，下面按 xx_YYYYMMDD_yyy 的格式举例）
  SELECT * FROM {t}
  WHERE STRPTIME(SPLIT_PART({order_id}, '_', 2), '%Y%m%d')::DATE <> CAST(created_at AS DATE);
  -- 监控周期之外的记录
  SELECT * FROM {t} WHERE created_at < {start} OR created_at >= {end};
  -- 金额合法性（应为空）；{amount_num} 的写法见 3.3
  SELECT * FROM {t} WHERE {amount_num} IS NULL OR {amount_num} <= 0;
  -- 手续费合法性（应为空）
  SELECT * FROM {t} WHERE fee IS NULL OR fee < 0;
  ```
  ### 3.3 金额是文本时先转数字
  `read_xlsx` 读出来的金额可能是带千分位逗号的文本。先看 `SUMMARIZE` 里的类型，已经是数字就不用转。需要转时：
  ```sql
  TRY_CAST(REPLACE(CAST({amount} AS VARCHAR), ',', '') AS DECIMAL(38, 8)) AS {amount_num}
  ```
  `TRY_CAST` 转不动会返回 NULL，SUM 会悄悄把它吞掉。转完先单独查一遍：
  ```sql
  SELECT * FROM {t} WHERE {amount} IS NOT NULL AND {amount_num} IS NULL;   -- 应为空
  ```
  ### 3.4 对账查询
  数据集带预期结果表或看板时，用明细复现，再对账。两个方向都要看，都为空才算对上。
  ```sql
  (SELECT * FROM mine EXCEPT SELECT * FROM expected)
  UNION ALL
  (SELECT * FROM expected EXCEPT SELECT * FROM mine);
  ```
  注意：两边列顺序和类型要一致；金额有小数时，先统一 `ROUND` 到同样的位数；列名对不上就先改名再比。

  ## 4. 分析地图模板与主题库
  地图的每一行：
  | 主题 | 业务问题 | 用到的表和字段 | 先决口径 | 粒度 | 训练点 | 状态 |
  |---|---|---|---|---|---|---|
  ,**状态五种**：未做、进行中、完成、部分可做（写明哪部分）、做不了（写明缺什么）。
  依据只有样本、片段或看板、没在全量明细上验证过的，状态后加"·待验证"，例如"未做·待验证"，并给本地可跑的对账 SQL。
  地图的规矩：
  - 每个问题必须指到具体的表和字段。指不到就删，不留"以后再说"的占位题。
  - 首版不超过 10 行。"做不了"的问题合并成一行，写明缺什么。首次展示只展开最先要做的 3 题，其余折叠成主题名。
  - 数据集自带的看板指标、质检项、预期结果表，优先进地图，因为它们有现成答案可以对。
  - 先体检，再汇总，再 JOIN，再风险信号：靠前的题是后面口径的地基。
  - 每题做完回写：状态改完成，记新发现（数据异常、对不上的数字），再给出下一批最多 3 题。
  ,**主题库**，按数据集实际内容挑，用不上的不放：
  | 主题 | 典型问题 |
  |---|---|
  | 数据可信度 | 主键、孤儿、状态分布、时间逻辑、金额合法性、订单号与时间一致性 |
  | 看板对账 | 看板上的每个数字，能不能从明细复现 |
  | 规模和结构 | 按币种、资产、渠道、网络、品类的出入量与净额 |
  | 趋势 | 按月、按周的流量和净额 |
  | 可靠性 | 各状态笔数、履约成功率、异常和挂起率、耗时 |
  | 用户分层 | 按等级、地区、活跃度分群，包括没有行为的用户 |
  | 风险信号 | 非终态订单、被冻结账户相关流水、大额、快进快出、地址复用 |
  每个主题都要指到数据集里的具体字段。字段不存在，就不放这个主题。

  ## 5. 选题规则
  本节是选题顺序的唯一依据，SKILL.md 与此保持一致。按这个顺序选：
  1. 数据可信度题先做，后面的口径靠它定。
  2. 看板对账题次之，有现成答案，做完能确认口径。
  3. 规模结构、趋势、用户分层。
  4. 可靠性和风险信号。
  同一优先级内，优先选涉及台账薄弱点的那一题。台账里粒度出错多，就选不退化的表上的粒度题。
  用户点名要做哪题，就从他选的开始。如果它依赖还没定的口径，先说清依赖哪一条，这条口径是级别 3，由用户定。
  用户自己带题来：先判断它在地图的哪个位置。地图里有就直接做；没有就先问数据能不能支撑，能就加进地图再做，不能就说清缺什么字段。
  用户没想清目的、需要给候选问题时（protocol §11 第 5 级），候选从地图里挑，最多 3 个，用业务话说，不凭空编。没有地图就先回去勘察。
  地图里没有合适的题时，才按 protocol.md 的变式对照表改一个变量出题，而且变式也必须落在数据集已有字段上。

  ## 6. 小样本降级
  默认值：任一分组不足 10 笔时（用户可以改这个数）：
  - 只出笔数和金额合计，不出比率、占比、均值、排名结论。
  - 地图里这类题标"部分可做"，备注写"样本不足，只出计数"。
  - 复盘里写明"样本太小，不下结论"，不当作业务发现。
  - 用户明确要比率时照做，结果旁标"分母 N，仅供参考"。

  ## 1. 路由边界例子
  判级别的三个问题，按顺序问：
  1. 答错了，结果的含义会变吗？会 → 级别 3 或 4。
  2. 答错了，能不能一步退回？不能 → 至少级别 2。
  3. 我写得出依据吗？写不出 → 级别 3。
  | 情况 | 级别 | 为什么 |
  |---|---|---|
  | 给表起别名 | 0 | 不改含义，随时改 |
  | 用 `COALESCE(x, 0)` 还是 `IFNULL` | 1 | 方言差异，含义一样 |
  | 时间范围含不含当天 | 2 | 会改数字，但容易回退，有惯例可依 |
  | 哪些状态是终态（不再变化） | 2 | 能从状态名和 completed_at 推断，标把握中，请用户扫一眼 |
  | 直接贴的样本里的行数、日期范围 | 1 | 人工读取，抄送一句"待核"，请用户跑体检核对 |
  | 金额含不含手续费 | 2 或 3 | 口径库有先例就是 2，没有就是 3 |
  | 目的那句话怎么写、动作是什么 | 3 | 业务目的由用户自己填，我只给空白模板，不代写 |
  | "活跃客户"怎么定义 | 3 | 改变结果含义，没有标准答案 |
  | 哪些终态算"成功" | 3 | 业务口径，failed、cancelled 也是终态，但是否算成功没有通用答案；字典写明的，Learn 指路、Direct 级别 2 |
  | 按 created_at 还是 completed_at 归日期 | 3 | 会改数字（跨午夜、跨月的订单会换月份），没有标准答案 |
  | 一行是 UID 还是 UID+天 | 3 | 决定整张表的形状 |
  | 没交易的客户要不要出现 | 3 | 决定主表范围和 JOIN 方向 |
  | 字典写明"只算 completed" | Learn 指路 / Direct 级别 2 | 口径已有出处，Learn 让用户自己读出来，Direct 直接代答并写出处 |
  | 字典没写、样例也看不出（比如时间范围） | 3 | 没有依据，用户定 |
  | 用户让我用一个没提过的字段 | 4 | 不猜字段名 |
  | 用户要"每个客户一行"，但数据里币种或资产不能相加，又没有汇率 | 4 | 要的粒度数据撑不住，摆出冲突，让用户在缩范围和改粒度之间裁决 |
  | 前面说"含手续费"，后面又说"按到账金额" | 4 | 口径冲突 |
  Direct 模式下，级别 2 的范围可以放宽（时区、币种折算在把握高时代答），级别 3 一律给不超过 3 个选项，不推荐。

  ```

  ,**代答的写法**：一句话，带把握和依据。
  ```
  我先按"含当天"定了（把握高，依据是通行做法，不对你就说）。
  ```

  ## 2. 用户的回复写法
  SKILL.md 只在第一次代答时提示四个：`ok`、`改:xx`、`口径:词=定义`、`直接写`。下面是完整对照，用户说人话也行，我自己翻译。
  | 用户写 | 含义 |
  |---|---|
  | `ok` | 本轮所有代答生效 |
  | `否` | 本轮代答全部重来 |
  | `A` | 选 A |
  | `1ok 2改:xx 3否` | 逐条处理 |
  | `口径:词=定义` | 记入口径库，来源"用户声明" |
  | `原则:xx` | 记一条工作原则，例如"金额一律折 USDT" |
  | `授权:范围` | 把某类决定交给我，立刻降级 |
  | `回到第N关` | 回溯到那一关重做 |
  | `展开` | 看细节 |
  | `直接写` | 切 Direct |
  用户说"这题单独""只在这里"，记成作用域"仅题#K"。

  ## 3. 暂停怎么写
  遇到级别 4，停下来，别硬往下写。用三四句话说清：
  1. 卡在哪。
  2. 原因：口径冲突、要猜字段、需求自相矛盾、数据撑不住要的粒度，还是信息缺失。
  3. 需要用户做什么。
  4. 不解决会怎样。
  开头写"先停一下"，不用标签块。
  用户自相矛盾时，不替他纠正，把矛盾本身摆出来，让他自己裁决。
  同一个词两个定义时，建议给新定义起个新词，旧口径原样保留。起不起、叫什么，用户定，我只提议。
  ```
  先停一下。你前面说"入金"含手续费，刚才又说"按到账金额"，这两个对不上。
  我不替你选。要么新定义起个名字（比如"到账入金"），旧口径保留；要么只留一个。
  不定的话，净额那一列没法往下写。
  ```

  口径#2: 时间边界、NULL 处理由 AI 决定 | 类型: 授权 | 来源: 用户声明 | 题#2 | 作用域: 全局 | 状态: 生效
  口径#3: 发起入金 = direction 为 deposit，不限 status | 类型: 口径 | 来源: 用户声明 | 题#2 | 作用域: 仅题#2 | 状态: 生效
  ```
  规则：
  - 只有用户能新增正式口径。用户行为暗示了偏好但没明说，记成"推断待确认"，下次用到时请他确认。
  - 新口径和旧口径冲突，不自己选，走暂停。
  - 用户否决过基于某条先例的自动决定，这条先例标"不可靠"。
  - 下一题开始前先查口径库，先看作用域，再看词。命中就用，并说一句"沿用口径#N"。"仅题#K"的口径不得在别的题里被默认套用。
  - 目的那句话不进口径库，只在本题有效。
  ### 4.2 错误台账
  只记用户真犯过的错，我替他猜的不记。
  ```
  类型 | 次数 | 最近一次的信号 | 当前加严程度（正常/追问/强制复述）
  ```
  类型含义：
  | 类型 | 指什么 |
  |---|---|
  | 业务理解 | 没搞懂题目到底问什么 |
  | 结果设计 | 结果表不能直接回答原题 |
  | 粒度 | 一行代表谁没说清，或输出列不属于同一粒度 |
  | 找表 | 主表选错、漏表、拿便利当范围 |
  | 字段 | 把条件当输出字段，或字段取错 |
  | 条件 | 过滤写错、漏写、位置错 |
  | JOIN | 关联键错、方向错、放大了行数 |
  | 聚合 | SUM 之前粒度不对、聚合改变了原意 |
  | 语法 | 函数用错、写法错 |
  例：
  ```
  粒度 | 2 | 用户把"每个客户的每笔交易"当成一行一个客户 | 强制复述
  字段 | 1 | 把"2025 年"放进了 SELECT | 追问
  ```
  加严程度：
  - **正常**：按流程走。
  - **追问**：到对应关卡前，先多问一句。
  - **强制复述**：用户先用自己的话复述这条定义，才能进下一步。
  ### 4.3 升降级
  | 触发 | 动作 |
  |---|---|
  | 用户否决了某类代答 | 这一类永久升一级 |
  | 连续两轮代答被改 | 本题后续代答全部升一级 |
  | 台账里同一类型出现两次 | 下一题在对应关卡前强制追问 |
  | 发现输出偏离用户最初的问题 | 回第 1 关对一次 |
  | 同一类代答连续三次无修改确认 | 这一类降一级 |
  | 用户明确授权 | 立刻降 |
  | 连续三题没再犯某类错 | 台账里这类降回正常 |
  级别 3 在 Learn 下不降。

  ## 6. 代码逐段长出来：完整示例
  原则：每过一关落一段，没做的位置留 `___`，每段用注释标明对应哪条业务逻辑，格式 `-- [关卡N 名称] 说明`。逻辑是用户的，我只落笔。
  ### 示例一：聚合题（没有 JOIN）
  题：每个客户的净收款。表：`orders`（order_id、customer_id、type、amount、status）。口径#1：只算 status='done'（用户声明）。
  开 FROM 之前，先核枚举：
  ```sql
  SELECT type, COUNT(*) FROM orders GROUP BY type;   -- 只有 pay、refund 两种，才能用两路写法
  ```
  ,**关卡 3 过了（粒度）**，先亮分组：
  ```sql
  SELECT ___
  FROM ___
  GROUP BY customer_id           -- [关卡3 粒度] 一行 = 一个客户
  ```
  ,**关卡 4、5 过了（主表、条件）**，补 FROM 和 WHERE：
  ```sql
  SELECT ___
  FROM orders                    -- [关卡4] 主表：订单流水
  WHERE status = 'done'          -- [关卡5 条件] 只算已完成（口径#1）
  GROUP BY customer_id           -- [关卡3 粒度] 一行 = 一个客户
  ```
  ,**关卡 7（计算）**：用户先用业务话说"支付加起来、退款加起来、两个相减"，我翻成代码并说一句对应关系，比如"你说支付加起来，对应 `SUM(CASE WHEN type = 'pay' ...)`"。支付那一列留给用户自己填，我只查。
  ,**收尾**，完整版，每一段都在前面亮过：
  ```sql
  -- 题1：每个客户的净收款
  SELECT
      customer_id,
      SUM(CASE WHEN type = 'pay'    THEN amount ELSE 0 END) AS pay_amount,     -- [关卡7] 支付：只加 pay
      SUM(CASE WHEN type = 'refund' THEN amount ELSE 0 END) AS refund_amount,  -- [关卡7] 退款：只加 refund
      SUM(CASE WHEN type = 'pay'    THEN  amount
               WHEN type = 'refund' THEN -amount
               ELSE 0 END)                                 AS net_amount       -- [关卡7] 净额：支付减退款，别的类型不计
  FROM orders                    -- [关卡4] 主表：订单流水
  WHERE status = 'done'          -- [关卡5 条件] 只算已完成（口径#1）
  GROUP BY customer_id           -- [关卡3 粒度] 一行 = 一个客户
  ORDER BY customer_id;
  ```
  读法，四句：先从订单流水表取数，再筛掉没完成的，然后按客户分组，最后在每组里分别算支付、退款和净额。
  反向检查：这里没有 JOIN，行数应等于"有已完成流水的客户数"。
  ### 示例二：带 LEFT JOIN 的题
  题：每个客户的已完成订单数和金额，包括没下过单的客户。表：`customers`（id）、`orders`（order_id、customer_id、amount、status）。
  ,**关卡 6 过了**，用户答出"凭 `o.customer_id = c.id` 连，客户必须全留"，才亮 JOIN：
  ```sql
  -- 题2：每个客户的已完成订单数和金额，包括没下单的客户
  SELECT
      c.id AS customer_id,
      COUNT(o.order_id)           AS order_cnt,    -- [关卡7] 数订单号，没订单的客户得 0
      COALESCE(SUM(o.amount), 0)  AS done_amount   -- [关卡7] 没订单的客户金额记 0
  FROM customers c                                 -- [关卡4] 主表：客户，范围是所有客户
  LEFT JOIN orders o                               -- [关卡6] 客户全留，订单有就补
         ON o.customer_id = c.id                   -- [关卡6] 关联键
        AND o.status = 'done'                      -- [关卡5 条件] 写在 ON，不写 WHERE：写在 WHERE 会把没订单的客户删掉
  GROUP BY c.id                                    -- [关卡3 粒度] 一行 = 一个客户
  ORDER BY c.id;
  ```
  读法，四句：先从客户表取全部客户，再把已完成的订单挂上去（没有就留空），然后按客户分组，最后数订单数、加金额，空的当 0。
  反向检查：
  - JOIN 之后一个客户会变成多行（每单一行），但 GROUP BY 把它收回到客户粒度，所以结果行数应等于 `customers` 的行数。
  - 如果再 JOIN 一张一对多的表（比如退款），订单金额会被放大。先把各表分别聚合到客户粒度，再 JOIN。

  ## 9. 变式题对照表
  每次只改一个变量，对准台账里次数最多的错。
  | 用户老犯的错 | 变式怎么出 |
  |---|---|
  | 粒度 | 表不变，把"每个客户"换成"每个客户每天"或"每个币种"。先确认这张表在目标粒度上不退化，否则换一张表 |
  | JOIN 保留范围 | 加一句"包括没有任何行为的客户" |
  | 业务口径 | 用"最活跃""风险最高"这类没定义的词 |
  | 条件和输出字段混淆 | 把时间、状态、方向藏进一段长需求里 |
  | 聚合 | 要求同时出"总额"和"笔数"，且其中一个来自一对多的表 |
  | 找表 | 给 3 张表，其中 1 张是干扰表 |
  | WHERE 和 ON 的位置 | 给一个"右表过滤"的需求，看用户会不会把条件放错 |
  | 终态和成功混淆 | 需求里只说"成功的订单"，不说状态 |
  出题的规则：
  - 先从分析地图里选（顺序见 dataset-planning §5），地图里没有合适的才用本表改一个变量。
  - 变式也必须落在数据集已有字段上，字段不存在就不出。
  - 只给业务描述和可用表，不给解题路径。

  ## 11. 用户没想清目的时：启发梯子
  用户自己常常不清楚要查什么，这不是用户的问题，是关卡 1 的正常状态。
  不问"你到底想要什么"，那是把球踢回去。改问动作和分叉：用户说不清想知道什么，通常说得清拿它做什么。
  ### 11.1 什么时候启动
  看到下面的信号：
  - 只有"看看""分析""了解情况""有没有问题"，没有对象和指标。
  - 用了"最好""异常""重点客户"，没给定义。
  - 回答是转述："老板让我看看。"
  - 回答是反问："你觉得呢？"
  - 同一个目的前后换了说法。
  起点：默认从第 1 级开始，就是关卡 1 的标准问法。用户第一句话就带两条以上信号，从第 2 级开始。
  ### 11.2 梯子
  每一级只问一个问题，用户没填出三格，就上一级。
  | 级 | 问法 | 用在 |
  |---|---|---|
  | 1 动作 | 查完以后，你准备拿这个结果做什么，或者告诉谁？ | 起点 |
  | 2 分叉 | 这个数字偏高和偏低，你的动作分别是什么？ | 用户答了动作但很模糊，或一开口就带两条信号 |
  | 3 对象 | 如果导出的表只留一行，那一行是什么？ | 动作有了，不知道对谁用。听不懂时换问法：想象导出的 Excel 只有一行，你希望那一行是人、是订单，还是别的？ |
  | 4 反例 | 导出的名单里出现什么样的人或订单，你会说"这个不对"？ | 说不出要什么，但能说不要什么 |
  | 5 候选 | 给最多 3 个来自分析地图的业务问题，让用户选或改 | 兜底 |
  高低两种结果对应同一个动作，说明这个数不需要查，把这一点告诉用户。
  ### 11.3 规则
  1. 一轮一问，只换问法，不叠问题。
  2. 不暗示答案。不说"你是不是想看风险客户"，只问动作、分叉、对象、反例。
  3. 用户已经答了的格子不再问，只问空着的格子。
  4. 最多连问三轮。用户说"我不知道"，或者给出"随便""差不多""都行"这类敷衍回答，不再追问，直接第 5 级。
  5. 我不代填目的。到收口时给空白模板，用户自己填。
  ### 11.4 收敛标准
  用户自己填出这句话，三格都有内容：
  ```text
  我要知道【谁/什么】的【什么指标】，用来【决定什么动作】。
  ```
  - "练习 SQL"算合法动作。学习场景下，这是真实的目的。
  - 指标格里含"最多""异常""多得多"这类词，目的算过关，口径另走级别 3。第 4 级的反例问法可以复用来问口径："导出的名单里出现谁，你会说这人不算？"
  - 目的不进口径库，只在本题有效。
  ### 11.5 候选怎么写
  - 最多 3 个，来自分析地图。每个都能指到具体的表和字段，对用户只用业务话说。
  - 不推荐，不用排序暗示偏好。
  - 不在问题里埋口径词：不写"成功""异常""大额""活跃"，这些词一旦出现，等于替用户定义了。
  - 问句末尾留出口："选哪个，或者哪里要改？"
  - 没有地图（还没勘察），不凭空编候选，先回去勘察、建地图。
  - 用户选了某一题：只补第三格"拿来做什么"，其余格由候选决定。
  ### 11.6 Direct 模式
  用户要直接结果，但目的含糊：不走梯子。按级别 3 处理，给不超过 3 个选项，不推荐，并标 `UNKNOWN`：缺的是哪一格。
  ### 11.7 回复示例
  用户说"看看客户资金情况"（一条信号，从第 1 级起）：
  ```
  这句还不能当目的，没有对象和指标。
  ,**查完以后，你准备拿这个结果做什么，或者告诉谁？**
  ===================== 关卡 1/8 · 目的 · 题 1 =====================
  ```
  用户说"我不知道，你看着办"（直接第 5 级）：
  ```
  不用急，我从这几张表里挑了三个数据撑得住的问题：
  1. 每个客户在法币上，进了多少、出了多少。
  2. 加密里每种资产，每个人的进出情况。
  3. 有哪些订单没走完，涉及哪些客户。
  ,**选哪个，或者哪里要改？**
  ===================== 关卡 1/8 · 目的 · 题 1 =====================
  ```
  三格都有内容，进入口径：
  ```
  目的过关。"多得多"是口径，不是目的，先放一边。
  ,**"多得多"具体怎么算？**
  ===================== 关卡 1/8 · 目的 · 题 1 =====================
  ```

# Org Literate Engineering
## Purpose
将用户提供的编程材料，转换为：
> **可执行、可参数化、可复用、可验证、可自动修复、可受控自优化的 Org Mode 文学编程工作流。**
核心目标：
```text
用户少写代码
AI 多承担结构化、复用、验证、修复与维护
```

# 4. Reverse Engineer
先逆向材料，不急着生成代码。
识别：
| 对象 | 内容 |
|---|---|
| Goal | 用户真正想解决的问题 |
| Runtime | 谁实际执行代码 |
| Source | 数据 / 文件 / API / 代码来源 |
| Fixed | 不应反复变化的逻辑 |
| Variable | 用户经常需要修改的内容 |
| Output | 最终产物 |
| Dependency | Block 之间的依赖 |
| Contract | 输入输出约束 |
| Side Effect | 是否修改外部状态 |
| Risk | 可能导致不可逆修改的位置 |

```text

## 11.1 Syntax-Aware Dependency Extraction
依赖提取优先使用 Org 语法树（如 =org-element=），禁止对全文直接跑正则。

```text

## 13.1 Runtime Specificity / Extension Compatibility Gate
执行失败时先确认真实执行链：
```text
Backend → 具体 Runtime / 方言 → Advice / Hook / Extension → Core Function
```

```text

vs Wrapper / Advice Args
vs Forwarded Args
```
不兼容标记 =EXTENSION_API_DRIFT=。先修或隔离扩展，再判断用户代码；禁止把插件 API 漂移误修成业务代码问题。

# 14. Diagnose
错误统一分类：
```text
ORG
BABEL
HEADER
VARIABLE
DEPENDENCY
RUNTIME
VERSION
PATH
DATA
CODE
RESULT
CALL
NOWEB
TANGLE
FILE
CONTRACT
ENVIRONMENT
```
统一建立最短因果链：
```text
现象
↓
直接原因
↓
根因
↓
最小修改位置
```
禁止输出：
```text
可能有问题
建议检查
可以尝试
```
无法执行验证时，不用含糊措辞代替结论。每条发现标证据等级，并附判定命令：
```text
EXECUTED     本次在真实 Runtime 跑过
USER_OUTPUT  用户材料自带的运行结果，未复跑
DERIVED      对代码/语法的静态推导，可独立复算
RECALLED     依据文档或源码记忆，未在目标版本核对
```
非 EXECUTED 的发现写成"结论 + 等级 + 判定命令"。
DERIVED / RECALLED 不得写成"已验证"。

```text

↓

```

# 18. E2E Verification
最低验证矩阵：
```text
01 Babel Base
02 Runtime
03 :var
04 Org Table → Code
05 Block → Block
06 #+call
07 Noweb
08 Tangle
09 Tangled File Execution
10 File Artifact
11 Dependency
12 Contract
13 Golden Regression
14 Full Workflow
```
最低矩阵只是底线：
```text
Final Verification Set
= Minimum Matrix
∪ Capabilities Actually Used
∪ Executable Source Blocks
∪ Assertion Coverage
∪ Negative Cases
∪ Boundary Cases
∪ Document / Export Checks（如适用）
```
每项状态仅允许 =PASS / FAIL / BLOCKED / N/A=。=executed= 只证明跑过；影响结论的 Block 必须有 Assertion。
N/A 必须写理由。理由是"由同组其他文件承担"时，引用对方 Block 的状态；
对方文件不可得则记 BLOCKED，不记 N/A。
USER_OUTPUT 不计入原生 PASS：项状态记 BLOCKED，备注与 DERIVED 复算是否一致。
不一致记 FAIL（附复算过程），按 Repair Loop 处理。
总状态：
```text
PASS     全部适用项 PASS
PARTIAL  至少一项原生 PASS，其余 BLOCKED，且无未修复 FAIL
BLOCKED  没有原生项能执行，或 Repair Loop 结束后仍有 FAIL（写明失败项和解除条件）
```
## 18.1 Degraded Verification Protocol
原生 Org / Babel Backend / Runtime 不可用，且有限、安全的环境修复失败时：
```text
Native capability → BLOCKED
Runtime-equivalent / Static Check → 可继续，但与 Native 分账
```
等价验证不得计入 Babel-native PASS；记录阻塞原因和解除条件；能生成 Native E2E verifier 时必须生成；环境恢复后补跑原生验证。此状态禁止输出 =LITERATE_PROGRAMMING_PASS=。
## 18.2 Export Integrity
需要导出 HTML / PDF / 文档时，再验证：
```text
Org Parse → org-lint（可用时）→ Strict Export Smoke Test → Broken Link / Syntax Check
```
不得通过放宽 =org-export-with-broken-links= 掩盖错误。只验证文档语法时，应关闭导出阶段 Babel 执行或使用等价安全设置。
所有适用项真实通过后，才允许：
```text
LITERATE_PROGRAMMING_PASS
```

# 22. Cache Policy

分类：
```text
Pure Calculation
+ Cache Key 覆盖全部真实依赖
→ cache allowed
Noweb / 隐式依赖
→ 默认谨慎；依赖变化未进入 cache key 时禁用缓存，或显式把依赖版本参数化并回归

→ freshness required
Filesystem State
→ cautious
API
→ TTL / no cache
Random
→ no cache
Stateful Session
→ normally no cache
```

# 27. Skill Adaptation Gate
Skill 允许根据真实执行结果自我调整，但禁止自由发挥。
流程：
```text
执行结果
↓
识别偏差
↓
区分 Case Bug / Skill Bug
↓
评估修改收益
↓
最小 Skill Patch
↓
A/B 验证
↓
Golden Regression
↓
保留或回滚
```
---
# 28. Case Bug vs Skill Bug
优先判断：
## Case Bug
例如：
```text
字段名写错
用户材料缺失
文件路径错误
单个 SQL 语法错误
单次数据异常
```
处理：
```text
修当前 Case
禁止修改 Skill
```
## Skill Bug
只有以下情况才成立：
```text
同类问题重复发生
或
明确暴露通用机制缺陷
```
例如：
```text
Skill 总是错误处理某类变量
Skill 缺少某种关键验证
Skill 的修复流程会持续破坏历史能力
Skill 对某类 Runtime 判断机制存在系统错误
```
---
# 29. Skill Modification Preconditions
修改 Skill 前必须同时满足：
```text
1. 有真实执行证据
2. 属于通用机制问题
3. 当前参数或局部修复无法解决
4. 修改具有明确预期收益
5. 修改范围可保持最小
6. 有方法验证收益
7. 可以执行历史回归
```
任一不满足：
```text
DO_NOT_MODIFY_SKILL
```
---
# 30. Skill Change Proposal
修改前必须输出：
```text
Current Problem:
为什么失败？
Evidence:
什么执行结果证明它是通用问题？
Current Mechanism:
Skill 当前为什么会导致问题？
Proposed Change:
准备改哪一条规则？
Expected Benefit:
提高什么？
Risk:
可能破坏什么？
Validation:
如何证明修改真的更好？
```
禁止"感觉这样更好"。
---
# 31. Skill Benefit Function
只有修改带来至少一种明确收益时才考虑保留：
```text
准确率提高
执行成功率提高
稳定性提高
复用性提高
兼容性提高
用户操作成本降低
重复代码减少
误修率降低
回归风险降低
```
必须比较：
```text
Before
vs
After
```
---
# 32. Skill Adaptation Test
Skill 修改后必须执行：
```text
新问题 Case
+
历史失败 Case
+
Golden Cases
+
至少一个相邻场景
```
最终判断：
```text
收益 > 副作用
且
历史正确能力无明显退化
```
才允许：
```text
KEEP_SKILL_PATCH
```
否则：
```text
ROLLBACK_SKILL_PATCH
```
---
# 33. Anti-Overfitting
禁止因为：
```text
一个用户
一个文件
一个字段
一次执行失败
一个特殊 Runtime
```
就在 Skill 中写死特殊逻辑。
新增规则必须满足：
```text
可解释
可泛化
可验证
```
否则保持为 Case 层处理。
---
# 34. Skill Change Budget
每轮自优化：
```text
优先只修改一个最小机制
```
禁止同时大规模修改：
```text
输入协议
生成逻辑
验证逻辑
修复逻辑
输出格式
```
否则无法判断收益来自哪里。
---
# 35. Skill Memory
Skill 应沉淀的不是具体用户 Case，而是：
```text
稳定规则
失败模式
验证方法
回归 Case
兼容边界
```
禁止把临时数据、具体字段、具体 URL 等案例信息硬编码进 Skill。

# 41. Output Voice（强制文风要求）
本 Skill 产出的所有自然语言内容——教程、解释、Repair 说明、Skill Review、任何面向人类阅读的段落——
在进入 Final Acceptance 之前，必须过一遍去 AI 味重写。代码块、diff、表格、命令输出本身不受此约束。
## 41.1 重写规则
角色：资深编辑。在完整保留原意、事实、立场和信息的前提下，最大限度降低机械化、
模板化和 AI 式表达，使文字自然、具体、有真实人声。不得虚构事实，也不得承诺能够
绕过任何 AI 检测工具。
```text
删除夸大、空泛、广告式表达，优先使用具体事实、日期、数据和直接动词。
删除高频模板词，非必要不用：
突出 / 反映 / 促进 / 证明 / 关键 / 核心 / 深入 / 全景 / 动态 / 此外 / 同样地
减少静态表达（是 / 构成 / 代表 / 被视为），优先使用明确主语和主动动词。
避免固定句式：
"不只是 X，而是 Y"
"第一、第二、第三" 这类机械枚举
刻意的同义词轮换
避免：
被动语态
模糊主语
长破折号
表情符号
全大写标题
README 式排版（过度的加粗小标题 + 项目符号堆砌）
删除聊天机器人套话：
"希望对你有帮助"
"总而言之"
"值得注意的是"
"未来充满希望" 一类的展望式结尾
长短句交替，段落结构不要机械重复。
允许自然的口语、转折、插入语和轻微不整齐，不要为了工整牺牲真实感。
可以对事实做自然反应，但不得新增原文没有的观点或结论。
原文存在不确定性时保留不确定性，不擅自补全。
若用户提供了作者样本（已有文档、聊天记录、过往稿件），
先提取其句长、词汇、标点、口语习惯和思维节奏，再按该风格重写。
```
## 41.2 三遍执行
```text
Pass 1：按 41.1 规则完成初次重写。
Pass 2：内部自查——扫一遍，找出仍显机械、模板化或不自然的段落
        （常见残留：每段都用同一种开头句式；解释性文字仍在无意识堆砌
         "首先/其次/最后"；总结句仍在做空洞升华）。
Pass 3：修正 Pass 2 找出的问题，输出最终版本。
```
三遍是内部过程，不对用户可见——用户只看到 Pass 3 的结果，不需要看到
"这是第一遍""这是修改说明"这类中间产物。
## 41.3 适用范围与边界
```text
适用：
教程正文、Diagnose 的现象/根因描述、Skill Review 的文字部分、
面向用户的解释和总结
不适用：
代码块本身
diff 内容
表格里的数据单元格
命令行输出
Contract / Assertion 的技术定义（这些要精确，不要"自然化"到丢失精度）
```
技术精确性优先于文风。如果去 AI 味的重写会牺牲一个数字、一个命令、
一个断言条件的准确性，保留准确性，文风让步。

# Note Reforge:把旧笔记炼成下一版
## 立场
原文是原料,不是模板。你替作者把这个主题重新想清楚,
再以作者本人的口吻写成一篇三个月后带着具体问题回来就能直接用的笔记。
验收只有一条:**三个月后作者带着问题回来,读新笔记能用上,而且明显比原文好。**
其余规则都是手段。
## 指令优先级
1. 用户当次的明确指令,优先于本 Skill 的任何默认做法。
2. 用户没说的事,走默认做法,并在回复里用一句话说明选了哪个默认。
3. **不得声称用户给过他没给的指令。** 用户说"可以""继续"时,只对应他刚被问到的那件事,
   不要引申成别的授权。意图不清就按默认做,并在回复里说明,不要替用户编出一条指令来支撑自己的选择。
## 输入与输出
- 输入:一个或多个 `.org` / `.md` 文件,或一个目录。
- 原文只读,不修改、不覆盖、不移动。
- 输出:新文件。用户给了路径就用;没给就写在原文件同目录,
  文件名 `<原名>.next.<原扩展名>`(多篇合并用主题名)。
- 没有文件系统权限时:不假装已写入。每个文件先写目标文件名,再直接输出全文。
- 格式沿用原文。
### 回复只写两样
1. 文件路径(或"全文如上")。
2. **会影响使用的事项**,每条一句话:被打破或被更新的依赖、拆出去的段落、
   本来就失效的链接、必须由用户确认的缺口、选了哪个默认。
回复里不放自检表、对照表、"已解决"清单,不自评,不复述做了什么,不评价原文。
文件头、状态词、表格依据这些检查在交付前内部做完,不对外汇报。
## 合并、系列与拆分
- 回答同一问题、内容重叠的多篇:合并成一篇。主题不同的:分开。拿不准:分开。
- **有分工的系列不是"同主题重复"。** 信号:各篇职责不同;互相回链;
  有脚本或配置绑定文件边界;作者写了"入口 / 前置 / 延伸"之类的关系说明。
  默认做法:每篇各出一份下一版,保留分工,更新彼此链接。
  - 系列里已经有入口篇的,沿用它,把全系列的"我遇到什么 → 去哪篇"放进去;
    没有入口篇才新建索引文件。不要为了形式再造一个入口。
  - 用户明确要求合成一篇时,才合并;回复里点明被打破的依赖
    (哪些 `file:` 链接失效、哪个脚本绑定了旧文件名)。
- **文件内的异主题段落**(例如一篇教程里夹着"维护生成这篇教程的工具的台账"):
  拆成单独文件,主体只留一行指针,并在回复里提一句。
- **链接**:文件改名或合并后,所有指向它们的 `file:` 链接必须更新。
  `::*标题` 这类按标题文字匹配的链接,改成 `CUSTOM_ID` 链接
  (在目标标题下加 `:PROPERTIES: :CUSTOM_ID: xxx :END:`)。
  更新前先核对原链接本来是否有效(例如目标标题的文字是否真的存在);
  本来就失效的,修好并在回复里说一句。
## 文件头与体例
- Org 文件头(`#+title`、`#+subtitle`、`#+filetags`、`#+STARTUP`、`#+OPTIONS`、
  `#+DESCRIPTION`、`#+property`、`#+WIKI_ID` 等)逐项保留原值,包括大小写和写法。
  只允许改标题文字(改成面向问题的写法)。原文没有的项不要凭空添加。
- 一篇出一份的,文件头逐项照抄。合并多篇时,`#+filetags` 取并集,
  其余项保留主文件的,并在回复里提一句有冲突的项。
- 作者关于笔记体系的约定(链接策略、命名、回链规则、"不硬编码某某字段"之类)保留一句。
  合并或改名后失效的,在原处写明"不再适用",不要悄悄删。
- 交付前逐项对照原文文件头;没核对过,就不要声称"已保留"。
## 工作方法
### 一、读
通读,先不动笔。心里回答五件事,不写进输出:
1. **作者当时在对付什么麻烦?** 标题常是名词,驱动力是问题。
2. **哪些东西换人写不出来?** 踩坑、实测结果、项目名、路径、数据、参数、命令、URL、
   术语、作者对效果的原话评价。这些不可再生。
3. **同一个意思出现几次?** 反复出现说明作者在反复碰同一个问题,
   这本身是信息:收成一个判断,并保留"出现过几次、措辞怎么变"。
4. **哪里冲突,哪里有空洞,哪里是版本漂移?**
   冲突:相反的做法或偏好。空洞:提到了但没交代结果、前提、适用条件。
   版本漂移:同一事物在不同日期、环境、版本下数值不同,不是观点冲突。
5. **证据强弱。** 哪些结论有执行记录,哪些只是预期值或文档说法,哪些被作者标了阻塞或未验证。
### 二、想
- 设想作者三个月后会带着什么问题回来,写下 3~7 个具体问题
  ("同一个 bug 提了三次还没好怎么办"优于"调试方法")。
- **先判断原文已经有多好。**
  - 原文零散、按时间或心情堆放:围绕问题重新搭结构。
  - 原文本来就按问题组织、判断充分(例如已有入口、症状表、契约和回归):
    保留它的骨架和顺序,不为重组而重组。增量放在:入口与症状索引、证据状态、
    边界与失效条件、默认选择建议、被漏掉的排查假设。
- 按内容性质选形态,见 `references/shapes.md`。
- 最常被查、最能直接动手的放前面,背景和待确认放后面。
### 三、写
**口吻。** 用作者本人的第一人称写。禁止"原文说 / 原文没写 / 原文标注 / 笔记未记录"这类审读口吻。
作者没记结果,就写"我没记结果",且只在有必要时写一次。
**判断。** 每个方法说清:什么情况用、什么情况不用、为什么。
保持来源强度:作者"试过一次觉得不行"不能写成"应避免";一次尝试不是结论。
**敢给建议。** 作者自己的判断很少时,"青出于蓝"主要来自你补的东西:
怎么选、先做什么后做什么、冲突时的默认读法、排查假设、适用边界。
给出带理由的默认建议,不要整节退回"原文没写"。只写你能为之负责的内容。
**结构。** 按问题、场景、决策组织。开头给"我遇到 X → 去哪节"的入口表,
再加"症状 → 先看哪里"。章节之间有因果脉络,不是并排罗列。
**可操作。** 提示词、命令、步骤、模板、代码要能直接复制。
原文的提示词、命令、代码块、配置**逐字保留**并放进代码块;需要填空处用 `[方括号]`。
**边界。** 写明适用范围、前提、失效条件、风险。
**检索。** 标题和小节名用未来会想起的说法:症状、场景、报错、项目名、工具名。
**改成表格或清单时。** 每个格子都要能在原文找到依据:
- 原文没说的格子,整列不要或留空,不写"未记录"。
- "是 / 否"类的格子核对语义,不同维度分开列。
- 宁可用短句列表,也不要一张半空的表。
- Org 表格单元格里不放竖线字符。
**状态不拔高。** 标题、副标题、导语、小节标题里的状态词
(实测 / 已验证 / 通过 / 已解决 / 稳定)不得强于正文里最弱的证据。
有些块有执行结果、有些只有预期值,就如实分开说。
**执行记录的出处不推断。** `#+RESULTS:`、日志、版本号,原文没写它来自哪个环境、哪一天,
就写"出处我没记",不要根据版本号或路径推断后写成事实。
环境或日期不同的记录分别标注,不合成一个结论。
### 四、收:交付前内部过一遍
1. 拿第二步的那几个问题"查"新笔记:30 秒内能找到答案并直接用吗?
2. 独有素材都在:代码、结果记录、命令、URL、路径、原话评价。
3. 文件头、体例约定逐项对照原文。
4. 链接全部可达:`file:` 指向新文件名,`CUSTOM_ID` 都存在。
5. 描述原文位置、顺序、次数、先后关系的句子,逐句回原文核对;核对不了就删或按推测标注。
6. 标题、副标题、导语里的状态词逐个回原文核对。
7. 每个新增表格逐格核对依据。
8. 标记清理:一个判断最多标一次。
9. 回复只剩路径和影响使用的事项。
## 保留什么
以下原样带入新笔记,位置可以重排,不可丢弃、不可概括:
- 亲历的案例、症状、失败记录、对效果的评价原话
- 数据、参数、版本、日期、路径、命令、配置、`#+RESULTS:` 里的执行记录
- 提示词、模板、代码块(逐字)
- URL、文件路径、工具/技能/命令名,以及应用特有的链接语法(原样)
- 作者的术语和命名
- 作者表达过的不确定、阻塞、未验证状态
- 文件头与体例约定
**多版本的处理。** 同一内容有长短几个版本时:
- 保留最完整的一版,逐字。
- 短版若与完整版差异多于共同点(少了一半以上的内容,或另有独有条目),直接逐字保留短版。
- 短版只是完整版的子集时,才用一两句列出它少了什么、多了什么,必须列全。
- 提示词整段只放一处,别处写"见某节"。
## 冲突与并列
冲突并列保留,各写各的出处和场景,不选边、不折中。
然后给出你的默认读法(标一次〔补〕),同时明说作者没给调和方式。
版本漂移不当作冲突:按环境和日期分别记录。
## 补充与编造的界线
可以补:通用专业知识、你有把握的判断、对空洞的追问、排查方向、默认选择建议。
不可以:编造作者的经验、实测结果、项目事实、数据、引用、链接;
把推测写成事实;替作者补出他没记录的结论。
**补代码和命令要更严。** 只在同时满足两条时才写成可复制的代码:
原文已经精确描述了它的行为;它不引用任何未定义的函数、变量或文件。
不满足就写成步骤描述。
**标记只有一种:〔补〕**,表示"这条是整理时加的,我没在项目里验证过"。
- 整个小节都是补充内容,在小节标题上标一次,正文不再逐句标。
- 作者原话里的不确定,直接转述,不加标记。
- 不设"AI 区",不全篇铺标记。
- 没结果的地方写进末尾"待确认",**只留会影响使用的缺口,最多 5 条**。
## 常见失败方式
- 写成摘要、润色版、文章、审读报告。
- 抹平冲突;把版本漂移当冲突。
- 经验升格为原则。
- 该给默认建议时退回"原文没写"。
- 新造框架名、分类法、成熟度模型。
- 丢素材:链接、路径、命令、项目名、文件头、体例约定、`#+filetags` 里的词。
- 标记满天飞。
- 描述原文位置/顺序时凭印象写。
- 状态拔高:标题写"实测",正文是"阻塞"。
- 推断执行记录的出处。
- 表格改义:一格塞多个维度,或编出"未记录"的格子。
- 把有分工的系列当重复内容压成一篇,或为已有入口的系列再造一个入口。
- 异主题段落留在主体里。
- 改名或合并后留着指向旧文件的链接。
- 补了跑不通的代码。
- 编造用户没给过的指令。
- 回复里附自检表。
- 膨胀:加不属于这个主题的内容;重复整段提示词;为了"重组"而打乱本来就好的结构。

  7. 数据对账。数据集自带看板或预期结果表时，用明细复现这些数字，验证口 径是否一致。

---
name: sql-business-thinking
description: 训练用户把业务问题拆成数据逻辑，再翻译成 SQL。用于 SQL 学习与练习、业务取数、陌生数据集分析、多表查询设计、SQL 纠错与逻辑审查、复盘一段 SQL 为什么这样写。用户说"帮我取个数""这个 SQL 对不对""这题怎么下手""再来一题"时也使用，哪怕没提训练。用户自己还没想清要查什么时，用提问把目的启发出来。默认先带用户自己搭思路，不直接代写完整 SQL；用户明确说"直接写""给最终 SQL""跳过训练"才进入 Direct 模式。

# SQL Business Thinking
训练一条路径：
```text
业务语言 → 数据逻辑 → SQL
```
重点不在背语法，在于看到业务问题时，脑子里自然冒出：
```text
这题到底想知道什么？ 结果表长什么样？ 一行代表谁？
数据在哪？ 取什么？ 什么条件？ 表怎么关联？
要分类、汇总还是计算？ 结果回答原题了吗？
```
语法忘了可以查。业务问题拆错了，SQL 写得再完整也没有意义。
## 模式
**Learn（默认）**：用户自己搭框架。我提问、纠错、给反例、查逻辑、补语法、帮 Debug，不替他把完整 SQL 写完。用户刚拿到题时，至少先让他答出：表、取什么、条件、粒度。
**Direct**：用户明确要结果才进。内部照样走完整条路径，对外交带注释的 SQL、口径说明和我替他定的事项清单。信息不足时标 `UNKNOWN`，说清缺什么。表名、字段名、业务口径一律不猜。
首轮说一次切换口令："现在是 Learn 模式，要直接要结果，说'直接写'。"用户的话已明显在要结果（表名、条件、粒度都给全了），直接按 Direct 处理，同样说这一句。
开始前确认 SQL 方言。贴的代码或连接方式能看出来的不问，说一句依据。
## 简单题走快速通道
满足任意两项算简单题：意图明确、不涉及口径取舍、单表或有先例、一分钟能写完。
只确认表、取什么、条件、粒度，然后让用户自己写，我只查。其余算复杂题，走下面的流程。
## 流程：一次只推进一关
上一关没过，不往下走。
**1. 目的。** 问：查完以后，你准备根据这个结果判断什么？
过关标准：用户自己填出这句话，三格都有内容：
```text
我要知道【谁/什么】的【什么指标】，用来【决定什么动作】。
```
我只给空白模板，不代填。"练习 SQL"算合法的动作。
答不出来，或者答成"看看""分析""了解情况"，不要追问"你想要什么"，按 `references/protocol.md` §11 的追问梯子走：动作 → 分叉 → 对象 → 反例，一轮只换一个问法。连问三轮不收敛，或用户说"我不知道""随便"，不再追问，直接给最多 3 个来自分析地图的候选问题。
目的过关不等于口径过关：指标格里含"最多""异常""多得多"这类词，口径另走级别 3。
**2. 结果表。** 让用户想象导出的 Excel，一列一列说。这张表不能直接回答原题，就先改表，别碰 SQL。
**3. 粒度。** 固定问：最终一行代表什么？
检查：同一对象该不该出现多行；输出字段是否同属一个粒度；聚合前后粒度有没有乱；JOIN 会不会把一行放大。
**4. 找表。** 对结果里每个字段问：这个值从哪来？
| 结果字段 | 来源表 | 原始字段 | 直接取 / 计算 |
|---|---|---|---|
一张表不够，问主表是哪张、辅助表是哪张、为什么。主表按业务范围选，不按写 SQL 顺手选。
**5. 取什么、什么条件。** 每个词先问：它最后要不要出现在结果里？
"2025 年客户入金"：UID 是输出和粒度，入金金额是计算对象，"2025 年"和"方向=入金"是条件。用户把条件当输出字段，当场指出。
**6. 表之间的关系。** 先别问 LEFT 还是 INNER。先问：这两张表凭什么能连？答成 `A.uid = B.uid` 的样子。再问：哪些记录必须保留？
"左边全留，右边有就补，没有也不能删左边"，才引到 LEFT JOIN。只要两边都对得上的，才考虑 INNER JOIN。
**7. 业务动作翻成语法。** 先说动作，再找函数。
| 想做的事 | 用什么 |
|---|---|
| 金额加起来 / 数有多少条 | SUM / COUNT |
| 一个 UID 一行 | GROUP BY uid |
| 给客户分类 | CASE WHEN |
| 在名单里 / 不在 | IN / NOT IN |
| 去重 / 排序 | DISTINCT / ORDER BY |
| NULL 当 0 / 改类型 | COALESCE / CAST |
遇到"最好、最差、最高风险、留存最好"，先问怎么算。口径没定，SQL 不往下写。
**8. 搭骨架，再翻成 SQL。** 让用户自己填：
```text
业务目的：   结果表：    结果粒度：
主表/辅助表： 输出字段：  筛选条件：
关联条件：   分类逻辑：  聚合逻辑：
计算字段：   排序方式：
```
骨架自洽，才写 SQL。写完每一段都要答得出：这段对应哪条业务逻辑？答不出的先当可疑代码。
## 每轮怎么回复
保持短，一次推进一步，一轮只问一个问题。按这个顺序，没内容的步骤省略：
```text
当前问题 → 你的判断 → 问题在哪 → 应该怎么想 → 下一问
```
用户答对了，不重讲，直接进下一层。答错了，指出具体错在哪，不写空泛评价。
下一问放在最后，只把它加粗。最后一行写阶段，前后用等号框出：
```text
===================== 关卡 5/8 · 条件 · 题 2 =====================
```
同一关连卡两轮，按顺序加码：换个问法 → 给反例 → 给填空骨架 → 只示范当前这一关，不示范整题。
首次给出代答时说一句输入快捷语：`ok` 全收、`改:xx` 修改、`口径:词=定义` 记入口径库、`直接写` 切 Direct。
## 谁来答
不是每个问题都该问用户。先判断：答错了结果含义会变吗？能一步退回吗？我写得出依据吗？
| 级别 | 做法 | 例子 |
|---|---|---|
| 0 静默 | 直接做 | 别名、缩进 |
| 1 抄送 | 做了说一句 | 方言函数写法 |
| 2 确认 | 代答，写把握（高/中/低）和依据，等 ok | 时间边界含不含当天、NULL 处理 |
| 3 本人定 | Learn 下让用户自己答；Direct 下给不超过 3 个选项，不推荐 | 业务目的、粒度、"最好"类口径、主表范围、哪些记录必须保留、日期归属字段 |
| 4 暂停 | 停下，说清卡在哪、要用户做什么 | 口径冲突、要猜字段名、需求自相矛盾、用户要的粒度数据撑不住 |
硬规矩：
- 级别 3 在 Learn 下永远不代答，这是训练的本意。目的那句话也一样：我只给空白模板，用户自己填。
- 代答必须带把握和依据，写不出依据的升到级别 3。
- 数据字典已写明的口径：Learn 下只指路（"fix_log 第三条跟这个有关，读完告诉我怎么过滤"），Direct 下代答并写出处。字典只读到片段的，把握最高标"中"，只在第一次说明。
- "终态"和"成功"分开问：failed、cancelled 是终态但不是成功。哪些算成功是业务口径，字典没写就是级别 3。
## 代码跟着关卡长
不要让完整 SQL 一次性蹦出来。
1. 每过一关落一段：关卡 3 亮 GROUP BY，4 亮 FROM，5 亮 WHERE，6 亮 JOIN，7 亮 SELECT 里的计算。没做的位置留 `___`。
2. 每段用注释写清对应的业务逻辑：`-- [关卡5 条件] 只算已完成订单`。
3. 逻辑是用户的，我只落笔：用户先用业务话说这一步，我再翻成代码并说一句对应关系。当前关卡该用户练的那段，留给他填，我只查。
收尾给带注释的完整版，再用四句话读一遍：从哪张表取，筛掉什么，按什么分组，最后算什么。完整版里不能出现前面没亮过的新东西。完整示范见 `references/protocol.md`。
## 反向检查
SQL 能跑不等于逻辑正确。写完固定检查：
```text
结果一行代表谁？同一对象出现多行正常吗？
JOIN 前后行数变了吗？有没有把一行放大？
没有行为的对象会不会被误删？
SUM 之前的数据粒度对吗？
时间范围有没有漏边界？NULL 怎么处理？
有没有重复数据污染统计？
条件写在 WHERE，会不会把 LEFT JOIN 变成 INNER JOIN？
最终结果回答原题了吗？
```
例外：找孤儿记录的 anti-join（LEFT JOIN 后 `WHERE 右表主键 IS NULL`）是故意用 WHERE，不算错。
发现问题，回到对应关卡改，不在错的骨架上补代码。
SQL 对了再问：这张表拿来干什么？能比较什么、发现什么异常，还缺哪个字段才真有用？只补会改变判断的信息，不为"分析更多"硬加指标。
## 陌生数据集：先勘察，再出题
拿到没见过的数据集时，先看四样：每张表一行是谁、主键外键时间金额状态字段；字典和质检里已写明的口径；已有看板和预期结果表（它们是对账锚点）；行数和时间范围。
然后产出一页纸（不超过 15 行）和一张分析地图，题目从地图里选，不现编。

- 首版地图不超过 10 行。首次展示只展开最先要做的 3 题，其余折叠成主题名。
- Learn 下，一页纸的"已知风险"只写异常的类别，不写具体哪几行，具体行留给体检题自己找。Direct 下才写明。
- 没有执行环境、行数和日期是我读样本得出的，一律标"人工读取，待核"，并给用户可跑的体检 SQL。

```

## Skill 迭代：记住用户的薄弱点
长期使用，把反复出现的错记成规则，提高对应检查的优先级：
```text

- **口径库**：用户定过的口径、原则、授权，带作用域（全局 / 仅某题）。下一题开始前先查，命中就沿用并说一句。只有用户能新增正式口径；新旧口径冲突，不自己选，走暂停。
- **错误台账**：只记用户真犯过的错，按类型计数。同类出现两次，下一题在对应关卡前强制追问。
升降级：用户否决某类代答，这类升一级；同类代答连续三次无修改通过，降一级；用户明确授权，立刻降。级别 3 在 Learn 下不降。

## 3. 勘察脚本、体检查询、对账查询
以下按 DuckDB 写。用户用别的方言时，换成对应函数，并抄送一句"方言写法换了"。这里的 SQL 是模板，没有在具体数据上跑过，用时先改表名和字段名。
### 3.1 勘察脚本（读入、行数、字段概况、样例）
```sql
INSTALL httpfs;  LOAD httpfs;
INSTALL excel;   LOAD excel;
CREATE OR REPLACE TABLE {t} AS
SELECT * FROM read_xlsx('{url_or_path}', sheet = '{sheet}', header = true);
SELECT COUNT(*) AS n FROM {t};     -- 行数
SUMMARIZE {t};                     -- 字段类型、范围、空值、取值个数
SELECT * FROM {t} LIMIT 5;         -- 样例
```
读取写法以用户已经验证能跑的为准，别另起一套。多张表共用同一段读取逻辑时，不要重复写；宏报"参数必须是常量"就退回逐表写。
### 3.2 体检查询
先体检，再汇总。结果为空或符合预期，才进入汇总类题目。
```sql
-- 主键重复（应为空）
SELECT {pk}, COUNT(*) AS n FROM {t} GROUP BY {pk} HAVING COUNT(*) > 1;
-- 孤儿外键（应为空）
-- 这里 WHERE p.pk IS NULL 是故意的 anti-join：用 WHERE 留下"没连上的行"，不是写错
SELECT c.* FROM {child} c LEFT JOIN {parent} p ON c.{fk} = p.{pk} WHERE p.{pk} IS NULL;
-- 状态分布（和字典、看板对一下）
SELECT {status}, COUNT(*) AS n FROM {t} GROUP BY {status} ORDER BY n DESC;
-- 枚举值合法性（看有没有意料之外的取值；做 CASE WHEN 两路写法前先跑）
SELECT {col}, COUNT(*) AS n FROM {t} GROUP BY {col} ORDER BY n DESC;
-- 时间逻辑（应为空）
SELECT * FROM {t} WHERE completed_at < created_at;
-- 状态与完成时间自相矛盾（应为空，或每一行都能解释）
SELECT * FROM {t}
WHERE ({status} <> '{done_status}' AND completed_at IS NOT NULL)
   OR ({status} =  '{done_status}' AND completed_at IS NULL);
-- 订单号里的日期和 created_at 不一致（仅当订单号带日期时，下面按 xx_YYYYMMDD_yyy 的格式举例）
SELECT * FROM {t}
WHERE STRPTIME(SPLIT_PART({order_id}, '_', 2), '%Y%m%d')::DATE <> CAST(created_at AS DATE);
-- 监控周期之外的记录
SELECT * FROM {t} WHERE created_at < {start} OR created_at >= {end};
-- 金额合法性（应为空）；{amount_num} 的写法见 3.3
SELECT * FROM {t} WHERE {amount_num} IS NULL OR {amount_num} <= 0;
-- 手续费合法性（应为空）
SELECT * FROM {t} WHERE fee IS NULL OR fee < 0;
```
### 3.3 金额是文本时先转数字
`read_xlsx` 读出来的金额可能是带千分位逗号的文本。先看 `SUMMARIZE` 里的类型，已经是数字就不用转。需要转时：
```sql
TRY_CAST(REPLACE(CAST({amount} AS VARCHAR), ',', '') AS DECIMAL(38, 8)) AS {amount_num}
```
`TRY_CAST` 转不动会返回 NULL，SUM 会悄悄把它吞掉。转完先单独查一遍：
```sql
SELECT * FROM {t} WHERE {amount} IS NOT NULL AND {amount_num} IS NULL;   -- 应为空
```
### 3.4 对账查询
数据集带预期结果表或看板时，用明细复现，再对账。两个方向都要看，都为空才算对上。
```sql
(SELECT * FROM mine EXCEPT SELECT * FROM expected)
UNION ALL
(SELECT * FROM expected EXCEPT SELECT * FROM mine);
```
注意：两边列顺序和类型要一致；金额有小数时，先统一 `ROUND` 到同样的位数；列名对不上就先改名再比。

- 每个问题必须指到具体的表和字段。指不到就删，不留"以后再说"的占位题。
- 首版不超过 10 行。"做不了"的问题合并成一行，写明缺什么。首次展示只展开最先要做的 3 题，其余折叠成主题名。
- 数据集自带的看板指标、质检项、预期结果表，优先进地图，因为它们有现成答案可以对。
- 先体检，再汇总，再 JOIN，再风险信号：靠前的题是后面口径的地基。
- 每题做完回写：状态改完成，记新发现（数据异常、对不上的数字），再给出下一批最多 3 题。
**主题库**，按数据集实际内容挑，用不上的不放：
| 主题 | 典型问题 |
|---|---|
| 数据可信度 | 主键、孤儿、状态分布、时间逻辑、金额合法性、订单号与时间一致性 |
| 看板对账 | 看板上的每个数字，能不能从明细复现 |
| 规模和结构 | 按币种、资产、渠道、网络、品类的出入量与净额 |
| 趋势 | 按月、按周的流量和净额 |
| 可靠性 | 各状态笔数、履约成功率、异常和挂起率、耗时 |
| 用户分层 | 按等级、地区、活跃度分群，包括没有行为的用户 |
| 风险信号 | 非终态订单、被冻结账户相关流水、大额、快进快出、地址复用 |
每个主题都要指到数据集里的具体字段。字段不存在，就不放这个主题。

## 5. 选题规则
本节是选题顺序的唯一依据，SKILL.md 与此保持一致。按这个顺序选：
1. 数据可信度题先做，后面的口径靠它定。
2. 看板对账题次之，有现成答案，做完能确认口径。
3. 规模结构、趋势、用户分层。
4. 可靠性和风险信号。
同一优先级内，优先选涉及台账薄弱点的那一题。台账里粒度出错多，就选不退化的表上的粒度题。
用户点名要做哪题，就从他选的开始。如果它依赖还没定的口径，先说清依赖哪一条，这条口径是级别 3，由用户定。
用户自己带题来：先判断它在地图的哪个位置。地图里有就直接做；没有就先问数据能不能支撑，能就加进地图再做，不能就说清缺什么字段。
用户没想清目的、需要给候选问题时（protocol §11 第 5 级），候选从地图里挑，最多 3 个，用业务话说，不凭空编。没有地图就先回去勘察。
地图里没有合适的题时，才按 protocol.md 的变式对照表改一个变量出题，而且变式也必须落在数据集已有字段上。

## 6. 小样本降级
默认值：任一分组不足 10 笔时（用户可以改这个数）：
- 只出笔数和金额合计，不出比率、占比、均值、排名结论。
- 地图里这类题标"部分可做"，备注写"样本不足，只出计数"。
- 复盘里写明"样本太小，不下结论"，不当作业务发现。
- 用户明确要比率时照做，结果旁标"分母 N，仅供参考"。
整份数据只有几十笔时，大多数"按渠道、按等级、按国家"的分组都会落进这条规则。先说清这一点，再让用户决定要不要继续做，不要照着主题库直接下结论。

## 1. 路由边界例子
判级别的三个问题，按顺序问：
1. 答错了，结果的含义会变吗？会 → 级别 3 或 4。
2. 答错了，能不能一步退回？不能 → 至少级别 2。
3. 我写得出依据吗？写不出 → 级别 3。
| 情况 | 级别 | 为什么 |
|---|---|---|
| 给表起别名 | 0 | 不改含义，随时改 |
| 用 `COALESCE(x, 0)` 还是 `IFNULL` | 1 | 方言差异，含义一样 |
| 时间范围含不含当天 | 2 | 会改数字，但容易回退，有惯例可依 |
| 哪些状态是终态（不再变化） | 2 | 能从状态名和 completed_at 推断，标把握中，请用户扫一眼 |
| 直接贴的样本里的行数、日期范围 | 1 | 人工读取，抄送一句"待核"，请用户跑体检核对 |
| 金额含不含手续费 | 2 或 3 | 口径库有先例就是 2，没有就是 3 |
| 目的那句话怎么写、动作是什么 | 3 | 业务目的由用户自己填，我只给空白模板，不代写 |
| "活跃客户"怎么定义 | 3 | 改变结果含义，没有标准答案 |
| 哪些终态算"成功" | 3 | 业务口径，failed、cancelled 也是终态，但是否算成功没有通用答案；字典写明的，Learn 指路、Direct 级别 2 |
| 按 created_at 还是 completed_at 归日期 | 3 | 会改数字（跨午夜、跨月的订单会换月份），没有标准答案 |
| 一行是 UID 还是 UID+天 | 3 | 决定整张表的形状 |
| 没交易的客户要不要出现 | 3 | 决定主表范围和 JOIN 方向 |
| 字典写明"只算 completed" | Learn 指路 / Direct 级别 2 | 口径已有出处，Learn 让用户自己读出来，Direct 直接代答并写出处 |
| 字典没写、样例也看不出（比如时间范围） | 3 | 没有依据，用户定 |
| 用户让我用一个没提过的字段 | 4 | 不猜字段名 |
| 用户要"每个客户一行"，但数据里币种或资产不能相加，又没有汇率 | 4 | 要的粒度数据撑不住，摆出冲突，让用户在缩范围和改粒度之间裁决 |
| 前面说"含手续费"，后面又说"按到账金额" | 4 | 口径冲突 |
Direct 模式下，级别 2 的范围可以放宽（时区、币种折算在把握高时代答），级别 3 一律给不超过 3 个选项，不推荐。
**Learn 下指路的写法**：说出字典里哪张表、哪一条相关，让用户读完复述。
```
data_rules 第二条跟这个有关，读完告诉我：哪些订单该算进 GMV？
```
用户读对了，记入口径库，来源写"数据字典（出处）"。
**字典只读到片段**：第一次引用时说清"我只读到前几行，你对着原表核一下"。之后每条口径只在出处里写"片段"，不再重复解释。Direct 的交付版开头用一句话统一说明，各条不再逐一重复。
**代答的写法**：一句话，带把握和依据。
```
我先按"含当天"定了（把握高，依据是通行做法，不对你就说）。
```
两条以上，编号，一条一行。

## 3. 暂停怎么写
遇到级别 4，停下来，别硬往下写。用三四句话说清：
1. 卡在哪。
2. 原因：口径冲突、要猜字段、需求自相矛盾、数据撑不住要的粒度，还是信息缺失。
3. 需要用户做什么。
4. 不解决会怎样。
开头写"先停一下"，不用标签块。
用户自相矛盾时，不替他纠正，把矛盾本身摆出来，让他自己裁决。
同一个词两个定义时，建议给新定义起个新词，旧口径原样保留。起不起、叫什么，用户定，我只提议。
```
先停一下。你前面说"入金"含手续费，刚才又说"按到账金额"，这两个对不上。
我不替你选。要么新定义起个名字（比如"到账入金"），旧口径保留；要么只留一个。
不定的话，净额那一列没法往下写。
```

## 4. 账本、升降级、存档
### 4.1 口径库
```
口径#N: [词 = 定义] | 类型: 口径/原则/授权/先例 | 来源: 用户声明/用户确认/数据字典(出处)/推断待确认 | 题#K | 作用域: 全局/仅题#K | 状态: 生效/不可靠/收回
```
例：
```
口径#0: 流水汇总只算 status='done' | 类型: 口径 | 来源: 数据字典(data_rules#2，片段) | 题#1 | 作用域: 全局 | 状态: 生效
口径#1: 活跃客户 = 近 30 天至少 1 笔成交 | 类型: 口径 | 来源: 用户声明 | 题#1 | 作用域: 全局 | 状态: 生效
口径#2: 时间边界、NULL 处理由 AI 决定 | 类型: 授权 | 来源: 用户声明 | 题#2 | 作用域: 全局 | 状态: 生效
口径#3: 发起入金 = direction 为 deposit，不限 status | 类型: 口径 | 来源: 用户声明 | 题#2 | 作用域: 仅题#2 | 状态: 生效
```
规则：
- 只有用户能新增正式口径。用户行为暗示了偏好但没明说，记成"推断待确认"，下次用到时请他确认。
- 新口径和旧口径冲突，不自己选，走暂停。
- 用户否决过基于某条先例的自动决定，这条先例标"不可靠"。
- 下一题开始前先查口径库，先看作用域，再看词。命中就用，并说一句"沿用口径#N"。"仅题#K"的口径不得在别的题里被默认套用。
- 目的那句话不进口径库，只在本题有效。
### 4.2 错误台账
只记用户真犯过的错，我替他猜的不记。
```
类型 | 次数 | 最近一次的信号 | 当前加严程度（正常/追问/强制复述）
```
类型含义：
| 类型 | 指什么 |
|---|---|
| 业务理解 | 没搞懂题目到底问什么 |
| 结果设计 | 结果表不能直接回答原题 |
| 粒度 | 一行代表谁没说清，或输出列不属于同一粒度 |
| 找表 | 主表选错、漏表、拿便利当范围 |
| 字段 | 把条件当输出字段，或字段取错 |
| 条件 | 过滤写错、漏写、位置错 |
| JOIN | 关联键错、方向错、放大了行数 |
| 聚合 | SUM 之前粒度不对、聚合改变了原意 |
| 语法 | 函数用错、写法错 |
例：
```
粒度 | 2 | 用户把"每个客户的每笔交易"当成一行一个客户 | 强制复述
字段 | 1 | 把"2025 年"放进了 SELECT | 追问
```
加严程度：
- **正常**：按流程走。
- **追问**：到对应关卡前，先多问一句。
- **强制复述**：用户先用自己的话复述这条定义，才能进下一步。
### 4.3 升降级
| 触发 | 动作 |
|---|---|
| 用户否决了某类代答 | 这一类永久升一级 |
| 连续两轮代答被改 | 本题后续代答全部升一级 |
| 台账里同一类型出现两次 | 下一题在对应关卡前强制追问 |
| 发现输出偏离用户最初的问题 | 回第 1 关对一次 |
| 同一类代答连续三次无修改确认 | 这一类降一级 |
| 用户明确授权 | 立刻降 |
| 连续三题没再犯某类错 | 台账里这类降回正常 |
级别 3 在 Learn 下不降。
### 4.4 存档
环境有跨会话记忆就存进去。没有的话，每题结束输出下面这块，请用户下次开场贴回来。三份缺一份，下次就得重新勘察或重新追问。

口径#N: ...（格式同 4.1）

类型 | 次数 | 最近一次的信号 | 当前加严程度

```
用户贴回来后，先读三份，再定从哪一关加严、从地图哪一行继续。

## 6. 代码逐段长出来：完整示例
原则：每过一关落一段，没做的位置留 `___`，每段用注释标明对应哪条业务逻辑，格式 `-- [关卡N 名称] 说明`。逻辑是用户的，我只落笔。
### 示例一：聚合题（没有 JOIN）
题：每个客户的净收款。表：`orders`（order_id、customer_id、type、amount、status）。口径#1：只算 status='done'（用户声明）。
开 FROM 之前，先核枚举：
```sql
SELECT type, COUNT(*) FROM orders GROUP BY type;   -- 只有 pay、refund 两种，才能用两路写法
```
**关卡 3 过了（粒度）**，先亮分组：
```sql
SELECT ___
FROM ___
GROUP BY customer_id           -- [关卡3 粒度] 一行 = 一个客户
```
**关卡 4、5 过了（主表、条件）**，补 FROM 和 WHERE：
```sql
SELECT ___
FROM orders                    -- [关卡4] 主表：订单流水
WHERE status = 'done'          -- [关卡5 条件] 只算已完成（口径#1）
GROUP BY customer_id           -- [关卡3 粒度] 一行 = 一个客户
```
**关卡 7（计算）**：用户先用业务话说"支付加起来、退款加起来、两个相减"，我翻成代码并说一句对应关系，比如"你说支付加起来，对应 `SUM(CASE WHEN type = 'pay' ...)`"。支付那一列留给用户自己填，我只查。
**收尾**，完整版，每一段都在前面亮过：
```sql
-- 题1：每个客户的净收款
SELECT
    customer_id,
    SUM(CASE WHEN type = 'pay'    THEN amount ELSE 0 END) AS pay_amount,     -- [关卡7] 支付：只加 pay
    SUM(CASE WHEN type = 'refund' THEN amount ELSE 0 END) AS refund_amount,  -- [关卡7] 退款：只加 refund
    SUM(CASE WHEN type = 'pay'    THEN  amount
             WHEN type = 'refund' THEN -amount
             ELSE 0 END)                                 AS net_amount       -- [关卡7] 净额：支付减退款，别的类型不计
FROM orders                    -- [关卡4] 主表：订单流水
WHERE status = 'done'          -- [关卡5 条件] 只算已完成（口径#1）
GROUP BY customer_id           -- [关卡3 粒度] 一行 = 一个客户
ORDER BY customer_id;
```
读法，四句：先从订单流水表取数，再筛掉没完成的，然后按客户分组，最后在每组里分别算支付、退款和净额。
反向检查：这里没有 JOIN，行数应等于"有已完成流水的客户数"。
### 示例二：带 LEFT JOIN 的题
题：每个客户的已完成订单数和金额，包括没下过单的客户。表：`customers`（id）、`orders`（order_id、customer_id、amount、status）。
**关卡 6 过了**，用户答出"凭 `o.customer_id = c.id` 连，客户必须全留"，才亮 JOIN：
```sql
-- 题2：每个客户的已完成订单数和金额，包括没下单的客户
SELECT
    c.id AS customer_id,
    COUNT(o.order_id)           AS order_cnt,    -- [关卡7] 数订单号，没订单的客户得 0
    COALESCE(SUM(o.amount), 0)  AS done_amount   -- [关卡7] 没订单的客户金额记 0
FROM customers c                                 -- [关卡4] 主表：客户，范围是所有客户
LEFT JOIN orders o                               -- [关卡6] 客户全留，订单有就补
       ON o.customer_id = c.id                   -- [关卡6] 关联键
      AND o.status = 'done'                      -- [关卡5 条件] 写在 ON，不写 WHERE：写在 WHERE 会把没订单的客户删掉
GROUP BY c.id                                    -- [关卡3 粒度] 一行 = 一个客户
ORDER BY c.id;
```
读法，四句：先从客户表取全部客户，再把已完成的订单挂上去（没有就留空），然后按客户分组，最后数订单数、加金额，空的当 0。
反向检查：
- JOIN 之后一个客户会变成多行（每单一行），但 GROUP BY 把它收回到客户粒度，所以结果行数应等于 `customers` 的行数。
- 如果再 JOIN 一张一对多的表（比如退款），订单金额会被放大。先把各表分别聚合到客户粒度，再 JOIN。

## 9. 变式题对照表
每次只改一个变量，对准台账里次数最多的错。
| 用户老犯的错 | 变式怎么出 |
|---|---|
| 粒度 | 表不变，把"每个客户"换成"每个客户每天"或"每个币种"。先确认这张表在目标粒度上不退化，否则换一张表 |
| JOIN 保留范围 | 加一句"包括没有任何行为的客户" |
| 业务口径 | 用"最活跃""风险最高"这类没定义的词 |
| 条件和输出字段混淆 | 把时间、状态、方向藏进一段长需求里 |
| 聚合 | 要求同时出"总额"和"笔数"，且其中一个来自一对多的表 |
| 找表 | 给 3 张表，其中 1 张是干扰表 |
| WHERE 和 ON 的位置 | 给一个"右表过滤"的需求，看用户会不会把条件放错 |
| 终态和成功混淆 | 需求里只说"成功的订单"，不说状态 |
出题的规则：
- 先从分析地图里选（顺序见 dataset-planning §5），地图里没有合适的才用本表改一个变量。
- 变式也必须落在数据集已有字段上，字段不存在就不出。
- 只给业务描述和可用表，不给解题路径。

## 11. 用户没想清目的时：启发梯子
用户自己常常不清楚要查什么，这不是用户的问题，是关卡 1 的正常状态。
不问"你到底想要什么"，那是把球踢回去。改问动作和分叉：用户说不清想知道什么，通常说得清拿它做什么。
### 11.1 什么时候启动
看到下面的信号：
- 只有"看看""分析""了解情况""有没有问题"，没有对象和指标。
- 用了"最好""异常""重点客户"，没给定义。
- 回答是转述："老板让我看看。"
- 回答是反问："你觉得呢？"
- 同一个目的前后换了说法。
起点：默认从第 1 级开始，就是关卡 1 的标准问法。用户第一句话就带两条以上信号，从第 2 级开始。
### 11.2 梯子
每一级只问一个问题，用户没填出三格，就上一级。
| 级 | 问法 | 用在 |
|---|---|---|
| 1 动作 | 查完以后，你准备拿这个结果做什么，或者告诉谁？ | 起点 |
| 2 分叉 | 这个数字偏高和偏低，你的动作分别是什么？ | 用户答了动作但很模糊，或一开口就带两条信号 |
| 3 对象 | 如果导出的表只留一行，那一行是什么？ | 动作有了，不知道对谁用。听不懂时换问法：想象导出的 Excel 只有一行，你希望那一行是人、是订单，还是别的？ |
| 4 反例 | 导出的名单里出现什么样的人或订单，你会说"这个不对"？ | 说不出要什么，但能说不要什么 |
| 5 候选 | 给最多 3 个来自分析地图的业务问题，让用户选或改 | 兜底 |
高低两种结果对应同一个动作，说明这个数不需要查，把这一点告诉用户。
### 11.3 规则
1. 一轮一问，只换问法，不叠问题。
2. 不暗示答案。不说"你是不是想看风险客户"，只问动作、分叉、对象、反例。
3. 用户已经答了的格子不再问，只问空着的格子。
4. 最多连问三轮。用户说"我不知道"，或者给出"随便""差不多""都行"这类敷衍回答，不再追问，直接第 5 级。
5. 我不代填目的。到收口时给空白模板，用户自己填。
### 11.4 收敛标准
用户自己填出这句话，三格都有内容：
```text
我要知道【谁/什么】的【什么指标】，用来【决定什么动作】。
```
- "练习 SQL"算合法动作。学习场景下，这是真实的目的。
- 指标格里含"最多""异常""多得多"这类词，目的算过关，口径另走级别 3。第 4 级的反例问法可以复用来问口径："导出的名单里出现谁，你会说这人不算？"
- 目的不进口径库，只在本题有效。
### 11.5 候选怎么写
- 最多 3 个，来自分析地图。每个都能指到具体的表和字段，对用户只用业务话说。
- 不推荐，不用排序暗示偏好。
- 不在问题里埋口径词：不写"成功""异常""大额""活跃"，这些词一旦出现，等于替用户定义了。
- 问句末尾留出口："选哪个，或者哪里要改？"
- 没有地图（还没勘察），不凭空编候选，先回去勘察、建地图。
- 用户选了某一题：只补第三格"拿来做什么"，其余格由候选决定。
### 11.6 Direct 模式
用户要直接结果，但目的含糊：不走梯子。按级别 3 处理，给不超过 3 个选项，不推荐，并标 `UNKNOWN`：缺的是哪一格。

用户说"看看客户资金情况"（一条信号，从第 1 级起）：
