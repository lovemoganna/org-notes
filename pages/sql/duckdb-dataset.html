**** Design
#+begin_src markdown
  请围绕“先想最终那张表”这个思路，生成一份可直接用于 DuckDB 入门练习的
  Spreadsheet 数据集。目标不是单纯造数据，而是让零基础读者通过数据直观看
  懂：**业务问题 → 最终结果表 → 原始数据 → SQL 处理逻辑**
 
  以“统计 2025 年每个客户的出入金”为例。先定义最终结果：
 
  | uid | 入金总额 | 出金总额 | 差额 |
  |-----|---------:|---------:|-----:|
 
  一行代表一个 UID。再反推需要的原始流水：
 
  | uid | 时间 | direction | amount |
  |-----|------|-----------|-------:|
 
  数据集必须能够支持用户逐步理解：
  1. `FROM`：数据从哪里来；
  2. `WHERE`：筛选 2025 年及目标业务范围；
  3. `CASE WHEN`：区分入金和出金；
  4. `SUM`：汇总金额；
  5. `GROUP BY uid`：把一个 UID 的多笔流水压成一行；
  6. 计算最终差额。
 
  Spreadsheet 至少包含：
  ,* `raw_transactions`：原始流水；
  ,* `expected_result`：正确聚合结果；
  ,* `data_rules`：字段与业务约束；
  ,* `qa_result`：自动质检结果。
 
  生成前先解析当前需求并固化约束，包括：
  1. 字段类型；
  2. UID、时间、方向、金额规则；
  3. 2025 年时间范围；
  4. 入金 / 出金枚举；
  5. 金额有效范围；
  6. 正常、异常、边界样本；
  7. 原始流水与最终结果的一致性。
 
  生成后自动质检：
  1. 字段是否完整；
  2. 数据类型是否正确；
  3. 是否存在非法方向或金额；
  4. 是否有必要的多笔流水样本；
  5. 是否覆盖纯入金、纯出金、同时存在出入金、零差额等场景；
  6. `expected_result` 是否能够由原始流水正确计算得到；
  7. 是否存在重复、矛盾或无法解释的数据。
 
  发现问题后自动修正并重新验证，未通过质检不得交付。最终目标：**读者打开
  Spreadsheet，就能直接看懂“原始流水为什么要被处理成最终结果表”，并能据
  此练习 SQL。**
#+end_src
**** Loop
#+begin_src markdown
  @data 这个出入金的数据不够真实，一般交易所分为两类：法币和链上，而且订
  单号不会这么假。请举一反三进行修正，当前生成数据集的质量较差。请将数据
  生成流程改造成自动质检闭环：**需求解析→ 数据约束 → 数据生成 → 自动质检
  → 修正 → 再验收**。然后返还优化好的完整需求方案。
 
  具体要求：
  1. 生成前先扫描当前需求、Schema、字段定义、业务规则和表间关系；
  2. 自动提取并固化约束，包括： 
     - 字段类型与取值范围； 
     - 必填与唯一性； 
     - 时间、金额等业务逻辑； 
     - 主外键及跨表关联； 
     - 正常、异常、边界场景的覆盖要求；
  3. 按约束生成数据，不允许脱离需求自由发挥；
  4. 生成后自动检查： 
     - 完整性；
     - 一致性；
     - 有效性；
     - 唯一性；
     - 引用完整性；
     - 业务逻辑一致性；
     - 场景覆盖是否充分；
  5. 发现问题后自动定位原因并修正，再重新质检； 
  6. 未通过验收的数据集不得作为最终结果。最终输出必须包含：
     - 数据集；
     - 生成约束；
     - 质检结果；
     - 发现的问题；
     - 修正记录；
     - 最终通过项与仍存在的风险。
  目标不是“生成看起来真实的数据”，而是生成**符合当前需求、关系正确、逻辑一致、可直接用于测试和分析的数据集**。

**** Last Plan
#+begin_src markdown
  请重新设计当前 DuckDB 教学数据集。
  目标不是生成“像交易所”的假数据，而是生成一套**业务结构合理、关系正确、可计算、可验证**的交易所出入金数据，用于零基础 SQL 学习。
  整体流程必须形成闭环：
  ,**需求解析 → 数据约束 → 数据生成 → 自动质检 → 自动修正 → 再验收**
  ---
  ## 1. 先定义业务边界
  交易所出入金至少拆成两个独立业务域：
  ### 法币出入金
  表示用户通过银行、支付渠道等完成的法币充值和提现。
  至少包含：
  ,* `fiat_order_id`
  ,* `uid`
  ,* `direction`
  ,* `currency`
  ,* `amount`
  ,* `fee`
  ,* `channel`
  ,* `status`
  ,* `created_at`
  ,* `completed_at`
  `direction`：
  ,* `deposit`
  ,* `withdrawal`
  典型状态应符合实际业务过程，例如：
  ,* `pending`
  ,* `processing`
  ,* `completed`
  ,* `failed`
  ,* `cancelled`
  ---
  ### 链上充提
  表示用户通过区块链地址完成的数字资产充值和提现。
  至少包含：
  ,* `crypto_order_id`
  ,* `uid`
  ,* `direction`
  ,* `asset`
  ,* `network`
  ,* `amount`
  ,* `fee`
  ,* `tx_hash`
  ,* `address`
  ,* `status`
  ,* `confirmations`
  ,* `created_at`
  ,* `completed_at`
  链上数据必须体现：
  ,* 币种；
  ,* 网络；
  ,* 地址；
  ,* TxHash；
  ,* 区块确认；
  ,* 网络手续费；
  ,* 链上交易状态。
  法币字段不得硬套到链上，链上专属字段也不得伪造到法币订单中。
  ---
  ## 2. 订单号必须接近真实系统数据特征
  不得继续使用：
  ```text
  ORDER001
  TX001
  001
  ```
  这类明显人工编造的编号。
  订单号应具备真实业务系统常见特征：
  ,* 全局唯一；
  ,* 长度稳定；
  ,* 无明显连续规律；
  ,* 可包含时间信息、业务前缀或随机字符；
  ,* 同一业务域保持统一格式；
  ,* 法币订单与链上订单可区分。
  不要复制某家真实交易所的内部订单规则，只需生成符合真实系统特征的模拟 ID。
  `tx_hash` 必须符合对应区块链的基本格式约束，不能使用普通字符串冒充。
  ---
  ## 3. 不得混算不同计价单位
  禁止直接执行：
  ```text
  1000 TRY + 500 USDT + 0.2 ETH
  ```
  每个聚合结果必须保留对应维度。
  法币至少按：
  ```text
  uid + currency
  ```
  聚合。
  链上至少按：
  ```text
  uid + asset + network
  ```
  聚合。
  因此最终结果应拆分为：
  ### `expected_fiat_result`
  | uid | currency | deposit_amount | withdrawal_amount | net_amount |
  | --- | -------- | -------------: | ----------------: | ---------: |
  ### `expected_crypto_result`
  | uid | asset | network | deposit_amount | withdrawal_amount | net_amount |
  | --- | ----- | ------- | -------------: | ----------------: | ---------: |
  其中：
  ```text
  net_amount = deposit_amount - withdrawal_amount
  ```
  只统计满足业务定义的有效成功订单。
  ---
  ## 4. Spreadsheet 结构
  至少包含以下 Sheet：
  ### `users`
  用户基础维表。
  一行代表一个 UID。
  ---
  ### `fiat_transactions`
  法币出入金原始订单。
  一行代表一笔法币订单。
  ---
  ### `crypto_transactions`
  链上充提原始订单。
  一行代表一笔链上订单。
  ---
  ### `expected_fiat_result`
  由 `fiat_transactions` 正确聚合得到的标准答案。
  ---
  ### `expected_crypto_result`
  由 `crypto_transactions` 正确聚合得到的标准答案。
  ---
  ### `data_rules`
  记录：
  ,* 字段定义；
  ,* 数据类型；
  ,* 是否必填；
  ,* 唯一性；
  ,* 枚举；
  ,* 业务规则；
  ,* 表间关系；
  ,* 允许为空的条件。
  ---
  ### `qa_result`
  记录所有自动质检结果。
  至少包含：
  ```text
  check_id
  check_type
  table_name
  rule
  result
  affected_rows
  severity
  details
  ```
  ---
  ### `fix_log`
  记录：
  ```text
  发现什么问题
  → 为什么错误
  → 修改了什么
  → 修改后是否通过
  ```
  ---
  ## 5. 统一字段与 SQL
  所有字段统一使用：
  ```text
  lower_snake_case
  ```
  禁止出现：
  ```text
  入金金额
  depositAmount
  Deposit_Amount
  ```
  等多套命名并存。
  SQL 字段、Spreadsheet 字段、Schema 和 `expected_result` 必须完全一致。
  教程中的中文只负责解释业务含义，不进入字段名。
  ---
  ## 6. 数据生成前必须自动解析约束
  生成任何数据前，先扫描：
  ,* 当前需求；
  ,* Schema；
  ,* Sheet；
  ,* 字段定义；
  ,* 主键；
  ,* 外键；
  ,* 枚举；
  ,* 时间规则；
  ,* 金额规则；
  ,* 状态机；
  ,* 表间关系；
  ,* SQL 最终输出结构。
  自动生成一份 Data Contract，再开始生成数据。
  没有明确依据的规则不得自行补成“事实”。
  确需假设时必须显式记录。
  ---
  ## 7. 必须覆盖的样本
  不能只生成正常数据。
  至少覆盖：
  ### 正常场景
  ,* 单笔入金；
  ,* 单笔出金；
  ,* 同一 UID 多笔订单；
  ,* 同一 UID 同时存在入金与出金；
  ,* 多 UID；
  ,* 多币种；
  ,* 多链；
  ,* 不同金额；
  ,* 不同日期。
  ### 业务边界
  ,* 只有入金；
  ,* 只有出金；
  ,* 入金与出金金额相同；
  ,* 极小金额；
  ,* 较大金额；
  ,* 年初、年末订单；
  ,* 创建时间与完成时间跨日期。
  ### 状态场景
  ,* completed；
  ,* pending；
  ,* failed；
  ,* cancelled。
  聚合 SQL 必须明确哪些状态计入结果。
  ### 数据质量异常
  主动构造少量用于学习质检的异常样本，例如：
  ,* 重复订单号；
  ,* 非法枚举；
  ,* 不存在的 UID；
  ,* 完成时间早于创建时间；
  ,* 非法币种或网络组合；
  ,* 缺失 TxHash；
  ,* 重复 TxHash；
  ,* 非法地址格式；
  ,* 金额异常。
  异常数据必须有明确测试目的，不得随机制造脏数据。
  ---
  ## 8. 自动质检
  生成完成后自动执行以下检查。
  ### Schema
  检查：
  ,* 字段是否缺失；
  ,* 类型是否正确；
  ,* 字段名是否一致；
  ,* 是否出现额外未知字段。
  ### 完整性
  检查：
  ,* 必填字段；
  ,* 条件必填字段；
  ,* NULL；
  ,* 空字符串；
  ,* 无意义默认值。
  ### 唯一性
  检查：
  ,* `uid`
  ,* `fiat_order_id`
  ,* `crypto_order_id`
  以及其他要求唯一的业务标识。
  ### 引用完整性
  检查：
  ```text
  transactions.uid
  → users.uid
  ```
  不得存在无来源 UID，除非该记录本身就是故意设计的异常测试 Case。
  ### 有效性
  检查：
  ,* direction；
  ,* status；
  ,* currency；
  ,* asset；
  ,* network；
  ,* 金额范围；
  ,* 时间范围；
  ,* ID 格式；
  ,* 地址及 TxHash 基本格式。
  ### 业务一致性
  例如：
  ,* `completed_at >= created_at`；
  ,* failed / cancelled 订单不得进入成功金额统计；
  ,* completed 链上订单应满足对应业务要求；
  ,* 资产必须支持对应 network；
  ,* 手续费不得出现明显不合理关系；
  ,* 法币订单不得出现链上字段。
  ### 聚合一致性
  重新使用原始数据计算结果，并与：
  ,* `expected_fiat_result`
  ,* `expected_crypto_result`
  进行双向比较。
  任何 UID、币种、资产、网络、金额或行数不一致，都判定失败。
  ---
  ## 9. 自动修正 Loop
  发现问题后不得直接交付。
  必须执行：
  ```text
  检测问题
  ↓
  定位违反的规则
  ↓
  定位受影响记录
  ↓
  修正数据
  ↓
  重新运行全部相关检查
  ↓
  检查是否产生新的问题
  ↓
  通过后交付
  ```
  修复一项问题后必须执行回归检查，不能只重新检查当前规则。
  ---
  ## 10. 最终交付
  必须同时交付：
  1. 完整 Spreadsheet 数据集；
  2. Schema；
  3. Data Contract；
  4. 数据生成约束；
  5. 场景覆盖清单；
  6. 自动质检结果；
  7. 发现的问题；
  8. 修正记录；
  9. 最终验收结果；
  10. 未解决风险；
  11. 与数据完全对应、可直接执行的 DuckDB SQL。
  不得只交付数据文件。
  ---
  ## 11. 最终验收标准
  只有同时满足以下条件才算通过：
  ,* 表的业务粒度明确；
  ,* 法币与链上业务正确分离；
  ,* 主外键关系正确；
  ,* 订单号与业务标识不存在明显人工假数据特征；
  ,* 时间、金额、状态符合业务逻辑；
  ,* 不同币种和资产不存在错误混算；
  ,* 正常、异常、边界场景均有覆盖；
  ,* SQL 可以直接执行；
  ,* SQL 输出与 `expected_result` 完全一致；
  ,* 所有自动质检通过；
  ,* 修正后未引入新的回归问题。
  最终目标不是：
  ,**“生成一批看起来像真的交易所数据。”**
  而是：**生成一套业务结构合理、数据关系正确、SQL 可计算、结果可验证、异常可解释、能够直接用于 DuckDB 教学和自动化测试的数据集。**

***** Stage 3
#+begin_src markdown
  在现有数据生成与质检流程后，增加一套 Spreadsheet 自动排版与视觉质检流程：
  ,**数据验收 → 结构识别 → 视觉规范 → 自动排版 → UI 质检 → 修正 → 最终验收**
  ## 1. 先理解每个 Sheet 的用途
  自动识别：
  ,* 原始数据表；
  ,* 结果表；
  ,* 规则表；
  ,* 质检表；
  ,* 修正记录表。
  根据用途决定布局，不允许所有 Sheet 套同一种样式。
  ## 2. 建立统一视觉规范
  整份工作簿统一：
  ,* 字体；
  ,* 字号层级；
  ,* 表头样式；
  ,* 背景色；
  ,* 边框；
  ,* 对齐；
  ,* 行高；
  ,* 列宽；
  ,* 数字格式；
  ,* 日期格式；
  ,* 状态颜色。
  控制颜色数量，只保留少量有明确语义的颜色：
  ,* 主色：标题、表头；
  ,* 成功：通过；
  ,* 警告：待检查；
  ,* 异常：失败；
  ,* 中性色：普通数据和辅助信息。
  颜色必须表达信息，不得为了“好看”随意上色。
  ## 3. 自动整理布局
  根据内容自动调整：
  ,* 列宽适配字段内容；
  ,* 行高保持紧凑；
  ,* 长文本合理换行；
  ,* 数字右对齐；
  ,* 文本左对齐；
  ,* 日期、金额和状态使用统一格式；
  ,* 冻结首行或关键列；
  ,* 启用筛选；
  ,* 重要结果优先放在左侧；
  ,* 高频查看字段靠前；
  ,* 辅助字段靠后。
  避免：
  ,* 无意义空行空列；
  ,* 大面积合并单元格；
  ,* 内容截断；
  ,* 列宽极端不一致；
  ,* 一张表横向无限延伸；
  ,* 装饰性渐变、阴影和高饱和色。
  ## 4. 按 Sheet 分层设计
  ### 原始数据表
  重点是快速浏览和筛选。
  保持高信息密度，不添加多余装饰。
  ### 结果表
  重点突出：
  ,* UID；
  ,* 分组维度；
  ,* 核心指标；
  ,* 最终结果。
  让用户打开后第一眼就看到分析结论。
  ### `data_rules`
  按：
  ,**字段 → 类型 → 约束 → 业务含义 → 示例**
  组织。
  ### `qa_result`
  让：
  ,* `PASS`
  ,* `WARN`
  ,* `FAIL`
  能够快速区分。
  异常项优先显示。
  ### `fix_log`
  按：
  ,**问题 → 原因 → 修正 → 复检结果**
  展示完整修正链路。
  ## 5. 自动视觉质检
  生成完成后检查：
  ,* 工作表风格是否统一；
  ,* 表头是否清晰；
  ,* 字体和字号是否一致；
  ,* 是否存在内容截断；
  ,* 列宽是否合理；
  ,* 数字和日期格式是否统一；
  ,* 状态颜色是否统一；
  ,* 对比度是否足够；
  ,* 是否存在无意义合并单元格；
  ,* 是否存在过度使用颜色；
  ,* 重要信息是否具有明确视觉层级；
  ,* 不同 Sheet 是否能够快速辨认用途。
  发现问题后自动调整，并重新检查。
  ## 6. 数据与展示必须分离
  视觉优化不得：
  ,* 修改原始数据值；
  ,* 修改字段名称；
  ,* 修改 Schema；
  ,* 修改公式逻辑；
  ,* 改变表间关系；
  ,* 为了排版删除记录。
  只允许调整：
  ,**样式、布局、格式、显示顺序和辅助交互。**
  ## 7. 最终验收
  交付前必须同时满足：
  ,* 数据质检通过；
  ,* Sheet 职责清晰；
  ,* 全局视觉规范统一；
  ,* 用户能快速找到关键数据；
  ,* 表格可以直接筛选、阅读和比较；
  ,* 异常项能够快速识别；
  ,* 不存在明显截断、拥挤、错位或格式混乱；
  ,* 数据、SQL、Schema 与视觉呈现完全一致。
  最终目标不是把 Spreadsheet “装修得漂亮”，而是让用户打开文件后能够：
  ,**快速看懂 → 快速定位 → 快速比较 → 快速发现异常 → 直接开始分析。**

  1. Design
    请围绕“先想最终那张表”这个思路，生成一份可直接用于 DuckDB 入门练习的
Spreadsheet 数据集。目标不是单纯造数据，而是让零基础读者通过数据直观看
懂：**业务问题 → 最终结果表 → 原始数据 → SQL 处理逻辑**

以“统计 2025 年每个客户的出入金”为例。先定义最终结果：

| uid | 入金总额 | 出金总额 | 差额 |
|-----|---------:|---------:|-----:|

一行代表一个 UID。再反推需要的原始流水：

| uid | 时间 | direction | amount |
|-----|------|-----------|-------:|

数据集必须能够支持用户逐步理解：
1. `FROM`：数据从哪里来；
2. `WHERE`：筛选 2025 年及目标业务范围；
3. `CASE WHEN`：区分入金和出金；
4. `SUM`：汇总金额；
5. `GROUP BY uid`：把一个 UID 的多笔流水压成一行；
6. 计算最终差额。

Spreadsheet 至少包含：
* `raw_transactions`：原始流水；
* `expected_result`：正确聚合结果；
* `data_rules`：字段与业务约束；
* `qa_result`：自动质检结果。

生成前先解析当前需求并固化约束，包括：
1. 字段类型；
2. UID、时间、方向、金额规则；
3. 2025 年时间范围；
4. 入金 / 出金枚举；
5. 金额有效范围；
6. 正常、异常、边界样本；
7. 原始流水与最终结果的一致性。

生成后自动质检：
1. 字段是否完整；
2. 数据类型是否正确；
3. 是否存在非法方向或金额；
4. 是否有必要的多笔流水样本；
5. 是否覆盖纯入金、纯出金、同时存在出入金、零差额等场景；
6. `expected_result` 是否能够由原始流水正确计算得到；
7. 是否存在重复、矛盾或无法解释的数据。

发现问题后自动修正并重新验证，未通过质检不得交付。最终目标：**读者打开
Spreadsheet，就能直接看懂“原始流水为什么要被处理成最终结果表”，并能据

## 1. 先定义业务边界
交易所出入金至少拆成两个独立业务域：
### 法币出入金
表示用户通过银行、支付渠道等完成的法币充值和提现。
至少包含：
* `fiat_order_id`
* `uid`
* `direction`
* `currency`
* `amount`
* `fee`
* `channel`
* `status`
* `created_at`
* `completed_at`
`direction`：
* `deposit`
* `withdrawal`
典型状态应符合实际业务过程，例如：
* `pending`
* `processing`
* `completed`
* `failed`
* `cancelled`
---
### 链上充提
表示用户通过区块链地址完成的数字资产充值和提现。
至少包含：
* `crypto_order_id`
* `uid`
* `direction`
* `asset`
* `network`
* `amount`
* `fee`
* `tx_hash`
* `address`
* `status`
* `confirmations`
* `created_at`
* `completed_at`
链上数据必须体现：
* 币种；
* 网络；
* 地址；
* TxHash；
* 区块确认；
* 网络手续费；
* 链上交易状态。
法币字段不得硬套到链上，链上专属字段也不得伪造到法币订单中。
---
## 2. 订单号必须接近真实系统数据特征
不得继续使用：
```text
ORDER001
TX001
001
```
这类明显人工编造的编号。
订单号应具备真实业务系统常见特征：
* 全局唯一；
* 长度稳定；
* 无明显连续规律；
* 可包含时间信息、业务前缀或随机字符；
* 同一业务域保持统一格式；
* 法币订单与链上订单可区分。
不要复制某家真实交易所的内部订单规则，只需生成符合真实系统特征的模拟 ID。
`tx_hash` 必须符合对应区块链的基本格式约束，不能使用普通字符串冒充。
---
## 3. 不得混算不同计价单位
禁止直接执行：
```text
1000 TRY + 500 USDT + 0.2 ETH
```
每个聚合结果必须保留对应维度。
法币至少按：
```text
uid + currency
```
聚合。
链上至少按：
```text
uid + asset + network
```
聚合。
因此最终结果应拆分为：
### `expected_fiat_result`
| uid | currency | deposit_amount | withdrawal_amount | net_amount |
| --- | -------- | -------------: | ----------------: | ---------: |
### `expected_crypto_result`
| uid | asset | network | deposit_amount | withdrawal_amount | net_amount |
| --- | ----- | ------- | -------------: | ----------------: | ---------: |
其中：
```text
net_amount = deposit_amount - withdrawal_amount
```
只统计满足业务定义的有效成功订单。
---

至少包含以下 Sheet：
### `users`
用户基础维表。
一行代表一个 UID。

### `fiat_transactions`

---
### `expected_crypto_result`
由 `crypto_transactions` 正确聚合得到的标准答案。
---
### `data_rules`

* 字段定义；
* 数据类型；
* 是否必填；
* 唯一性；

## 7. 必须覆盖的样本
不能只生成正常数据。
至少覆盖：
### 正常场景
* 单笔入金；
* 单笔出金；
* 同一 UID 多笔订单；
* 同一 UID 同时存在入金与出金；
* 多 UID；
* 多币种；
* 多链；
* 不同金额；
* 不同日期。
### 业务边界
* 只有入金；
* 只有出金；
* 入金与出金金额相同；
* 极小金额；
* 较大金额；
* 年初、年末订单；
* 创建时间与完成时间跨日期。
### 状态场景
* completed；
* pending；
* failed；
* cancelled。
聚合 SQL 必须明确哪些状态计入结果。
### 数据质量异常

* 重复订单号；

## 8. 自动质检
生成完成后自动执行以下检查。
### Schema
检查：
* 字段是否缺失；
* 类型是否正确；
* 字段名是否一致；
* 是否出现额外未知字段。
### 完整性
检查：
* 必填字段；
* 条件必填字段；
* NULL；
* 空字符串；
* 无意义默认值。
### 唯一性
检查：
* `uid`
* `fiat_order_id`
* `crypto_order_id`
以及其他要求唯一的业务标识。
### 引用完整性
检查：
```text
transactions.uid
→ users.uid
```
不得存在无来源 UID，除非该记录本身就是故意设计的异常测试 Case。
### 有效性
检查：
* direction；
* status；
* currency；
* asset；
* network；
* 金额范围；
* 时间范围；
* ID 格式；
* 地址及 TxHash 基本格式。
### 业务一致性
例如：
* `completed_at >= created_at`；
* failed / cancelled 订单不得进入成功金额统计；
* completed 链上订单应满足对应业务要求；
* 资产必须支持对应 network；
* 手续费不得出现明显不合理关系；
* 法币订单不得出现链上字段。
### 聚合一致性
重新使用原始数据计算结果，并与：
* `expected_fiat_result`
* `expected_crypto_result`
进行双向比较。
任何 UID、币种、资产、网络、金额或行数不一致，都判定失败。

## 9. 自动修正 Loop
发现问题后不得直接交付。
必须执行：
```text
检测问题
↓
定位违反的规则
↓
定位受影响记录
↓
修正数据
↓
重新运行全部相关检查
↓
检查是否产生新的问题
↓
通过后交付
```
修复一项问题后必须执行回归检查，不能只重新检查当前规则。

## 11. 最终验收标准
只有同时满足以下条件才算通过：
* 表的业务粒度明确；
* 法币与链上业务正确分离；
* 主外键关系正确；
* 订单号与业务标识不存在明显人工假数据特征；
* 时间、金额、状态符合业务逻辑；
* 不同币种和资产不存在错误混算；
* 正常、异常、边界场景均有覆盖；
* SQL 可以直接执行；
* SQL 输出与 `expected_result` 完全一致；
* 所有自动质检通过；
* 修正后未引入新的回归问题。
最终目标不是：
**“生成一批看起来像真的交易所数据。”**
而是：**生成一套业务结构合理、数据关系正确、SQL 可计算、结果可验证、异常可解释、能够直接用于 DuckDB 教学和自动化测试的数据集。**

1.2.3. Spreadsheet

  1. Loop
    1. Stage 1
      请阅读当前的Excel工作表、字段、数据类型以及表之间的关系，以确定现有的数据集是否足以支持当前的分析和测试需求。检查要点：

1. 必填字段是否齐全； 
2. 各表能否正确关联； 
3. 时间、金额、状态等业务逻辑是否完整； 
4. 是否覆盖正常、异常、边界场景； 
5. 是否存在缺失、重复、冲突或无效字段； 
6. 是否有必须补充的数据表或样品？

原则: **不要仅仅为了增加数据量而扩展，只添加当前需求真正需要的内容**。
最终直接输出：**当前数据集是否足够→缺少什么→为什么缺少→最小补充解。
    2. Stage 2
      请根据当前数据表填写。
    3. Stage 3
      在现有数据生成与质检流程后，增加一套 Spreadsheet 自动排版与视觉质检流程：
**数据验收 → 结构识别 → 视觉规范 → 自动排版 → UI 质检 → 修正 → 最终验收**
## 1. 先理解每个 Sheet 的用途
自动识别：
* 原始数据表；
* 结果表；
* 规则表；
* 质检表；
* 修正记录表。
根据用途决定布局，不允许所有 Sheet 套同一种样式。
## 2. 建立统一视觉规范
整份工作簿统一：
* 字体；
* 字号层级；
* 表头样式；
* 背景色；
* 边框；
* 对齐；
* 行高；
* 列宽；
* 数字格式；
* 日期格式；
* 状态颜色。
控制颜色数量，只保留少量有明确语义的颜色：
* 主色：标题、表头；
* 成功：通过；
* 警告：待检查；
* 异常：失败；
* 中性色：普通数据和辅助信息。
颜色必须表达信息，不得为了“好看”随意上色。
## 3. 自动整理布局
根据内容自动调整：
* 列宽适配字段内容；
* 行高保持紧凑；
* 长文本合理换行；
* 数字右对齐；
* 文本左对齐；
* 日期、金额和状态使用统一格式；
* 冻结首行或关键列；
* 启用筛选；
* 重要结果优先放在左侧；
* 高频查看字段靠前；
* 辅助字段靠后。
避免：
* 无意义空行空列；
* 大面积合并单元格；
* 内容截断；
* 列宽极端不一致；
* 一张表横向无限延伸；
* 装饰性渐变、阴影和高饱和色。
## 4. 按 Sheet 分层设计
### 原始数据表
重点是快速浏览和筛选。
保持高信息密度，不添加多余装饰。
### 结果表
重点突出：
* UID；
* 分组维度；
* 核心指标；
* 最终结果。
让用户打开后第一眼就看到分析结论。
### `data_rules`
按：
**字段 → 类型 → 约束 → 业务含义 → 示例**
组织。
### `qa_result`
让：
* `PASS`
* `WARN`
* `FAIL`
能够快速区分。
异常项优先显示。
### `fix_log`
按：
**问题 → 原因 → 修正 → 复检结果**
展示完整修正链路。
## 5. 自动视觉质检
生成完成后检查：
* 工作表风格是否统一；
* 表头是否清晰；
* 字体和字号是否一致；
* 是否存在内容截断；
* 列宽是否合理；
* 数字和日期格式是否统一；
* 状态颜色是否统一；
* 对比度是否足够；
* 是否存在无意义合并单元格；
* 是否存在过度使用颜色；
* 重要信息是否具有明确视觉层级；
* 不同 Sheet 是否能够快速辨认用途。
发现问题后自动调整，并重新检查。
## 6. 数据与展示必须分离
视觉优化不得：
* 修改原始数据值；
* 修改字段名称；
* 修改 Schema；
* 修改公式逻辑；
* 改变表间关系；
* 为了排版删除记录。
只允许调整：
**样式、布局、格式、显示顺序和辅助交互。**
## 7. 最终验收
交付前必须同时满足：
* 数据质检通过；
* Sheet 职责清晰；
* 全局视觉规范统一；
* 用户能快速找到关键数据；
* 表格可以直接筛选、阅读和比较；
* 异常项能够快速识别；
* 不存在明显截断、拥挤、错位或格式混乱；
* 数据、SQL、Schema 与视觉呈现完全一致。
最终目标不是把 Spreadsheet “装修得漂亮”，而是让用户打开文件后能够：
**快速看懂 → 快速定位 → 快速比较 → 快速发现异常 → 直接开始分析。**
