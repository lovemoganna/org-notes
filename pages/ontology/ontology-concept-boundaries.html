* 导言：本体不是术语表，而是一组可被检验的承诺
 
在知识系统里，“把字段改成更专业的名字”不等于完成了本体建模。术语表只回答“我们怎样称呼它”，本体还要回答：它是什么、它不是什么、它与什么发生关系、哪些陈述允许成立，以及系统凭什么得出结论。
 
一个能落地的本体至少同时承担四种责任：
 
- *识别责任*：给同一个对象稳定的身份，不因数据来源不同而被重复创建。
- *分类责任*：说明对象属于哪些类型，以及类型之间的包含或排斥关系。
- *关系责任*：说明对象如何连接，关系的方向、基数和适用范围是什么。
- *推理责任*：明确哪些结论可以由现有事实推出，哪些只能保持 =UNKNOWN=。
 
本文关注“模型如何被定义”。与之互补的 [[file:ontology-evidence-evolution.html][本体治理：从证据追踪到安全演化]] 关注“模型如何在真实数据和持续变化中保持可信”。
* 一、从业务问题开始，而不是从类名开始
 
建模的第一步不是画图，而是收集系统必须回答的问题。问题决定需要哪些概念，证据决定系统是否有资格回答。
 
以订单履约为例，三个看似相近的问题需要不同的模型能力：
 
1. “订单现在是什么状态？”需要状态事实和时间。
2. “订单是否可以取消？”需要取消策略、支付状态、履约阶段和优先级规则。
3. “为什么不能取消？”还需要规则命中记录与证据来源。
 
如果模型只有 =Order.status=，它可以回答第一个问题，却不能声称支持后两个问题。能力声明必须小于或等于真实实现；有限字段映射不能冒充通用推理。
 
可以把建模目标写成验收表：
 
| 能力问题       | 必要概念                        | 必要关系                 | 缺失时输出 |
|----------------+---------------------------------+--------------------------+------------|
| 查询订单状态   | Order、OrderStatus              | hasStatus                | UNKNOWN    |
| 判断是否可取消 | CancellationPolicy、Fulfillment | governedBy、hasStage     | UNKNOWN    |
| 解释判断依据   | Evidence、RuleEvaluation        | supportedBy、evaluatedBy | UNKNOWN    |
 
这张表的意义在于防止“先有类，后找用途”。没有对应问题、查询或约束的概念，应当被标记为候选，而不是直接进入核心本体。
* 二、概念边界：用判定标准区分类、属性与事件
 
一个名字应该成为类、属性还是事件，可以用三个问题判断：
 
1. 它是否拥有独立身份？
2. 它是否会在时间中变化，并且变化本身需要被记录？
3. 其他对象是否需要直接引用它？
 
例如，“客户等级”如果只是客户当前的一个枚举值，可以建成数据属性；如果等级有有效期、审批人、计算依据和历史记录，它更适合成为 =MembershipLevelAssignment= 事件或关系实体。
 
| 领域表达 | 较弱模型    | 较强模型              | 采用较强模型的条件             |
|----------+-------------+-----------------------+--------------------------------|
| 客户地址 | 字符串属性  | Address 实体          | 地址需复用、校验或追踪历史     |
| 订单状态 | 枚举属性    | StatusTransition 事件 | 需要时间线、操作者或原因       |
| 商品分类 | 文本标签    | ProductCategory 概念  | 需要层级、同义词或规则         |
| 购买关系 | customer_id | Purchase 事件         | 需要金额、时间、渠道等关系属性 |
 
边界没有唯一的“哲学正确答案”，但必须有可验证的工程理由。最小模型优先；只有当查询、约束或追溯需求出现时，才把属性提升为实体或事件。
* 三、身份：相同、相似与同名不能混为一谈
 
身份错误会直接污染整张知识图谱。两个记录字段相似，不代表它们是同一个对象；两个名称相同，也不代表它们可以合并。
 
建议把身份判断拆成三层：
 
- *确定身份*：存在受信任的稳定标识，例如政府编号、系统主键或经过验证的跨源映射。
- *候选匹配*：名称、地址、时间等特征相似，但仍需确认。
- *明确不同*：存在冲突证据，例如不同的唯一编号或互斥时间区间。
 
身份合并必须保存来源和规则。若系统只做字符串归一化，应把结果称为“规范化候选”，而不是“已确认同一实体”。删除匹配证据后，结论应退回 =UNKNOWN=，这是一项重要的反证测试。
* 四、关系设计：让谓词表达业务，而不是表达存储结构
 
关系名称应当能组成自然且明确的句子：
 
#+begin_example
  订单 governedBy 取消策略
  订单 placedBy 客户
  发货 supportedBy 承运单据
#+end_example
 
=hasData=、=relatedTo=、=containsInfo= 之类的泛化关系虽然容易创建，却几乎不能支持稳定查询。关系至少需要明确以下信息：
 
| 项目   | 示例                       | 需要回答的问题             |
|--------+----------------------------+----------------------------|
| 定义域 | placedBy 的主体是 Order    | 哪些对象可以使用此关系？   |
| 值域   | placedBy 的客体是 Customer | 关系指向什么类型？         |
| 方向   | Order → Customer           | 反向查询是否使用 inverse？ |
| 基数   | Order 恰有一个下单客户     | 零个或多个是否合法？       |
| 时间   | governedBy 在下单时生效    | 使用当前策略还是历史策略？ |
 
下面的 Turtle 片段表达了最小语义，不包含业务尚未承诺的推理能力：
 
#+begin_src turtle
  @prefix ex: <https://example.org/ontology/> .
  @prefix owl: <http://www.w3.org/2002/07/owl#> .
  @prefix rdfs: <http://www.w3.org/2000/01/rdf-schema#> .
 
  ex:Order a owl:Class .
  ex:Customer a owl:Class .
 
  ex:placedBy a owl:ObjectProperty ;
    rdfs:domain ex:Order ;
    rdfs:range ex:Customer .
#+end_src
* 五、约束与推理必须分开
 
“事实不完整”和“事实为假”不是一回事。在开放世界语义下，没有记录 =placedBy= 并不能自动证明订单没有客户；它可能只是证据尚未进入系统。数据质量约束则可以要求发布前每个订单必须具备一个客户。
 
因此，应把两类规则分开：
 
- *推理规则*：从已有事实导出新事实，例如“易腐商品是需要冷链处理的商品”。
- *质量约束*：检查当前数据是否满足使用条件，例如“已发布订单必须关联一个客户”。
 
混用两者会产生危险结果：校验失败被误读为业务事实，或者缺失数据被误读为否定结论。
 
一个查询也应主动暴露未知状态：
 
#+begin_src sparql
  SELECT ?order ?customer
  WHERE {
    ?order a ex:Order .
    OPTIONAL { ?order ex:placedBy ?customer . }
  }
#+end_src
 
应用层看到未绑定的 =?customer= 时，应返回“客户证据缺失”，而不是虚构默认客户。
* 六、从本体到数据库：映射不是等价
 
关系数据库和本体关注的重点不同。表结构强调存储、完整性和执行效率；本体强调概念、语义和跨来源解释。两者可以映射，但不能简单宣称一一等价。
 
#+begin_src sql
  CREATE TABLE orders (
    order_id      VARCHAR PRIMARY KEY,
    customer_id   VARCHAR NOT NULL,
    placed_at     TIMESTAMP NOT NULL,
    status        VARCHAR NOT NULL
  );
#+end_src
 
这张表提示了 =Order=、=Customer=、=placedBy= 和 =placedAt=，但不会自动说明：
 
- =customer_id= 的命名空间是否跨系统稳定；
- =status= 的合法迁移顺序；
- 删除客户时订单语义如何保留；
- 历史订单应采用哪个版本的策略。
 
正确做法是维护显式映射：每个本体概念对应哪些表和字段、使用什么转换规则、映射在哪个版本生效，以及失败时输出什么。
* 七、最小可验证建模循环
 
一个适合实际项目的最小循环如下：
 
1. 写出 3—7 个必须回答的能力问题。
2. 为每个问题列出真实输入、必要证据和预期输出。
3. 只创建回答这些问题所需的类、关系和属性。
4. 用正常数据、陌生数据和缺失证据各运行一次。
5. 检查模型是否会把 =UNKNOWN= 错报为确定结论。
6. 保存查询、约束、映射和测试结果，形成可复现证据链。
 
完成的判据不是“图画出来了”，而是：真实输入经过真实查询或规则执行，输出满足预先定义的验收条件，并且反证用例能够让系统正确失败。
* 八、建模检查清单
 
- [ ] 每个核心概念都有清晰的纳入与排除条件。
- [ ] 每个对象的身份来源和合并规则可追踪。
- [ ] 每条关系都有明确方向、定义域和值域。
- [ ] 时间变化没有被压扁成无法追溯的当前值。
- [ ] 推理规则与数据质量约束分开管理。
- [ ] 缺失证据会产生 =UNKNOWN=，而不是默认真或默认假。
- [ ] 每项对外能力都能指向真实实现与验证用例。
* 结语：好本体的价值是减少误解
 
本体的目标不是制造更多概念，而是让不同模块、不同数据源和不同使用者对同一事实采用一致且可检验的解释。概念边界解决“我们在谈什么”，身份解决“它是不是同一个”，关系解决“它如何连接”，约束和推理解决“系统可以得出什么”。
 
当模型进入长期运行后，还必须回答证据失效、规则冲突和版本迁移问题。下一篇 [[file:ontology-evidence-evolution.html][本体治理：从证据追踪到安全演化]] 将把这些问题组织成一个可回滚、可审计的演化闭环。

  • status 的合法迁移顺序；
  • 删除客户时订单语义如何保留；
  • 历史订单应采用哪个版本的策略。

正确做法是维护显式映射：每个本体概念对应哪些表和字段、使用什么转换规则、映射在哪个版本生效，以及失败时输出什么。

8. 七、最小可验证建模循环

一个适合实际项目的最小循环如下：

  1. 写出 3—7 个必须回答的能力问题。
  2. 为每个问题列出真实输入、必要证据和预期输出。
  3. 只创建回答这些问题所需的类、关系和属性。
  4. 用正常数据、陌生数据和缺失证据各运行一次。
  5. 检查模型是否会把 UNKNOWN 错报为确定结论。
  6. 保存查询、约束、映射和测试结果，形成可复现证据链。

完成的判据不是“图画出来了”，而是：真实输入经过真实查询或规则执行，输出满足预先定义的验收条件，并且反证用例能够让系统正确失败。

9. 八、建模检查清单

  • [ ] 每个核心概念都有清晰的纳入与排除条件。
  • [ ] 每个对象的身份来源和合并规则可追踪。
  • [ ] 每条关系都有明确方向、定义域和值域。
  • [ ] 时间变化没有被压扁成无法追溯的当前值。
  • [ ] 推理规则与数据质量约束分开管理。
  • [ ] 缺失证据会产生 UNKNOWN，而不是默认真或默认假。
  • [ ] 每项对外能力都能指向真实实现与验证用例。

10. 结语：好本体的价值是减少误解

本体的目标不是制造更多概念，而是让不同模块、不同数据源和不同使用者对同一事实采用一致且可检验的解释。概念边界解决“我们在谈什么”，身份解决“它是不是同一个”，关系解决“它如何连接”，约束和推理解决“系统可以得出什么”。

当模型进入长期运行后，还必须回答证据失效、规则冲突和版本迁移问题。下一篇 本体治理：从证据追踪到安全演化 将把这些问题组织成一个可回滚、可审计的演化闭环。
