* 导言：模型上线之后，治理才真正开始
 
本体第一次发布时通常整洁、连贯、充满确定性；真实数据进入后，问题才会出现：同一对象来自多个系统，规则在不同时间生效，字段含义发生漂移，证据互相冲突，旧查询仍依赖已经废弃的关系。
 
因此，生产级本体不能只保存“当前结论”，还要保存结论从哪里来、由什么规则产生、适用于哪个时间和版本，以及在证据消失时是否能够撤回。
 
如果还没有确定概念边界、身份规则和关系语义，应先阅读 本体论建模：从概念边界到可计算语义。本文假定基础模型已经存在，重点讨论它怎样持续保持可信。
* 一、证据优先：结论必须能够回到来源
 
一条可治理的知识陈述至少包含五个维度：
 
| 维度     | 要回答的问题           | 示例              |
|----------+------------------------+-------------------|
| 主张     | 系统认为发生了什么？   | 订单 O-17 已发货  |
| 来源     | 谁或什么系统提供？     | WMS 事件 E-88     |
| 时间     | 事实何时成立或被观察？ | 2026-08-15 10:30  |
| 方法     | 如何得到该结论？       | 事件映射规则 R-12 |
| 置信状态 | 已确认、候选还是未知？ | confirmed         |
 
如果系统只保存 =shipped=true=，用户无法判断它来自承运商回执、仓库扫描还是人工修改，也无法在来源被撤销后更新结论。
 
证据对象不必一开始就设计得复杂，但至少应保存稳定标识、来源类型、原始引用、观察时间和内容摘要。敏感原文可以留在受控存储中，本体只保留不可混淆的引用。
* 二、把“观察”“解释”和“决定”分层
 
治理中最常见的错误，是把原始数据直接写成最终业务结论。更安全的结构分为三层：
 
1. *观察层*：记录外部系统实际给出的值，不替来源修正含义。
2. *解释层*：使用版本化映射和规则，把观察转换为领域事实。
3. *决定层*：在领域事实之上执行策略，产生允许、拒绝或待确认等结果。
 
例如，仓库事件 =PACKED= 是观察；“订单已进入履约阶段”是解释；“取消请求需要人工审批”是决定。三层分开后，规则改变时可以重算决定，而无需篡改原始事件。
 
#+begin_example
  Evidence E-88
    observedCode = "PACKED"
    sourceSystem = "WMS"
 
  Interpretation I-31
    derives fulfillmentStage = "packing"
    evaluatedBy mapping-v3
    supportedBy E-88
 
  Decision D-09
    outcome = "manual_review"
    evaluatedBy cancellation-policy-v5
    supportedBy I-31
#+end_example
* 三、冲突不是异常噪声，而是一等数据
 
两个可靠来源可能给出不同结论。仓库系统显示“已打包”，支付系统显示“已退款”，客服系统仍显示“等待取消”。如果治理层简单采用最后写入值，冲突会消失在数据表里，却继续存在于业务中。
 
冲突处理应包含以下步骤：
 
1. 保留所有原始主张，不覆盖来源记录。
2. 判断它们是否真的互斥，还是适用于不同时间或对象。
3. 运行明确的优先级或协调规则。
4. 保存规则命中过程和最终状态。
5. 如果规则无法裁决，输出 =UNKNOWN= 或 =REQUIRES_REVIEW=。
 
不要把优先级藏在应用代码的 =if/else= 中而不留记录。规则技术可以很简单，关键是能力声明真实、执行结果可追踪。
 
下面的伪 Python 展示一个保守裁决器：
 
#+begin_src python
  def resolve_shipping_status(claims):
      confirmed = [c for c in claims if c.evidence_verified]
      if not confirmed:
          return {"status": "UNKNOWN", "reason": "NO_VERIFIED_EVIDENCE"}
 
      values = {c.value for c in confirmed}
      if len(values) > 1:
          return {
              "status": "REQUIRES_REVIEW",
              "reason": "CONFLICTING_VERIFIED_EVIDENCE",
              "evidence_ids": [c.evidence_id for c in confirmed],
          }
 
      return {"status": confirmed[0].value, "reason": "CONSISTENT_EVIDENCE"}
#+end_src
 
它没有假装自己能够解决所有冲突，而是把能力边界显式暴露给调用方。
* 四、时间是本体治理的核心维度
 
“当前事实”会随时间改变，规则也会改变。至少要区分三种时间：
 
- *有效时间*：事实在现实世界中何时成立。
- *记录时间*：系统何时知道这件事。
- *规则时间*：解释或策略版本何时生效。
 
例如，昨天发生的发货事件今天才同步进入系统。若只保存一个 =updated_at=，系统无法重建昨天晚上的真实认知状态，也无法解释为什么当时做出了某个决定。
 
一个适合审计的查询应指定时间边界：
 
#+begin_src sql
  SELECT order_id, interpreted_stage, evidence_id, rule_version
  FROM order_stage_history
  WHERE order_id = 'O-17'
    AND valid_from <= TIMESTAMP '2026-08-15 10:00:00'
    AND (valid_to IS NULL OR valid_to > TIMESTAMP '2026-08-15 10:00:00')
    AND recorded_at <= TIMESTAMP '2026-08-15 10:05:00';
#+end_src
 
这个查询回答的是“系统在 10:05 所掌握的信息中，10:00 有效的履约阶段是什么”，比笼统的“订单状态是什么”更精确。
* 五、本体版本：变更类型决定迁移策略
 
不是所有模型变更都同样危险。可以按兼容性分为四类：
 
| 变更 | 示例                 | 风险 | 最小处理             |
|------+----------------------+------+----------------------|
| 新增 | 增加 Evidence 类     | 低   | 新查询按需采用       |
| 扩展 | 为关系增加可选属性   | 中   | 检查旧消费者         |
| 收紧 | 基数从可选变为必填   | 高   | 先审计历史数据       |
| 破坏 | 拆分类、改变关系含义 | 很高 | 双写、迁移、回滚方案 |
 
版本号本身不能保证兼容性。每次变更都应提供机器可读或至少结构化的差异：新增什么、弃用什么、哪些查询受影响、数据怎样迁移、失败怎样回滚。
 
弃用应经历明确周期：
 
1. 标记旧概念为 deprecated，但继续读取。
2. 新旧结构双写或提供派生映射。
3. 比较两种查询结果，定位不一致。
4. 迁移消费者并观察一段时间。
5. 只有在依赖归零后才停止写入旧结构。
 
直接重命名关系而不保留映射，会让历史数据和下游查询在没有明显错误的情况下悄悄失联。
* 六、质量门禁：发布前验证模型、数据和能力
 
本体发布不能只检查文件是否能解析。至少需要三类门禁：
** 1. 结构门禁
 
- WIKI_ID、IRI 或内部标识是否唯一；
- 关系的定义域和值域是否引用有效概念；
- 是否出现循环依赖、孤立核心类或意外自关系；
- 弃用概念是否仍被新增模型引用。
** 2. 数据门禁
 
- 必需证据是否存在；
- 身份合并是否存在互斥唯一标识；
- 时间区间是否重叠；
- 枚举值、基数和引用完整性是否满足约束。
** 3. 能力门禁
 
- 每个对外能力是否有真实查询或规则实现；
- 正常、陌生、缺失和冲突输入是否都执行过；
- 删除证据后，结论是否撤回或变成 =UNKNOWN=；
- 旧版本消费者是否仍能得到约定结果。
 
只有三类门禁都通过，才能说“该版本可发布”。解析成功只说明语法正确，不说明系统可信。
* 七、主动反证：寻找能够推翻模型的输入
 
治理测试的目标不是证明当前模型永远正确，而是确认它能在错误条件下诚实失败。
 
推荐的反证集合：
 
- *改输入*：改变关键证据，输出必须相应变化。
- *删证据*：删除唯一依据，结论必须退回 =UNKNOWN=。
- *造冲突*：输入两个互斥且同等可信的主张，系统必须暴露冲突。
- *换陌生数据*：使用训练或设计阶段未出现的标识和类别，检查是否错误套用默认映射。
- *回放旧版本*：用历史快照运行新规则，验证迁移是否改变既有结论。
- *制造中断*：在迁移中途失败，验证旧模型、索引和输出是否完整恢复。
 
反证结果应与正常结果一样进入证据链，而不是只在开发者终端里短暂出现。
* 八、可回滚发布流程
 
一个最小而可靠的本体发布流程可以写成：
 
#+begin_example
  冻结验收条件
    → 快照当前模型、数据与查询结果
    → 在隔离环境执行迁移
    → 运行结构、数据、能力门禁
    → 运行反证集合
    → 比较新旧关键查询
    → 原子切换版本
    → 观察并保留回滚窗口
#+end_example
 
回滚不能只恢复本体文件。如果迁移已经改写数据、索引或缓存，必须把这些状态纳入同一个事务边界。否则“代码回滚成功”仍可能留下混合版本系统。
 
每次发布至少保存：
 
- 模型版本与内容哈希；
- 数据迁移版本；
- 规则与映射版本；
- 验收查询及其输出摘要；
- 失败报告和回滚结果；
- 发布者、时间和运行环境。
* 九、治理看板应该呈现什么
 
治理看板不应只显示节点数和边数。数量增加可能意味着知识更完整，也可能意味着重复实体和无意义关系更多。
 
更有用的指标包括：
 
| 指标           | 说明                   | 反映的问题   |
|----------------+------------------------+--------------|
| 无证据主张率   | 没有关联来源的结论占比 | 可解释性风险 |
| 冲突未决数     | 尚未裁决的互斥主张     | 业务阻塞     |
| UNKNOWN 比例   | 证据不足的查询占比     | 数据覆盖不足 |
| 弃用依赖数     | 仍引用旧概念的消费者   | 迁移风险     |
| 身份合并撤销数 | 被证明错误的实体合并   | 匹配规则质量 |
| 回滚演练成功率 | 可完整恢复的发布次数   | 运营韧性     |
 
这些指标必须能回到具体对象和证据，不能只保留聚合数字。
* 十、生产治理检查清单
 
- [ ] 每个结论可以追溯到来源、时间、方法和版本。
- [ ] 原始观察、领域解释和业务决定彼此分层。
- [ ] 冲突会被保留和报告，不会被最后写入静默覆盖。
- [ ] 有效时间、记录时间和规则生效时间可区分。
- [ ] 破坏性变更具备双写、迁移和回滚路径。
- [ ] 结构、数据、能力三类门禁全部实际运行。
- [ ] 缺失、冲突、陌生数据和中断条件均有反证。
- [ ] 发布记录包含模型、数据、规则和输出证据。
* 结语：可信来自可撤回，而不是永远确定
 
成熟的本体系统不会假装所有事实都确定。它知道结论依赖什么，也知道何时应该撤回；它允许模型演化，但要求变化可比较、可迁移、可回滚。
 
概念边界和关系语义提供稳定的语言，证据与版本治理提供长期可信度。两者结合后，本体才不只是一次性的知识图，而是能够持续接受新事实、暴露不确定性并安全变化的工程系统。基础建模方法见 本体论建模：从概念边界到可计算语义。

def resolve_shipping_status(claims):

            "status": "REQUIRES_REVIEW",

  AND (valid_to IS NULL OR valid_to > TIMESTAMP '2026-08-15 10:00:00')
  AND recorded_at <= TIMESTAMP '2026-08-15 10:05:00';

这个查询回答的是“系统在 10:05 所掌握的信息中，10:00 有效的履约阶段是什么”，比笼统的“订单状态是什么”更精确。

6. 五、本体版本：变更类型决定迁移策略

不是所有模型变更都同样危险。可以按兼容性分为四类：

变更 示例 风险 最小处理
新增 增加 Evidence 类 低 新查询按需采用
扩展 为关系增加可选属性 中 检查旧消费者
收紧 基数从可选变为必填 高 先审计历史数据
破坏 拆分类、改变关系含义 很高 双写、迁移、回滚方案

版本号本身不能保证兼容性。每次变更都应提供机器可读或至少结构化的差异：新增什么、弃用什么、哪些查询受影响、数据怎样迁移、失败怎样回滚。

弃用应经历明确周期：

  1. 标记旧概念为 deprecated，但继续读取。
  2. 新旧结构双写或提供派生映射。
  3. 比较两种查询结果，定位不一致。
  4. 迁移消费者并观察一段时间。
  5. 只有在依赖归零后才停止写入旧结构。

直接重命名关系而不保留映射，会让历史数据和下游查询在没有明显错误的情况下悄悄失联。

7. 六、质量门禁：发布前验证模型、数据和能力

本体发布不能只检查文件是否能解析。至少需要三类门禁：

7.1. 1. 结构门禁

  • WIKI_ID、IRI 或内部标识是否唯一；
  • 关系的定义域和值域是否引用有效概念；
  • 是否出现循环依赖、孤立核心类或意外自关系；
  • 弃用概念是否仍被新增模型引用。

7.2. 2. 数据门禁

  • 必需证据是否存在；
  • 身份合并是否存在互斥唯一标识；
  • 时间区间是否重叠；
  • 枚举值、基数和引用完整性是否满足约束。

7.3. 3. 能力门禁

  • 每个对外能力是否有真实查询或规则实现；
  • 正常、陌生、缺失和冲突输入是否都执行过；
  • 删除证据后，结论是否撤回或变成 UNKNOWN；
  • 旧版本消费者是否仍能得到约定结果。

只有三类门禁都通过，才能说“该版本可发布”。解析成功只说明语法正确，不说明系统可信。

8. 七、主动反证：寻找能够推翻模型的输入

治理测试的目标不是证明当前模型永远正确，而是确认它能在错误条件下诚实失败。

推荐的反证集合：

  • 改输入：改变关键证据，输出必须相应变化。
  • 删证据：删除唯一依据，结论必须退回 UNKNOWN。
  • 造冲突：输入两个互斥且同等可信的主张，系统必须暴露冲突。
  • 换陌生数据：使用训练或设计阶段未出现的标识和类别，检查是否错误套用默认映射。
  • 回放旧版本：用历史快照运行新规则，验证迁移是否改变既有结论。
  • 制造中断：在迁移中途失败，验证旧模型、索引和输出是否完整恢复。

反证结果应与正常结果一样进入证据链，而不是只在开发者终端里短暂出现。

9. 八、可回滚发布流程

一个最小而可靠的本体发布流程可以写成： 


冻结验收条件
  → 快照当前模型、数据与查询结果
  → 在隔离环境执行迁移
  → 运行结构、数据、能力门禁
  → 运行反证集合
  → 比较新旧关键查询
  → 原子切换版本
  → 观察并保留回滚窗口

回滚不能只恢复本体文件。如果迁移已经改写数据、索引或缓存，必须把这些状态纳入同一个事务边界。否则“代码回滚成功”仍可能留下混合版本系统。

每次发布至少保存：

  • 模型版本与内容哈希；
  • 数据迁移版本；
  • 规则与映射版本；
  • 验收查询及其输出摘要；
  • 失败报告和回滚结果；
  • 发布者、时间和运行环境。

10. 九、治理看板应该呈现什么

治理看板不应只显示节点数和边数。数量增加可能意味着知识更完整，也可能意味着重复实体和无意义关系更多。

更有用的指标包括：

指标 说明 反映的问题
无证据主张率 没有关联来源的结论占比 可解释性风险
冲突未决数 尚未裁决的互斥主张 业务阻塞
UNKNOWN 比例 证据不足的查询占比 数据覆盖不足
弃用依赖数 仍引用旧概念的消费者 迁移风险
身份合并撤销数 被证明错误的实体合并 匹配规则质量
回滚演练成功率 可完整恢复的发布次数 运营韧性

这些指标必须能回到具体对象和证据，不能只保留聚合数字。

11. 十、生产治理检查清单

  • [ ] 每个结论可以追溯到来源、时间、方法和版本。
  • [ ] 原始观察、领域解释和业务决定彼此分层。
  • [ ] 冲突会被保留和报告，不会被最后写入静默覆盖。
  • [ ] 有效时间、记录时间和规则生效时间可区分。
  • [ ] 破坏性变更具备双写、迁移和回滚路径。
  • [ ] 结构、数据、能力三类门禁全部实际运行。
  • [ ] 缺失、冲突、陌生数据和中断条件均有反证。
  • [ ] 发布记录包含模型、数据、规则和输出证据。

12. 结语：可信来自可撤回，而不是永远确定

成熟的本体系统不会假装所有事实都确定。它知道结论依赖什么，也知道何时应该撤回；它允许模型演化，但要求变化可比较、可迁移、可回滚。

概念边界和关系语义提供稳定的语言，证据与版本治理提供长期可信度。两者结合后，本体才不只是一次性的知识图，而是能够持续接受新事实、暴露不确定性并安全变化的工程系统。基础建模方法见 本体论建模：从概念边界到可计算语义。
