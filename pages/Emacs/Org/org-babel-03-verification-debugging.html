* 1. #+call 与 ob-async：先排除 Advice API drift
 
如果 =price-total= Block 本身能执行，但这一行报 =wrong-number-of-arguments=，并且回溯进入 =ob-async-org-babel-execute-src-block=，不要改 Python。这个错误发生在 Emacs Lisp Advice 层：当前 Org 会把 =executor-type= 继续传给 =org-babel-execute-src-block=，而旧版或本地修改版 =ob-async= 仍只接受 =orig-fun / arg / info / params=。
 
先看当前内存，而不是看磁盘上的配置文件：
 
#+begin_example
  M-: (help-function-arglist #'org-babel-execute-src-block t)
  M-: (help-function-arglist #'ob-async-org-babel-execute-src-block t)
#+end_example
 
典型冲突：
 
#+begin_example
  Org:
  (&optional arg info params executor-type)
 
  legacy ob-async advice:
  (&optional orig-fun arg info params)
#+end_example
 
先验证是不是 =ob-async=。临时移除旧 Advice，再执行同一条 =#+call:=：
 
#+begin_example
  (advice-remove 'org-babel-execute-src-block
                 #'ob-async-org-babel-execute-src-block)
#+end_example
 
如果此时返回 =55.0=，=price-total= 和 Org Babel 都正常，故障就是 Advice API drift。
 
注意：仅把一个兼容文件放到磁盘上没有任何作用。必须让当前 Emacs 真正加载它，而且加载顺序必须晚于你的 =ob-async= 定制。配套 =ob-async-org-babel-compat-v2.el= 会做三件事：先捕获旧实现；再从当前 =org-babel-execute-src-block= Advice 链中移除旧 =ob-async=；最后挂上能接收 =executor-type= 的 wrapper。安装后立即自检，旧 Advice 仍存在就直接报错，不允许假装修复成功。
 
在配置中放到 =ob-async= 配置之后：
 
#+begin_example
  (load-file "[local-path-redacted]")
#+end_example
 
加载后先执行：
 
#+begin_example
  M-: (my/ob-async-compat-status)
#+end_example
 
必须看到：
 
#+begin_example
  :legacy-advice-present nil
  :compat-advice-present t
#+end_example
 
然后再执行：
 
#+begin_example
  ,#+call: price-total(subtotal=50, tax_rate=0.2, discount=5)
#+end_example
 
预期：
 
#+begin_example
  55.0
#+end_example
 
兼容层只绕开带 =executor-type= 的 CALL 类执行；普通 Source Block 仍委托给你已经加载的旧 =ob-async=，所以原有 =:async= 行为不需要整体删除。若你直接维护自己的 V6 =ob-async= 源码，则更根本的修复仍然是：函数签名加入 =executor-type=，并让所有同步 fallback 原样向下转发该参数。
 
关系：复现入口见 [[file:org-babel-01-execution-foundations.org::*4. 参数传递：把变化从代码中抽出来][01｜参数传递中的 price-total]]；修复后回到原调用重新验证。
* 2. Expanded Source First：调试时先看真实执行代码
 
涉及 =:var=、=#+call:=、Noweb、Session、Tangle 或 Header Args 继承时，先执行 =C-c C-v v=，再诊断 Runtime。
 
#+begin_example
  Block + Header Args + Variable + Noweb + Call
  → Expanded Source
  → Runtime
  → Result
  → Contract
#+end_example
 
例如 =noweb-price= 报 =tax_rate is not defined=：先看 Expanded Source 是否存在变量注入，再区分 HEADER / VARIABLE / NOWEB / RUNTIME。不要直接重写代码。
 
示例：回到 [[file:org-babel-02-composition-engineering.org::*2. Noweb：组合源码，而不是复制源码][02｜Noweb]] 对照原始片段、展开源码和最终 Runtime。
* 3. 错误分类与最小修复
 
分类：
 
#+begin_example
  ORG / BABEL / HEADER / VARIABLE / DEPENDENCY / RUNTIME / VERSION / PATH
  DATA / CODE / RESULT / CALL / NOWEB / TANGLE / FILE / CONTRACT / ENVIRONMENT
#+end_example
 
修复顺序：
 
#+begin_example
  参数 > 环境 > Header > 语法 > 局部逻辑 > 依赖 > 结构 > 整体重构
#+end_example
 
例：=org-babel-build/generated_report.py= 不存在。
 
#+begin_example
  文件不存在
  → Tangle 未执行或目标路径错误
  → TANGLE / FILE
  → 检查 :tangle 与工作目录
#+end_example
 
不要因此重写报告函数。
 
示例：Tangle 的 WRITE 边界与生成文件修复路径见 [[file:org-babel-02-composition-engineering.org::*5. Tangle：Org 才是 Source of Truth][02｜Tangle]]。
* 4. 自动化执行：从笔记升级成可回归工程
 
交互执行适合学习；稳定后应支持批处理。
 
原 V10 的配套 verifier 仍可作为单文件来源的 E2E 回归基线。先跑 clean-room：
 
#+begin_example
  emacs --batch -Q -l verify-org-babel-v10.el
#+end_example
 
=-Q= 会跳过用户 init、site file 和大部分本地定制，因此它证明的是“教程在干净 Emacs/Org 基线中自洽”，不是“你的日常 Emacs 配置没有兼容问题”。GNU Emacs 同时规定 =--batch= 本身就隐含 =-q=，默认不会加载用户 init。
 
再跑“实际配置 batch”模式。因为 batch 不会自动读 init，需要显式 =-l=：
 
#+begin_example
  ORG_BABEL_VERIFY_MODE=actual emacs --batch -l /path/to/init.el -l verify-org-babel-v10.el
#+end_example
 
Windows PowerShell 可先设置 =$env:ORG_BABEL_VERIFY_MODE='actual'=，再把 =/path/to/init.el= 换成自己的 Emacs 配置入口。actual 模式不替你加载 Python/Shell Babel backend，也不重写 Python command；缺什么就直接 FAIL，用来发现实际配置漂移。它仍然是 batch 进程，不等同于交互 Emacs；Session、终端和 UI 相关差异最终还应在日常 Emacs 中跑一次对应 Block。
 
Verifier 会把教程复制到临时目录，避免 Tangle 覆盖工作区文件；最低矩阵、教程实际使用能力、负向 Contract、Source Block 执行覆盖和断言覆盖必须同时闭合，才打印 =LITERATE_PROGRAMMING_PASS=。任一断言失败，batch 非零退出。
 
模块化后的三份 Org 已改变文件边界，因此旧 =verify-org-babel-v10.el= 的 PASS 只能证明原 V10 单文件基线没有退化，不能直接等价为“三模块 E2E PASS”。三模块需要让 verifier 显式读取 01 / 02 / 03 三个文件后再做同一矩阵；在此之前，只把本次拆分的结构、链接、命名对象和代码块完整性回归记为通过。
** 4.1 导出前检查 Org 语法，而不是放宽 broken-links
 
Org 会把双中括号解析成链接。教程正文如果只是想描述 Python 的嵌套列表，不要直接写成双中括号形式；否则里面的文字可能被识别为 fuzzy internal link。
 
导出前先运行：
 
#+begin_example
  M-x org-lint
#+end_example
 
然后再做一次严格导出。不要把 =org-export-with-broken-links= 改成 =mark= 或 =t= 来掩盖问题；那只会让导出继续，不会修复错误链接。Native E2E 也必须在 =org-export-with-broken-links=nil=、=:eval= 关闭的条件下完成一次 HTML export smoke test。

* 7. Verification
 
本文件的验证状态不应手写成 PASS。以配套 E2E 执行结果为准。
 
状态定义：
 
- PASS：对应能力真实执行并符合 Contract；
- FAIL：真实执行完成，但输出/断言错误；
- BLOCKED：缺少 Runtime、Backend、网络或环境能力，无法完成真实执行；
- N/A：当前案例明确不使用该能力。

** 8.3 已有执行证据支持的 Skill Patch

** 8.4 待原生执行
 
- Cache + Noweb：Org 文档说明 cache 变化检测不会展开 Noweb；配套 verifier 已保留修改 fragment 后重跑的 Risk Probe。
- Environment Parity：=-Q= 只能证明 clean-room 基线；actual-config batch 还要显式加载用户 init，而且 batch 仍不完全等价于交互 Emacs。配套 verifier 已分成 clean / actual 两种模式，但当前环境无 Emacs，尚不能给这个机制补丁判 =PATCH_ACCEPTED=。
 
两项均保持 =PENDING_NATIVE_EXECUTION=。
** 8.5 当前结论
 
V10 Runtime 等价验证与静态审计继续覆盖跨平台 Shell、#+call 环境兼容和既有回归；具体计数以配套 verifier 输出为准。Babel-native E2E 仍因无 Emacs 阻塞。已确认应继续保留的补丁方向包括 Degraded Verification、E2E Coverage Closure、Syntax-Aware Dependency、Global Compression Closure，并新增 Runtime Specificity / Extension Compatibility；Environment Parity 与 Cache + Noweb 仍等待原生执行证据。

2. 1. #+call 与 ob-async：先排除 Advice API drift

如果 price-total Block 本身能执行，但这一行报 wrong-number-of-arguments，并且回溯进入 ob-async-org-babel-execute-src-block，不要改 Python。这个错误发生在 Emacs Lisp Advice 层：当前 Org 会把 executor-type 继续传给 org-babel-execute-src-block，而旧版或本地修改版 ob-async 仍只接受 orig-fun / arg / info / params。

先看当前内存，而不是看磁盘上的配置文件： 


M-: (help-function-arglist #'org-babel-execute-src-block t)
M-: (help-function-arglist #'ob-async-org-babel-execute-src-block t)

典型冲突： 


Org:
(&optional arg info params executor-type)

legacy ob-async advice:
(&optional orig-fun arg info params)

先验证是不是 ob-async。临时移除旧 Advice，再执行同一条 #+call:： 


(advice-remove 'org-babel-execute-src-block
               #'ob-async-org-babel-execute-src-block)

如果此时返回 55.0，price-total 和 Org Babel 都正常，故障就是 Advice API drift。

注意：仅把一个兼容文件放到磁盘上没有任何作用。必须让当前 Emacs 真正加载它，而且加载顺序必须晚于你的 ob-async 定制。配套 ob-async-org-babel-compat-v2.el 会做三件事：先捕获旧实现；再从当前 org-babel-execute-src-block Advice 链中移除旧 ob-async；最后挂上能接收 executor-type 的 wrapper。安装后立即自检，旧 Advice 仍存在就直接报错，不允许假装修复成功。

在配置中放到 ob-async 配置之后： 


(load-file "[local-path-redacted]")

加载后先执行： 


M-: (my/ob-async-compat-status)

必须看到： 


:legacy-advice-present nil
:compat-advice-present t

然后再执行： 


#+call: price-total(subtotal=50, tax_rate=0.2, discount=5)

预期： 


55.0

兼容层只绕开带 executor-type 的 CALL 类执行；普通 Source Block 仍委托给你已经加载的旧 ob-async，所以原有 :async 行为不需要整体删除。若你直接维护自己的 V6 ob-async 源码，则更根本的修复仍然是：函数签名加入 executor-type，并让所有同步 fallback 原样向下转发该参数。

关系：复现入口见 01｜参数传递中的 price-total；修复后回到原调用重新验证。

3. 2. Expanded Source First：调试时先看真实执行代码

涉及 :var、#+call:、Noweb、Session、Tangle 或 Header Args 继承时，先执行 C-c C-v v，再诊断 Runtime。 


Block + Header Args + Variable + Noweb + Call
→ Expanded Source
→ Runtime
→ Result
→ Contract

例如 noweb-price 报 tax_rate is not defined：先看 Expanded Source 是否存在变量注入，再区分 HEADER / VARIABLE / NOWEB / RUNTIME。不要直接重写代码。

示例：回到 02｜Noweb 对照原始片段、展开源码和最终 Runtime。

4. 3. 错误分类与最小修复

分类： 


ORG / BABEL / HEADER / VARIABLE / DEPENDENCY / RUNTIME / VERSION / PATH
DATA / CODE / RESULT / CALL / NOWEB / TANGLE / FILE / CONTRACT / ENVIRONMENT

修复顺序： 


参数 > 环境 > Header > 语法 > 局部逻辑 > 依赖 > 结构 > 整体重构

例：org-babel-build/generated_report.py 不存在。 


文件不存在
→ Tangle 未执行或目标路径错误
→ TANGLE / FILE
→ 检查 :tangle 与工作目录

不要因此重写报告函数。

示例：Tangle 的 WRITE 边界与生成文件修复路径见 02｜Tangle。

5. 4. 自动化执行：从笔记升级成可回归工程

交互执行适合学习；稳定后应支持批处理。

原 V10 的配套 verifier 仍可作为单文件来源的 E2E 回归基线。先跑 clean-room： 


emacs --batch -Q -l verify-org-babel-v10.el

-Q 会跳过用户 init、site file 和大部分本地定制，因此它证明的是“教程在干净 Emacs/Org 基线中自洽”，不是“你的日常 Emacs 配置没有兼容问题”。GNU Emacs 同时规定 --batch 本身就隐含 -q，默认不会加载用户 init。

再跑“实际配置 batch”模式。因为 batch 不会自动读 init，需要显式 -l： 


ORG_BABEL_VERIFY_MODE=actual emacs --batch -l /path/to/init.el -l verify-org-babel-v10.el

Windows PowerShell 可先设置 $env:ORG_BABEL_VERIFY_MODE'actual'，再把 =/path/to/init.el 换成自己的 Emacs 配置入口。actual 模式不替你加载 Python/Shell Babel backend，也不重写 Python command；缺什么就直接 FAIL，用来发现实际配置漂移。它仍然是 batch 进程，不等同于交互 Emacs；Session、终端和 UI 相关差异最终还应在日常 Emacs 中跑一次对应 Block。

Verifier 会把教程复制到临时目录，避免 Tangle 覆盖工作区文件；最低矩阵、教程实际使用能力、负向 Contract、Source Block 执行覆盖和断言覆盖必须同时闭合，才打印 LITERATE_PROGRAMMING_PASS。任一断言失败，batch 非零退出。

模块化后的三份 Org 已改变文件边界，因此旧 verify-org-babel-v10.el 的 PASS 只能证明原 V10 单文件基线没有退化，不能直接等价为“三模块 E2E PASS”。三模块需要让 verifier 显式读取 01 / 02 / 03 三个文件后再做同一矩阵；在此之前，只把本次拆分的结构、链接、命名对象和代码块完整性回归记为通过。

5.1. 4.1 导出前检查 Org 语法，而不是放宽 broken-links

Org 会把双中括号解析成链接。教程正文如果只是想描述 Python 的嵌套列表，不要直接写成双中括号形式；否则里面的文字可能被识别为 fuzzy internal link。

导出前先运行： 


M-x org-lint

然后再做一次严格导出。不要把 org-export-with-broken-links 改成 mark 或 t 来掩盖问题；那只会让导出继续，不会修复错误链接。Native E2E 也必须在 org-export-with-broken-links=nil、:eval 关闭的条件下完成一次 HTML export smoke test。

8. 7. Verification

本文件的验证状态不应手写成 PASS。以配套 E2E 执行结果为准。

状态定义：

  • PASS：对应能力真实执行并符合 Contract；
  • FAIL：真实执行完成，但输出/断言错误；
  • BLOCKED：缺少 Runtime、Backend、网络或环境能力，无法完成真实执行；
  • N/A：当前案例明确不使用该能力。
