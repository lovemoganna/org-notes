* 这次究竟测试什么
只测试两个*纯文本提示*能否衔接真实工作：A 将用户的口头要求整理成事实与问题；B 直接使用 A 的原始结果，写成可交给开发者的最小需求。

不是 Python、API、软件开发或执行器性能测试。此处的 Org 源块只用来存放、命名和复用原样提示文本；不要求它们包含程序。首轮通过人工复制调用模型，保留实际回复。以后确有需要时，再为纯文本提示接入模型执行后端。

[[https://lovemoganna.github.io/org-notes/pages/collected/programming/prompt-chain-org/0fa57c1e-9f62-4b7a-a760-8933e856bf17.html][提示链 001 历史文章]] 独立保留；本篇沿用原文章身份与网址。

* 本次真实输入
#+name: task-input
#+begin_src text :eval never :exports code
透视结构放置区现在占据的空间很大，而且随着放置的维度和度量越多，高度就会越高，此外左边的侧边栏有一部分还空着，想办法合理调整下布局。
#+end_src

* 两个独立的纯文本提示
** Prompt A：先把需求看明白
目的：提取用户确实说过的事实，不急着提出解决方案。

#+name: prompt-a
#+begin_src text :eval never :exports code
阅读下方用户的原始需求，只输出四项：
1. 已确认的界面现象。
2. 用户真正希望实现的效果。
3. 原文明确提出的限制；没有就写“未明确”。
4. 必须到真实产品里检查的信息。
每项简短、具体。不得虚构界面尺寸、代码结构或已执行的修改；不要设计解决方案。
#+end_src

** Prompt B：把 A 的结果变成可执行任务
目的：消费 A 的实际输出，生成工程师能直接开始检查和实施的任务单。

#+name: prompt-b
#+begin_src text :eval never :exports code
阅读提供的原始需求与问题摘要，写出一份最小开发任务单：
- 目标与问题
- 需要检查的界面区域
- 一项优先尝试的低风险布局调整
- 可以在真实界面上检查的验收条件
- 尚需现场核实的事实
直接给出可使用的任务单，不要再次分析提示词。没有看过源码就不要声称已经实施；把建议与事实分开。
#+end_src

* 怎样完成一次纯文本实验
1. 将 =prompt-a= 的文字与 =task-input= 一起发送给 AI，保存 A 的*完整原始回复*。
2. 在另一轮对话，将 =prompt-b= 的文字、同一份 =task-input= 和 A 的*完整原始回复*一起发送给 AI；保存 B 的*完整原始回复*。
3. 在下面按次记录模型、时间、实际输入、A/B 输出和有无中断，随后提交此 Org 文件，由现有笔记发布机制更新*同一篇文章*。

此处的命名 =text= 源块仅存放纯文本，不是可执行的模型调用。标准 Org-Babel 没有通用的“执行文本提示即调用大模型”后端；因此本轮不能把按 =C-c C-c= 运行文本块说成已测试成功。Org 负责组织实验，AI 由人工调用；以后才考虑是否安装专门的 Babel 后端。
