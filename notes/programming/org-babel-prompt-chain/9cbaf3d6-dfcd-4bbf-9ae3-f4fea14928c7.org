* 实验 002：只测试纯文本提示
本实验不学习编程、不生成代码，也不开发 Python/API 调用器。目标是把两段纯文本指令放进 Org-Babel，让 A 的实际回复直接成为 B 的上下文，结果写回同一份 Org 文件。

使用现成的 [[https://github.com/jwiegley/ob-gptel][ob-gptel]]（Org-Babel 的 gptel 后端）；提示词本身保持纯文本。[[https://lovemoganna.github.io/org-notes/pages/collected/programming/prompt-chain-org/0fa57c1e-9f62-4b7a-a760-8933e856bf17.html][提示链 001 历史文章]] 不做修改。

* 一、真实任务
原始问题：透视结构放置区占据很大空间；维度和度量越多，放置区高度越高；左侧边栏还有空余位置。需要合理调整布局。

交付物：一份可以直接交给开发者的简洁布局修改任务单。本轮只验证文本输入和输出，不冒充已经修改过 PivotStudio。

* 二、Prompt A：识别用户真正的问题
只负责提取事实和约束，不设计方案。

#+name: prompt-a
#+begin_src gptel :eval never-export :exports both
阅读下面这段真实 UI 需求，只输出四项：
1. 已确认的现象；
2. 用户希望达到的效果；
3. 原始需求明确提出的限制（没有就写“未明确”）；
4. 仍然需要在真实界面中核实的信息。
不要猜测源码、尺寸或已有实现，也不要提出具体改造方案。

原始需求：
透视结构放置区现在占据的空间很大，而且随着放置的维度和度量越多，高度就会越高，此外左边的侧边栏有一部分还空着，想办法合理调整下布局。
#+end_src

* 三、Prompt B：交付可执行任务单
只负责把原始需求和 A 的结果转换为实际任务。=:prompt prompt-a= 是由 ob-gptel 提供的前后轮传递机制，不属于提示词正文。

#+name: prompt-b
#+begin_src gptel :prompt prompt-a :eval never-export :exports both
基于上一轮中的原始需求与问题摘要，直接输出一份最小开发任务单：
- 要解决的具体问题；
- 应检查的界面区域；
- 一项低风险、可以实际尝试的布局改动；
- 能在真实产品中检查的验收条件；
- 仍需现场确认的事实。
用人能直接读懂的短句。区分事实和建议，不假装已经查看或修改源码。
#+end_src

* 四、怎样测试
前提：本地 Emacs 已有可正常调用模型的 =gptel=，并安装、启用 =ob-gptel= 的 =gptel= Babel 后端。无需在 Org 文件中编写 API 请求代码或保存密钥。

1. 将光标放到 =prompt-a= 块内，按 =C-c C-c=；模型的原始响应应写入 =#+RESULTS: prompt-a=。
2. 确认 A 真的返回文本后，在 =prompt-b= 块内按 =C-c C-c=。ob-gptel 的 =:prompt prompt-a= 将 A 的提示和实际结果作为前一轮对话上下文交给 B。
3. 查看 =#+RESULTS: prompt-b=，确认它是实际任务单而不是操作说明。保存文件并提交 Git；现有网站发布器更新此文章，不生成新文章。
4. 两个结果应保留在本 Org 文件内。重复运行前，另存原始结果到下方新增的测试记录，避免覆盖前一次实验。

若尚未安装 =ob-gptel=，或当前模型连接不可用，本实验标记 =BLOCKED=；不得人工制造 =#+RESULTS= 冒充模型调用。站点构建时不会调用模型（=:eval never-export=）。 首次运行前可先用普通 gptel 对话确认模型连接可用；必须先得到 A 的真实结果，再运行 B。

**目标：** 减少透视结构放置区的空间占用，避免字段数量增加时持续压缩主要工作区域。
