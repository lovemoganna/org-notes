新页面或整体换视觉风格，选 Hallmark；已有页面需要修布局、文案和交互细节，选 Impeccable。先指定真实页面和具体问题，不要一上来要求重做整个产品。

* 先判断用哪个

| 任务 | 首选 | 动作 |
|------+------+------|
| 新建页面、整页改版 | Hallmark | 选主题或 =custom=；重设计用 =redesign= |
| 不改代码，只诊断已有页面 | Hallmark | =audit= |
| 修复布局、文字、冗余组件 | Impeccable | =critique= 后用 =layout= / =distill= |
| 交付前排查可访问性和响应式 | Impeccable | =audit= / =detect= |

* Hallmark：搭建或重设计网页

项目：[[https://github.com/Nutlope/hallmark][Nutlope/hallmark]]；主题预览：[[https://www.usehallmark.com/][usehallmark.com]]。

Hallmark 提供 50 种视觉主题，也支持 =custom= 自定义。它按用户实际任务组织页面，重点检查低对比度、移动端布局故障、空表单和重复装饰。

** 安装

在项目根目录执行，要求 Node.js 18+。不加 =-g= 只安装到当前项目。

#+begin_src sh :eval never-export
# 仅在当前项目安装
npx skills add nutlope/hallmark

# 或在用户级安装，供多个项目使用
npx skills add nutlope/hallmark -g
#+end_src

使用 Claude Code 时可以输入 =/hallmark=；使用 Codex CLI 时通过 =$hallmark= 调用。Cursor 和 OpenCode 按各自的 Skill 发现机制调用。若没有自动触发，明确说“使用 hallmark 处理当前任务”。

** 用法一：新建页面

给 Agent 明确的页面任务：

#+begin_example
使用 Hallmark，为数据分析产品设计一个“导入数据”页面。
目标：零基础用户能找到导入入口，完成文件上传，并知道接下来怎样配置行、列和指标。
要求：先确认页面的真实业务动作，不编造功能和数据；提供适合该任务的视觉方向；完成后检查桌面与手机布局。
#+end_example

主题只决定视觉风格，不替代真实内容和功能；想跳过主题用 =custom=。

** 用法二：审查已有页面或重设计

#+begin_example
/hallmark audit ./index.html
/hallmark redesign ./src/app
#+end_example

=audit= 只报告问题，=redesign= 会修改页面。示例路径须换成项目里的真实路径。

只换视觉风格、不改布局，可加 =keep the layout=；只修典型 AI 设计痕迹，可加 =polish=。重设计后仍要测试原有交互。

** 浏览器检查的前提

静态检查不等于浏览器验证。=sloplint --render= 还需要 Chrome 和 =puppeteer-core=；下方脚本在 Hallmark 仓库中执行。

#+begin_src sh :eval never-export
npm i -g puppeteer-core
# 在 Hallmark 仓库中运行的示例
node skills/hallmark/scripts/sloplint.mjs ./index.html --render
#+end_src

* Impeccable：检查并精修已有界面

项目：[[https://github.com/pbakaus/impeccable][pbakaus/impeccable]]；文档：[[https://impeccable.style/docs][impeccable.style/docs]]。

Impeccable 提供 24 个设计命令和 62 条检测规则，适合按组件调整已有产品：先评审问题，再用对应命令修复。

** 安装与初始化

#+begin_src sh :eval never-export
# 在项目根目录安装，并按提示选择适配的编码工具
npx impeccable install

# 以后更新
npx impeccable update
#+end_src

重新加载编码工具后，在 Agent 对话中执行：

#+begin_example
/impeccable init
/impeccable document
#+end_example

=init= 生成描述用户与任务的 =PRODUCT.md=；=document= 把当前视觉规范写入 =DESIGN.md=，供后续修改复用。

Codex 用 =$impeccable= 或 =/skills= 调用。自动检查 Hook 应先审阅权限，再在对应工具中启用。

** 高频命令与使用时机

| 命令 | 何时使用 |
|------+----------|
| =/impeccable critique= | 先做 UX 评审，按问题严重程度排序 |
| =/impeccable audit= | 检查可访问性、性能、主题和响应式等技术问题 |
| =/impeccable layout= | 修复布局、间距与视觉节奏 |
| =/impeccable typeset= | 调整字体、字号与文字层级 |
| =/impeccable distill= | 删去影响主任务的复杂组件与冗余界面 |
| =/impeccable clarify= | 改善标签、提示和操作文案的可理解性 |
| =/impeccable adapt= | 处理不同屏幕及设备尺寸 |
| =/impeccable harden= | 排查错误状态、溢出、国际化及边界情况 |
| =/impeccable polish= | 发布前的细节精修 |

指定目标组件即可调用，例如 =/impeccable critique the data import page=。

** 不通过 Agent 也能做确定性检查

#+begin_src sh :eval never-export
# 检查源码中的规则问题
npx impeccable detect src/

# 检查渲染中的开发页面（需要 Chrome 或 Edge）
npx impeccable detect http://localhost:5173

# 输出可供脚本处理的 JSON
npx impeccable detect --json .

# 列出全部规则
npx impeccable detect --list-rules
#+end_src

把路径和开发服务器地址换成实际值。源码扫描不能代替渲染检查；退出码 =2= 表示发现问题，=1= 表示无法扫描。

* 一个真实产品怎样操作

数据透视表的“行、列、指标”区域过大时，先用 =critique= 定位问题，再用 =distill= 或 =layout= 修改，最后验证拖拽、数据刷新和移动端布局。

可直接复制的任务提示：

#+begin_example
使用 Impeccable 检查当前数据透视表工作区。
问题：行、列、指标放置区占用空间过大，影响数据结果阅读。
先读取真实代码和界面，找出问题，不预设设计方案。
只优化该区域的布局与视觉层级，保留现有拖拽和字段配置功能。
完成后给出修改前后截图，在桌面与手机宽度下验证布局，
实际测试字段拖放、切换数据集和结果刷新。
列出已通过、失败和未运行的验证项，不以截图好看代替功能正确。
#+end_example

验收比较修改前后的任务完成路径、桌面和手机布局、原有功能回归与新增错误。不能用“更好看”代替“更好用”。

* 可复用元提示：按任务直接调用

将方括号中的内容换成真实项目、页面与问题。以下是给支持项目访问和代码修改能力的 Agent 的任务提示，不是终端命令。应先确认对应 Skill 已安装并加载；未获得执行环境时只给出方案，不宣称完成修改或测试。

** 1. 不知道选哪个 Skill：自动选择

#+begin_example
检查[项目/页面]，目标是[用户要完成的任务]，当前问题是[观察到的现象]。
先阅读真实界面与代码，判断需要新建/整体重设计，还是局部精修。
只选一个主 Skill：整体视觉方向用 Hallmark；已有界面细节用 Impeccable。
说明选择依据、预计修改范围及不可改变的功能；随后直接执行最小必要修改。
使用真实截图、操作回归和代码差异验收，不能验证的项目如实列出。
#+end_example

** 2. Hallmark：从零生成有业务目标的页面

#+begin_example
使用 Hallmark 创建[页面名称]，目标用户是[受众]。
用户需要在这个页面完成[核心任务]；已有真实内容和约束是[资料/约束]。
先基于任务安排操作与内容层级，再选视觉主题；不合适则使用 custom。
不要编造数据、评价、功能或无效按钮。
实现后检查桌面与手机布局、表单与导航的实际行为，并报告结果。
#+end_example

** 3. Hallmark：保留功能，重设计旧页面

#+begin_example
使用 Hallmark 先 audit [现有页面路径]，列出影响用户操作的具体设计问题。
再 redesign [现有页面路径]，目标风格为[视觉方向]。
保留原有内容、导航、事件处理、表单与数据行为；若只换视觉，keep the layout。
修改前保存基线；修改后逐项比较上述连接和核心操作，不得用设计截图代替功能测试。
输出实际改动、验证证据及未解决项。
#+end_example

** 4. Impeccable：针对一个组件做最小改进

#+begin_example
使用 Impeccable 检查[页面/组件]，问题是[具体障碍]。
读取 PRODUCT.md、DESIGN.md（存在时）及相关代码，先 critique，确定根因。
根据问题只选择必要动作：layout、typeset、distill、clarify、adapt 或 harden。
只修改相关组件，不扩大到全站；保留[功能/数据/交互约束]。
实际测试修改前后的任务路径、不同视口和相关交互，记录新增错误。
#+end_example

** 5. 检验 Skill 是否真的有用：独立 A/B 对照

#+begin_example
用同一原始版本、同一任务和相同验收标准对比[Skill A]与[Skill B]。
在两个独立分支或副本中运行，不允许后一组读取前一组修改后的代码。
保存两组完整输入、原始输出、代码差异和截图。
分别检查任务完成、功能回归、可访问性、响应式和新增问题。
只依据实际证据判断哪组更合适；如果没有可测量改善，不要宣布 Skill 有效。
未执行的测试标记为“未验证”，不要把静态审查当作端到端通过。
#+end_example
