* 如何使用
我先判断需求属于什么任务、要拿到什么结果，再选择 Skill。下面的入口按问题分类，不按仓库或名称排序。无须先理解全部 11 个 Skill。
日常调用只需说明：使用[Skill 名称]，处理[输入材料]，交付[目标产物]，保持[关键约束]。对模型尚未加载的 Skill，先让它读取表中对应的 =SKILL.md= 和必要依赖，不能把“GitHub 上存在”当作“当前环境可执行”。
一个具体例子：使用 =ontology-constrained-analysis=，分析[真实工作簿]，先检查 Runtime Gate，再按 Gate 1–4 验证，交付带实际 SQL、Result、证据和限制的报告；不得预设业务结论。

* 复用选择
| 我现在遇到什么需求？ | 首选 Skill | 要拿到什么结果 |
|---------------------+------------+----------------|
| 一堆真实业务数据，不知道字段背后的对象、合法关系和高价值问题 | =ontology-constrained-analysis= | 两张本体表、问题、真实 Signal、经过验证的 Finding |
| 已有取数目标，想学习 SQL、调试查询或交付 SQL 分析报告 | =sql-business-thinking= | 可执行 SQL、真实结果及结论，或教学步骤 |
| 有一批数据，要做面向决策的业务看板，不想套固定模板 | =dataset-dashboard-builder= | 业务主题、经过验证的指标与可验收看板 |
| 领导反馈、旧 BRD 和散乱产品要求难以直接交付研发 | =bprd-plus= | 明确功能、约束和验收标准的 BRD |
| 标签规则、流程、SOP 或判定标准缺少统一口径 | =standards-engineering-loop= | 可执行、可追溯、可测试的标准 |
| 有历史笔记，想保留原经验并重建后续查阅和使用路径 | =note-reforge= | 保留证据和独有素材的下一版笔记 |
| 有代码文章或教程，希望用 Emacs Org Babel 复用和实际运行 | =org-literate-engineering= | 可参数化、可执行、可验证的 Org 文件 |
| Skill 跑不通，想定位根因、修复、回归，又怕过拟合一个案例 | =skill-lab= | 实际测试证据、最小修复和回归结论 |
| Skill 已经定稿，想合规收录到 canonical 仓库 | =skill-repository= | 主库文件及必要依赖、更新后的 README |
| 有新知识或教程，要发布成 Org Museum 页面 | =org-museum-ingest= | 新 Org 笔记、提交和发布回执 |
| 已有 Org Museum 页面，要继续炼化而不丢失身份与原引用 | =org-museum-update= | 原路径更新、保留旧引用及发布校验 |

** 三个容易选错的边界
1. =ontology-constrained-analysis= 管“业务世界是否定义正确、关系是否合法、Finding 是否有证据”；=sql-business-thinking= 管“业务问题怎样写成 SQL 并验证结果”；=dataset-dashboard-builder= 管“哪些分析值得在看板持续呈现”。三者可按任务组合，但并非每次都必须全部调用。
2. =bprd-plus= 处理要研发实施的需求；=standards-engineering-loop= 处理长期复用的规则、SOP 和判定标准。不要把二者混成同一产物。
3. =skill-lab= 是测试和修复，不等于收录；=skill-repository= 只收录已确认 Skill，不默认调试。=note-reforge= 负责炼化内容；=org-museum-ingest= 或 =org-museum-update= 负责发布，已有页面只能走原地更新。

本页只整理 2026 年 10 月 1 日后 GitHub 有明确新增或维护记录的 Skill，不给旧仓库中的全部 Skill 做全量盘点，也不把提交次数当作调用频率。
