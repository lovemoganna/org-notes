* 先确定需要什么结果
本篇解决一个问题：交给 Gemini Antigravity 的评估任务，最终如何证明有实际价值，而不是输出一份结构完整、证据空洞的报告？

核心判断：*只能用真实任务的对照结果证明 Skill 的收益；报告长度、测试数量、模型自评及框架完整度都不能代替证据。*

交付分为三类：
| 交付 | 必须回答 | 验收证据 |
|------+----------+----------|
| 评估结论 | 使用 Skill 是否比不使用更有效 | 同任务的真实 A/B 结果 |
| 缺陷与裁决 | 哪些能力改善、退化或仍不可验证 | 具体失败案例、差异、根因 |
| 可复现资产 | 其他人如何独立重跑 | 测试输入、命令、脚本、原始输出 |

如果当前没有真实对照，结论只能写“证据不足”，不能把搭好脚手架描述成评估完成。

* 先做最小实验，不先造大型框架
第一步先选 2～4 个真实案例，完成无 Skill 与当前 Skill 的受控对照。确认实验可运行、输入可追溯、结果可独立验证后，才扩展到 20 个案例。

实验必须固定：原文快照、任务目标、验收标准、模型版本、可用工具、授权范围及初始状态。两组分开运行，防止无 Skill 组通过仓库或上下文偷读正式 Skill。

必要时再增加“精简候选版”第三组；没有实际负收益证据时，不为显示改进而删减规则。

* 验收分三层，不能互相替代
- L1 确定性检查：原文事实、Org 文件头、代码块、关键链接、禁止写入与未授权操作。用 Python 或现有脚本验证。
- L2 独立语义检查：由不知道实验组身份的评审者评价事实、证据、判断及行动。模型评审需要人工样本校准；生成者自评不等于独立评估。
- L3 下游真实任务：让独立读者基于产物完成预设任务，检查正确性、证据定位与可执行性。这是判断新增知识价值的主要依据。

举例：若原文是 Org Mode 故障排查笔记，不问“新版是否更专业”，而是让读者依据两组文章定位指定故障、区分实测与猜测、找到操作位置，并给出正确下一步。

* 最终报告只需要什么
#+begin_src text
结论：有增益 / 无明显增益 / 存在退化 / 证据不足
实验：任务数、A/B 正确率、关键失败、耗时与成本
发现：最多三项，每项列观察、证据、根因与决策影响
裁决：KEEP / PATCH / REVERT / BLOCK
交付：原始结果位置、脚本路径、复现命令、冻结版本
剩余问题：仅列出影响下一次决策的未知项
#+end_src

报告正文建议控制在 800 字以内；完整日志和案例不要删，作为独立证据保存。无效背景、重复原则、空泛的“持续优化”不进入正文。

* 可直接发送 Antigravity 的执行约束
#+begin_src markdown
# Skill 评估的执行与交付约束

本任务以实际决策价值为目标，不以字数、框架、轮次或测试数量衡量成果。

1. 先运行 2～4 个真实案例的小规模 A/B 对照；先证明评估方法可运行，再决定是否扩展到 20 个案例。
2. 每个关键结论必须对应：实际观察、可追溯证据、根因判断、决策影响。证据缺失时不得下结论。
3. 保存输入版本、模型与环境、执行命令、原始输出、评分结果；区分静态检查、模拟运行、独立评分与真实任务验收。
4. 只修复有具体失败案例的缺陷。对每项修改说明失败任务、根因归属、预期可测收益及维护代价。
5. 禁止没有失败样本的“优化建议”、概念堆叠、过程自评和未经执行的通过声明。
6. 没有实质增益时允许 KEEP；有关键退化时优先 REVERT；条件不足则 BLOCK，不制造成果。
7. 不擅自改生产 Skill，也不提交或发布未授权修改。

最终只交付：结论、实验数据、最多三项关键发现、处理裁决、可复现路径和阻碍下一步的未知项。
没有新增证据就停止循环。完整原始日志另存，不用冗长总结替代执行证据。
#+end_src

* 四个拒收问题
收到结果后核对：
1. 是否真的执行了相同输入的无 Skill / 有 Skill 对照？
2. 是否可以独立复核任务答案与评分，而非相信模型自评？
3. 能否指出具体失败案例、失败步骤和有证据的根因？
4. 能否给出 KEEP / PATCH / REVERT / BLOCK 裁决，并说明哪项证据改变了决策？

任一缺失，都不能宣称完整评估已完成。样本太小只能得出当前样本的观察结论，不能外推为普遍有效。
