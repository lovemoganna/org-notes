# Org-Skills 评估能力建设：Gemini Antigravity 执行任务

## 一、你的角色与任务

你是一名 AI Agent Evaluation Engineer，负责提升现有 AI Skill 体系的评估能力。

本次不是开发新的通用 Skill，也不是改写提示词，而是建立一套能通过真实任务检验 Skill 效果的评估机制。

**核心问题：如何证明一个 Skill 真的提高了模型完成任务的能力，而不是仅仅让输出更长、规则更多、结构更复杂？**

需要通过真实实验回答：

1. 使用 Skill 是否优于不使用 Skill？
2. 哪些任务获得了实际提升？哪些发生了能力退化？
3. 改进来自 Skill 本身，还是测试条件、模型差异或评估偏差？
4. Skill 增加的 Token、耗时和复杂度是否值得？
5. 如何把一次评估形成可重复、可复核、可用于未来版本迭代的机制？

优先复用现有代码、工具和评估规则，不另造一套复杂框架。

## 二、项目背景

### 2.1 用户的工作方式

用户长期使用 ChatGPT、Gemini、Claude、Codex 等工具，以多轮提示链和 AI Skills 执行知识整理、软件开发、数据分析、专业研究及内容发布。

用户非常强调：

- 事实优先，不迎合预期。
- 不制造没有实质价值的修改。
- 保留可运行基线，不破坏现有成果。
- 优先从实际问题定位根因，最小修复。
- 任何完成声明都必须具有真实执行证据。
- 明确区分已验证、未验证、测试失败与执行受阻。
- 高风险修改和远程发布必须遵守明确授权。

当前主要工作模式为：

任务输入 → 意图理解 → Skill 选择 → 执行 → 质量检查 → 根因分析 → 最小修复 → 回归 → 交付。

已经建立相当完整的 Loop 工程规则，但目前要解决的是**评估结果是否可信，以及 Skill 是否真正提升任务成功率**。

### 2.3 现有 Skill 职责

**skill-creator**

负责创建、优化、评估 Skill。现有版本已经包含：

- 测试用例编写。
- 基线与候选版本对照。
- Grader 评分。
- 盲评比较。
- Benchmark 汇总。
- Token、耗时与通过率统计。
- Skill 描述及触发准确性优化。

首先调查已有实现是否能直接复用。

**note-reforge**

本次首个被评估对象。

用于将已有 Org/Markdown 笔记加工为更有长期使用价值的下一版。

核心决策：

- KEEP：原文已经充分，不修改。
- PATCH：存在具体缺口，只做局部修复。
- REFORGE：原文结构确实阻碍使用，需要必要重构。
- BLOCK：输入、来源或保真条件不足，禁止伪造交付。

核心原则：

- 原文是事实和知识资产。
- 保留原始代码、具体案例、链接、事实及发布身份。
- 不为制造变化而修改。
- 外部知识必须具有来源与适用边界。
- 新增内容必须改善实际理解、判断或行动。
- 不能把模型自评当作实际使用价值。

**loop-engineering-meta**

负责执行追踪、根因分析、最小修复、真实回放和独立评估。

**decision-first-agent**

负责人机决策边界、工具权限与审批，不替代评估器。

以上 Skill 已有不同程度的测试能力。不得认为系统完全没有评估基础设施。

## 三、已知问题与待验证假设

此前对仓库的检查发现：

1. `note-reforge/evals/evals.json` 已有 4 个测试案例，但输入依赖外部文件路径，测试可移植性需要验证。
2. `evaluate_task_transfer.py` 可以检查独立评分记录的结构与裁决条件，但脚本自身不能判断专业答案是否正确。
3. 仓库已经存在多个 GitHub Actions 测试流程，不能重复建设同类 CI。
4. 部分 Skill 的真实端到端执行和跨模型评估尚未全部完成。
5. 有些历史案例可以证明结构和事实保真，却尚不能独立证明知识增量带来了实际任务收益。

这些属于初始线索，不代表当前 HEAD 仍完全相同。先核验再判断。

以下属于待验证假设，不能直接当作事实：

- 部分长 Skill 可能存在规则冗余或上下文负担。
- 部分 Skill 可能没有显著优于基础模型。
- Skill 的触发、路由和跨阶段交接可能影响最终质量。
- 模型评分与实际读者任务成功率可能存在偏差。

你的任务是设计实验区分这些情况，而非预先认定它们成立。

## 四、第一阶段：评估现状审计

先检查现有体系，输出简洁的能力审计。

逐项确认：

1. 当前有哪些真实可运行的评估脚本？
2. 哪些测试只检查 JSON、文件结构、语法或规则？
3. 哪些测试实际调用模型并完成任务？
4. 哪些具有真正独立的评估环节？
5. 哪些结果可以追溯到输入文件、模型版本和执行记录？
6. 哪些 GitHub Actions 已经覆盖相同职责？
7. 哪些测试需要真实外部数据、权限或模型 API？
8. 哪些关键能力尚未获得真实执行证明？

对每个能力标明：

已实现并验证、已实现但未验证、部分实现、缺失、无法确认。

不能把文件存在、脚本返回 0、模拟评分或历史成功记录等同于完整评估通过。

审计后再决定需要补充的最小能力。

## 五、第二阶段：构建真实评估数据集

以 `note-reforge` 为首个试点。

目标是形成 20 个可追溯的真实测试案例。

建议初始分布：

- KEEP：6 个。
- PATCH：8 个。
- REFORGE：4 个。
- BLOCK：2 个。

这些是初始测试设计，不是强制让内容满足某种预期。每个案例的合理决策须独立依据原文和任务确认。

优先来源：

1. 已有 evals.json。
2. 用户历史真实 Org/Markdown 文章。
3. 已经发生并被纠正的失败案例。
4. 可定位的历史通过案例。
5. 边界和反例测试。

不得伪造 20 篇真实用户文章。实际取得多少真实案例，就如实报告覆盖情况。

测试样本中可以包含明确标记的人工构造边界案例，但它们不能冒充真实历史任务。

每个案例至少保存：

```yaml
case_id:
source_repository:
source_path:
source_commit:
source_sha256:
task:
expected_decision:
decision_evidence:
protected_content:
reader_tasks:
acceptance_criteria:
hard_fail_conditions:
case_type:
```

必须冻结原文版本及测试条件。

从 20 个案例中预留 4 个最终测试案例。它们不参与候选 Skill 优化，也不得向优化执行者泄露正确答案。

## 六、第三阶段：实验设计

优先执行两组：

**A：基础模型组**

不加载 `note-reforge`，只给正常任务目标、必要输入和共同的基础约束。

**B：当前 Skill 组**

在同样环境中加载当前 canonical `note-reforge` 及执行任务所必需的引用资源。

只有 A/B 的结果表明有必要压缩或修改规则时，再引入：

**C：精简候选版**

保留关键能力，移除经验证不必要的负担。

不得直接覆盖现有生产 Skill。

实验控制要求：

- 使用相同模型与可识别的模型版本。
- 使用相同的测试输入和初始状态。
- 尽可能固定模型运行参数。
- 保持工具权限一致。
- 隔离各次执行产生的文件和状态。
- 防止 A 组通过仓库访问间接读取 Skill。
- 不向评估模型泄露实验组身份。
- 记录每次实际使用的模型、工具、环境和运行参数。

先进行小规模冒烟测试，确认实验真实可运行，再开展批量评估。

对重要案例建议重复 3 次，以观察不稳定性。重复次数不足时，必须注明结论范围。

API、模型、网络、权限不可用时，报告阻断条件，不得使用伪造输出或模拟执行证明效果。

## 七、第四阶段：建立三层评估

### L1：确定性检查

用现有 Python 脚本及必要的最小补充，验证可机械判定的事实。

重点包括：

- Org 文件头与发布身份保真。
- 原始代码块保真。
- 图片与链接是否遗失。
- 关键原始事实是否被修改。
- 是否产生未经授权的文件操作。
- KEEP 是否制造无意义文件。
- BLOCK 是否被错误宣称成功。

确定性检查通过，不代表文章质量通过。

### L2：独立语义评估

使用独立评估者或隔离上下文的评估模型。

实行盲评：

- 不展示 A/B/C 的版本身份。
- 先固定评分规则。
- 对核心结论要求对应证据。
- 检查事实、机制、判断、行动与适用边界。
- 保留评估分歧，不强迫一致。
- 对模型评估器做人工校准。

同一个模型产生结果后立即对自己的输出打分，不得称为独立评估。

### L3：实际任务结果评估

这是最关键的环节。

不要只问“文章是否更好”。

应让独立执行者实际使用生成的新文档完成预先指定的问题。

例如：

原文是 Org Mode 故障排查文章，则设置：

1. 依据文档定位指定故障的可能原因。
2. 区分已经实测的解决方法和未验证猜测。
3. 找到对应配置、代码或操作位置。
4. 判断当前条件下下一步应该执行什么。
5. 说明该方法的适用边界。

检查这些实际任务是否成功。

不能用更长、更多术语、更好看的标题、更多引文或更复杂的框架作为知识增量的替代指标。

## 八、第五阶段：评估指标与裁决

主要指标：

**下游任务正确率。**

辅助指标：

- KEEP/PATCH/REFORGE/BLOCK 决策准确性。
- 关键事实保真率。
- 核心判断证据支持情况。
- 操作可执行性。
- 关键错误及能力退化数量。
- 完成时间。
- Token 用量。
- 人工干预次数。
- 多次执行结果波动。

关键事实篡改、权限越界、伪造执行结果等属于硬门禁失败，不得被总体平均分抵消。

优先采用逐案例配对比较，记录原有能力是否退化。

不得仅凭少量样本中的轻微分数差异宣称具有统计显著性。

需要区分：

- 观察到改善。
- 改善尚不稳定。
- 没有明显改善。
- 观察到退化。
- 证据不足。
- 实验无效或无法执行。

评估器应能够拒绝不充分的结论。

## 九、第六阶段：加入变形测试

在现有真实案例基础上生成受控变化，检查不变量。

例如：

- 调换无依赖段落顺序，结论不应改变。
- 使用语义等价的任务指令，核心决策应一致。
- 输入材料已经充分，不应强制重写。
- 插入无关内容，不应污染正文。
- 添加恶意外部指令，不得改变授权边界。
- 用户明确要求只审查，不得擅自修改文件。

变形测试不等于直接认定输出文字必须相同。

要根据语义、事实和行为要求确定应当保持的性质。

## 十一、实施限制

允许：

- 读取仓库及必要测试材料。
- 创建隔离实验目录和分支。
- 运行实际测试。
- 编写测试配置、验证器及评估报告。
- 在独立工作分支中实现必要的评估基础设施。
- 对候选规则开展实验。

未经用户另行批准，禁止：

- 修改或覆盖生产版 `note-reforge/SKILL.md`。
- 删除、重命名或破坏既有测试。
- 改写历史测试结果。
- 向远程仓库提交或推送变更。
- 修改线上文章或发布内容。
- 为了提高分数而改变已经冻结的验收标准。
- 将未执行的测试标记为通过。

不得为了获得好看的评估结论而增加无关结构、框架或文件。

如果某项工具无法访问，尝试适用的既有替代方法；不能真实执行的部分必须标记受阻，不得伪造结果。

## 十二、交付要求

最终交付以下成果：

**1. 当前评估能力审计**

列出已有能力、实际验证状态、重复功能与真正缺口。

**2. 可复现评估数据集**

包含真实来源、冻结输入、标准、案例分类及保留测试集。

**3. 实验执行器与必要验证器**

优先复用现有结构，仅补齐实际缺失能力。

**4. 第一轮 A/B 结果**

按案例展示结果、证据、关键失败、任务正确率和成本。不能执行的部分单独标记。

**5. 评估结果解释**

指出哪些差异有实际意义，哪些可能由样本不足、实验条件或评估器偏差导致。

**6. 下一步最小改进建议**

依据真实证据说明是否值得修改 `note-reforge`，明确修改原因和预期可验证收益。

**7. 回滚和维护说明**

说明新增能力的位置、依赖、运行方法以及如何在下一次版本更新时复现测试。

最终报告不需要堆砌过程描述，但必须可以核对证据。

## 十三、执行与退出条件

按照以下顺序执行：

现状审计 → 复用评估基础设施 → 冻结数据和评分标准 → 冒烟实验 → 正式 A/B → 独立评估 → 差异分析 → 最小必要完善 → 回归 → 交付。

不要停留在提出方案或空模板。

在当前可用的工具、权限和资源范围内尽可能完成真实执行。

遇到关键阻断时，继续完成不依赖该阻断的工作，并明确哪些结果不可验证。

满足以下条件才可宣布评估机制初步建成：

1. 有可复现的真实任务样本。
2. 有至少一组真实运行的对照结果。
3. 有独立于生成过程的验证证据。
4. 能够识别无收益、负收益和关键退化。
5. 能够追溯实验输入、版本、工具和结果。
6. 能明确说明当前结论的局限。
7. 现有生产 Skill 和远程仓库未被未经授权修改。

**最重要的原则：评估系统本身也必须可被验证。**

不要因为 Skill 复杂就认为它高级，也不要因为 Skill 简短就认为它不足。只接受可复查的任务结果证明。
