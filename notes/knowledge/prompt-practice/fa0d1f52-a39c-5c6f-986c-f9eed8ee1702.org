* 使用入口
我需要的不是让提示词看起来专业，而是检验它是否让模型在具体任务上稳定给出可用结果。先检查 *清晰性、上下文、精确性、角色扮演* 四个维度，再实际运行、比较与记录。角色扮演只在任务需要特定视角时使用，不是每条提示词的必需成分。〔补〕

1. *定目标*：写明真实任务、使用者、输入材料和成功条件。缺了判断标准，就先不要打效果分。
2. *改输入*：找出会让模型猜测的指令，补足必要的背景、限制、数量、格式和示例。
3. *试运行*：用相同任务和模型条件比较修改前后。原文建议每版生成 *3–5 次*，这是初始试验次数，不是统计显著性的保证。
4. *留下证据*：保存提示词版本、模型和参数、实际输出、失败案例与人工修订量；只有结果改善才推广新版本。〔补〕

* 四维质检

| 维度 | 先检查什么 | 常见失败 | 优先修法 |
|------+------------+----------+----------|
| 清晰性 | 任务、动作、歧义 | 只说“研究一下”“优化一下” | 写出对象与可执行动作 |
| 上下文 | 背景、受众、目标、资源 | 模型必须猜业务情境 | 补充任务所需的事实及限制 |
| 精确性 | 数量、格式、示例、排除项 | 无法判断输出是否符合要求 | 给出可检查的结果契约 |
| 角色扮演 | 视角、知识边界、口吻 | 用角色包装代替真实依据 | 仅在确需特定视角时使用 |

**原文量化建议，不是通用科学标准。** 原材料提出句子宜 *15–25 字*、超过 *40 字* 时考虑拆分、每百字术语不超过 *3 个*、非专业人员复述成功率 *≥90%*、模糊指令占比 *<10%*、上下文可用 =5W1H= 与至少两层背景检查。这些是历史笔记的候选检查规则；原文没有提供足以证明各阈值普适有效的实验数据。中文不能直接把英文的 Flesch Reading Ease 评分当成通用可读性证据。〔补〕

* 三个可复制案例

** 案例一：补齐上下文
下面的业务数据是*原文历史示例*，不是现在的经营现状。先保留示例本身，再决定是否替换为真实项目。〔补〕

#+begin_src text
背景：我们是一家成立3年的B2B SaaS初创公司（20人团队），主要为中小型制造企业提供库存管理软件。
当前状况：获客成本高（$500/客户），主要依赖付费搜索广告，月均新增客户10个，客户生命周期价值约$2000。
目标：在下一季度（Q3 2023）将获客成本降低30%，同时保持或提高新客户获取速率。
预算：营销预算为每月$15,000。

请提出三种可行的营销策略调整方案，每种方案需包含实施步骤、预期成本和ROI分析。
#+end_src

用它检查：模型有没有在 *$15,000/月* 的预算下提出三种方案；是否引用已给定的客户成本、客户数量和生命周期价值；成本与 ROI 计算是否可复算。不能把示例数字解释为实际业绩。〔补〕

** 案例二：让输出可验证
#+begin_src text
为电子商务网站生成5条高端家用咖啡机的产品描述：
- 每条描述长度：60-80字
- 目标受众：30-45岁的城市专业人士
- 必须包含：一项技术规格、一项用户体验优势、一个情感诉求点
- 风格：专业但友好，避免过度营销词汇（如“革命性”、“颠覆”）
- 价格范围：2000-5000元

示例格式：“[产品名称]采用[技术规格]，能够[具体功能]。每天清晨，您可以享受[用户体验]，让[情感诉求]成为日常。”
#+end_src

可直接验收输出数量、每条长度、必填要素和禁用词；产品技术规格、价格与事实真实性仍需来自真实产品资料，不能由模板自动证明。〔补〕

** 案例三：避免含混任务
| 原始写法 | 明确后的写法 |
|----------+--------------|
| 优化公司的营销策略。 | 补充行业、目标客户、获客成本、目标、时间与预算，再要求方案 |
| 生成一些产品描述。 | 指定产品、数量、受众、规格与输出结构 |
| 像物理学家一样解释黑洞。 | 说明受众、需要的科学概念、解释深度及准确性要求 |
| 讨论供需关系及其影响。 | 要求解释需求和供给变化，并使用具体市场场景 |

这些简写只用于定位原文的改进方向，不替代附件中的完整正反案例。原文还有医疗伦理、光合作用、黑洞角色扮演、历史事件与科幻日志等完整示例，均保存在冻结原文附件中。〔补〕

* 评分与试验记录

原文的权重是：*清晰性 30%、上下文 25%、精确性 25%、角色扮演 20%*，各维度评分 *1–5 分*。可采用加权平均做一次内部检查，但权重反映原笔记的判断，并非跨业务、跨模型验证后的最佳权重。若任务不需要角色扮演，不应仅因角色缺失就判质量不合格。〔补〕

| 字段 | 本次如何填写 |
|------+--------------|
| 版本与任务 | 原版/新版；真实输入；期望解决的问题 |
| 环境 | 模型版本、参数、运行日期 |
| 检查 | 格式合规、事实准确、关键要求遗漏 |
| 结果 | 每版的实际响应、失败例、人工修正量 |
| 决策 | 保留原版 / 采用新版 / 继续收集证据 |

执行顺序沿用原文：*预评估、试运行、反馈循环、版本记录、周期审查*。如果没有真正跑模型，只能记录“结构建议”，不能写成“已验证有效”。〔补〕

* 来源中的事实边界

原文有一段历史提示把 *1775 年独立战争爆发* 与 *萨拉托加之战* 并列作为解释对象。这里存在时间线不匹配：美国国家公园管理局记录 1775 年 4 月列克星敦和康科德的交火，而萨拉托加战役发生于 *1777 年*。因此不应照抄该示例作为“1775 年爆发原因”的正确示范。原句完整保留在附件供比较。〔补〕

另一个边界是原文使用理查德·费曼的具体身份设计角色提示。角色可以控制讲述视角，却不能保证生成的历史交流细节或科学事实真实；需要事实核查时应优先要求可核对的依据。〔补〕
