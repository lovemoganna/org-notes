#+WIKI_STATUS: published

想让 AI 稳定完成复杂任务，光说“认真思考、反复优化”没有用。要告诉它什么时候搜索、何时换方案、凭什么接受结果，以及失败后从哪里继续。这些规则组合起来，才是一条能重复调用的提示链。

本文提供九种*可直接粘贴进 ChatGPT、Claude 或 Codex 对话*的提示模板。它们不要求 Excel 公式，也不默认需要 API。涉及联网、文件、代码或独立代理的步骤，只有产品确实提供相应能力才能执行。

原有的五类基础工作流（顺序、路由、并行、编排、评估优化）及历史 Google Sheets 结果，见[[https://lovemoganna.github.io/org-notes/pages/collected/knowledge/prompt-engineering/c596dd07-857d-4bff-b7e3-b3b9f5e1571d.html][《提示链案例解析》]]。本文不重复那份表格，也不把历史显示结果当作新测试。

* 遇到什么问题，用哪一条

| 实际问题 | 选择 | 它解决的关键麻烦 |
|----------+------+------------------|
| 查资料时不知道下一步该查什么 | ReAct 行动观察链 | 根据搜索得到的事实调整下一步 |
| 想了一个方案就不再考虑其他办法 | 思维树 | 比较路线，失败时退回分叉点 |
| 几条思路都不错，却不知道怎样组合 | 思维图 | 将不同方案的有用部分重新连接 |
| 不同问题总被套进同一种分析表 | 自组装分析链 | 先选适合当前问题的分析方法 |
| 一篇文章有数据和事实疑点 | 证据修订链 | 逐项核实，只改有问题的地方 |
| 搜了一堆网页，却没解决真正的问题 | 按需检索链 | 先找证据缺口，再决定查什么 |
| 同类错误下次又出现 | 经验记忆链 | 把实际失败转成下一次可用的规则 |
| 每个问题都要求多角色辩论 | 条件辩论链 | 只在有实质争议时增加审查 |
| 多个代理交接时丢任务、丢约束 | 契约交接链 | 用明确的交付物与验收标准接力 |

* 用法：先保存一次，再多轮调用

选一种模式，把它的完整“启动提示”发送到一个新对话。随后发送下面的“第2轮、第3轮”指令，不需要反复粘贴整份规则。一个聊天里的连续指令是自然语言约定，不是产品自带的斜杠命令。要跨新聊天复用，可把模板放进 ChatGPT Project 指令、可用的 Skill 或项目文件中；新会话还需要提供上次的简短状态记录。

共同约定：*每轮只汇报已经做过的动作和取得的证据；不会的工具就说不能用；没有真实运行，就标“未验证”*。修改最多三轮；完成、遇到阻塞或没有新证据时停止。

* ReAct：查到一条信息，再决定下一步

想象你要安装一个陌生的开源工具。如果一开始就让 AI 写完整安装教程，它很可能把老版本参数和新版本混在一起。更可靠的做法是：先读官方仓库，再根据实际看到的依赖检查下一步。

#+begin_src text
# ReAct：行动—观察—调整
你是按真实证据行动的研究助手。
收到“启动｜任务”后，先明确需要核实的一个问题，再调用当前可用的工具。
每次获取工具结果，都要回答：
1. 实际查到了什么？给出可核查的来源。
2. 原来的判断是否需要改变？
3. 下一步最值得核实的一个问题是什么？
只做对任务有用的操作。每轮最多四次工具动作。
没有工具或资料无法访问时，不假装已查到。
“继续”表示根据最新结果推进；“收尾”表示汇总已证实事实和未知。
#+end_src

*三轮怎么用*：
1. =启动｜查找 Graph of Thoughts 的官方安装要求=。
2. =继续｜检查官方 README 提到的运行环境=。
3. =收尾｜只给出有出处的安装条件，未核实的不要补=。

*怎样知道有用*：第二轮应根据第一轮读到的真实说明继续查，而不是事先捏造安装命令。没有联网工具时，这条链只能处理用户已提供的文档，不能声称检索成功。

* 思维树：先走几条路，走不通就回来

打算做一款英语学习工具时，可能有三条不同的路线：现成聊天工具、低代码产品、自己开发。不能只因为第一条最容易想到，就断言它最好。

#+begin_src text
# Tree of Thoughts：分叉—比较—回溯
收到“探索｜目标｜限制”后：
1. 固定目标和不可改变的限制。
2. 提出三条真正不同的可行路线，每条写明前提、主要代价和失败条件。
3. 不符合硬约束的路线淘汰，保留淘汰原因。
4. 收到“深挖｜路线名”时，只展开这条路线的下一层。
5. 收到“回溯｜路线名”时，回到该分叉点重新选择。
6. 收到“收敛”时，比较留下的方案，给出一条建议和一个备选。
最多探索三层。缺乏价格、技术或资源证据的地方，只能列为待核实。
#+end_src

*三轮怎么用*：
1. =探索｜为成年人设计每天15分钟的英语口语训练｜不开发独立App=。
2. =深挖｜利用现成聊天产品的路线=。
3. =回溯｜对比使用现成课程的路线=，然后 =收敛=。

*怎样知道有用*：至少能看到真实不同的路线和回溯理由。单纯把同一个方案写成三个标题，不是分叉探索。

* 思维图：把不同方案拼出新方法

思维树在选择路线；思维图还允许把两条路线组合。例如，用游戏提供即时反馈，用知识图谱记录学过的概念，再让 AI 根据薄弱点出题。

#+begin_src text
# Graph of Thoughts：建点—连接—验证
收到“建图｜问题”后，建立三个来自不同领域的解决思路节点。
每个节点记录：核心机制、成立条件、限制。
收到“连接｜节点A｜节点B”时：
- 说明两个机制能否兼容；
- 若能，指出组合后真正新增的能力；
- 若不能，说明具体冲突，不强行合并。
收到“扩展｜节点ID”时，只扩展该节点。
收到“验证｜节点ID”时，提出一个最低成本、结果可观察的实验。
输出节点名称与关系，避免只堆概念。
#+end_src

*三轮怎么用*：
1. =建图｜如何让人真正记住读过的技术文章？=
2. =连接｜知识图谱节点｜间隔复习节点=。
3. =验证｜新组合节点：用十篇文章开展一周学习实验=。

*怎样知道有用*：组合方案应产生新行为，例如“根据概念依赖安排复习”，而不只是把两个产品功能摆在同一页。

* 自组装分析：问题不同，分析办法也该变

评价一个软件是否值得采用，需要比较需求、能力、成本；解释一个历史争议，需要核对史料和不同证据。两者都套“优势、劣势、机会、威胁”会遗漏重要问题。

#+begin_src text
# SELF-DISCOVER：按任务挑选分析方法
收到“发现｜问题”时，先判断这是什么类型的问题。
从事实核验、因果分析、计算、方案比较、反例排除、创意组合中挑选必要方法。
说明为何选这些方法，以及它们的先后依赖；不要为凑齐方法而全选。
收到“执行”时按所选结构完成任务，需要新资料就实际检索。
收到“质疑｜遗漏点”时检查结构是否缺了影响结论的关键维度。
收到“固化”时，保存本次可复用的方法及适用条件，而不是把答案当成通用规则。
#+end_src

*三轮怎么用*：
1. =发现｜为什么某个开源工具有很多用户，却很难赚钱？=
2. =执行=。
3. =质疑｜是否遗漏了真正付费的人和使用者不是同一群体？=。

*怎样知道有用*：面对经济问题和程序错误时应选择不同检查结构；“方法选对了”仍不等于答案的事实已验证。

* RARR：文章有疑点，先查证再改字

遇到一篇声称“某项目速度提升90倍”的文章，不能一口气改写成流畅科普。先找清楚：是哪个版本、什么测试环境、与谁比较、数据出自哪里。

#+begin_src text
# RARR：查主张—找证据—最小修订
收到“反查｜文章”时：
1. 提取其中可核实的事实主张，并编号。
2. 对每项主张查找一手资料，核对数据、时间、版本和限制条件。
3. 标记“证据支持／证据反驳／证据不足”，提供来源。
收到“补证｜编号”时只深入该主张。
收到“修订”时，只修改被反驳或说得过满的内容；保留有根据的原文。
收到“复核”时重新查改动后的关键事实与引用。
未经核实的内容不能写成确定事实；不能因为文字流畅就称修订完成。
#+end_src

*三轮怎么用*：
1. =反查｜[粘贴一篇介绍开源引擎性能的文章]=。
2. =补证｜主张C02：最高性能提升倍数=。
3. =修订=，再 =复核=。

*怎样知道有用*：读者能看出改了哪一句、为什么改、出处在哪里。没有可信测试条件时，把“最高可达”保留为来源声称，而非普遍性能承诺。

* 按需检索：缺什么证据，才去查什么

要比较 DuckDB 和 SQLite，不需要先搜索几十篇“数据库排行榜”。应该先明确关心的是分析速度、事务处理还是部署成本，再查官方资料能否回答。

#+begin_src text
# 按需检索：问题—缺口—补证
收到“研究｜问题”后：
1. 拆成必须回答的关键子问题。
2. 对每项标记“已有足够依据／需要补证／证据冲突”。
3. 只对后两类启动针对性检索，优先一手来源。
4. 检查新来源是否真正回答了缺口；不相关就换查询目标。
收到“检查覆盖”时，列出仍未回答的问题。
收到“补证｜具体问题”时，仅查指定缺口。
收到“结论”时给出有证据支持的建议与未解决事项。
最多连续补证三轮；不能靠增加链接数量证明结论正确。
#+end_src

*三轮怎么用*：
1. =研究｜本地知识库应该选 DuckDB 还是 SQLite？=
2. =检查覆盖=。
3. =补证｜两者在并发写入与事务方面的区别=，再 =结论=。

*怎样知道有用*：新增搜索应填补具体证据空洞，而不是重复已知常识。这里借鉴 Self-RAG 的按需检索思想，*不是原研究训练模型的等价实现*。

* Reflexion：犯过的错，下一题别再犯

练英语时，第一次把“可能”误译为“一定”；下一题如果再犯同类错误，说明仅靠一次纠正还不够。需要把反馈写成简短、明确、可复用的检查规则。

#+begin_src text
# Reflexion：试做—反馈—经验复用
收到“训练｜目标”时，给出一个适量任务并保存验收要求。
收到“反馈｜实际错误”时：
1. 对照原任务确认错误是否存在；
2. 找到影响下一轮的可迁移原因；
3. 写成一条具体检查规则，不保存空泛的“更仔细”。
收到“下一题”时，换一个场景测试这条规则。
收到“复盘”时，根据真实表现决定保留、修改或撤销经验。
收到“导出经验”时，给出短状态卡，供新会话继续使用。
没有实际反馈时，不能把模型自我检讨当成已证实的学习效果。
#+end_src

*三轮怎么用*：
1. =训练｜把一段含“可能、通常、必须”的英文说明翻成中文=。
2. =反馈｜把 may 翻成了“一定”，改变了原句确定性=。
3. =下一题｜再给一段带不确定性表达的说明=，之后 =复盘=。

*怎样知道有用*：换题后仍正确保留可能性，才说明经验可能有帮助。普通聊天不会自动保证永久保存经验；跨会话需使用项目文件、Skill 或状态卡。

* 条件辩论：有实质争议，才请反方挑错

选择软件方案时，不必每次都让五个 AI 角色开会。只有关键条件互相冲突，或者错误决策成本高时，对抗审查才值得增加开销。

#+begin_src text
# 条件辩论：判断—异议—查证—裁决
收到“判断｜问题”时，先给出基于现有证据的初步结论。
只有满足以下条件之一时，启动对立审查：
- 可靠资料出现实质冲突；
- 一个尚未证实的条件会改变选择；
- 方案存在重大、难恢复的代价；
- 出现能推翻初步结论的具体反例。
收到“提出异议”时，先给出最强反对论点及其可核实依据。
收到“交叉验证”时，实际核对决定性事实，不靠角色投票。
收到“裁决”时说明接受、否定或保留争议的理由。
最多两轮对抗；同一个模型扮演正反方不等于独立代理。
#+end_src

*三轮怎么用*：
1. =判断｜三个人的初创团队该自建数据平台还是购买SaaS？=
2. =提出异议｜审查维护时间和数据合规要求=。
3. =交叉验证=，再 =裁决=。

*怎样知道有用*：简单问题应直接处理；发生真正冲突时，结论会随着新证据改变。本模板只是对选择性辩论研究的普通对话改编，不具备原研究训练分类器的性能保证。

* 契约交接：换一个代理，工作不从头来

有些任务先由 AI 理需求，再让 Codex 写代码，最后让另一个工具测试。交接失败常发生在这里：后一个工具只收到“请继续”，不知道完成标准，也不知道哪些内容不能改。

#+begin_src text
# 契约交接：任务—执行—验收—交接
收到“接收｜目标”时，建立任务契约：
目标、输入及来源、允许操作、禁止事项、交付物、验收条件。
收到“分派”时，只为实际需要的阶段分配工作，注明依赖关系。
收到“验收｜阶段名”时，检查真实产物与原始契约的差异；未通过就返回缺口。
收到“交接”时，导出一份新会话也能读懂的交接包：
- 当前目标与约束
- 已完成内容及可访问的产物位置
- 已运行的检查与结果
- 未完成事项及下一步
收到“完结”时，只把有证据的结果标为完成。
没有独立代理能力时按单模型分阶段执行，并如实说明。
#+end_src

*三轮怎么用*：
1. =接收｜根据产品需求开发一个可筛选的任务看板=。
2. =分派｜先定义页面功能，再实施，再验证=。
3. =交接｜为新的 Codex 会话准备继续开发所需的完整状态=。

*怎样知道有用*：关闭原会话后，接手者能凭交接包找回目标、代码位置、已测结果和下一步，不必猜测。交接成功不等于接手者已经执行成功。

* 怎么判断提示链真的可复用

不是看提示写了多少字，而是看同样的调用约定能否在下一次任务中继续起作用。

- *用真实输入*：选择当前正在处理的问题，而不是让模型捏造“已经运行”的演示。
- *留可检查的结果*：搜索有来源，代码有实际运行记录，修改有差异，失败有证据。
- *换一个条件复试*：例如从“有资料可查”改成“资料缺失”，看能否正确停止或降级。
- *只修失败点*：如果缺的是工具权限，就不要无限重写提示词；如果成功方案已足够简单，也不要为展示复杂工作流增加步骤。
- *给下一次留入口*：版本、已知边界、已证实失败、最短继续指令。
