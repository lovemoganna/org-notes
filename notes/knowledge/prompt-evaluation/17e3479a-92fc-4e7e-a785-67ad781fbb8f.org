\# Vibe Coding 系统一致性审查与质量修复\
\## 一、任务目标\
全面审查整个系统及所有组件、子页面的 UI、功能和交互。识别并修复长期 Vibe Coding 过程中产生的视觉漂移、重复实现、样式冲突、交互不一致和功能缺陷。\
保留现有整体设计风格、正常功能和稳定实现。不以重新设计界面为目标，不进行无依据的重构。最终确保整个系统的视觉统一、功能完整、交互一致、运行稳定，并支持持续迭代。\
\## 二、当前问题\
长期多轮 AI 修改可能使系统逐渐出现以下问题：\
1\. 视觉不一致：不同页面的字体、字号、颜色、间距、边框、圆角、组件尺寸和布局规则存在差异。浅色与深色主题的表现可能不统一。\
2\. 组件重复：相同或相近功能存在多套实现。局部 CSS、特殊样式和覆盖规则不断增加，可能产生样式冲突。\
3\. 交互不一致：同类组件在不同页面的操作逻辑、交互状态和反馈方式存在差异。部分按钮、菜单、链接或其他操作入口可能无法正常使用。\
4\. 功能不稳定：空数据、长文本、异常输入、加载失败、禁用状态、页面切换和窗口尺寸变化等场景可能存在功能或布局问题。\
5\. 修改范围失控：局部修复可能影响无关页面和正常功能。重复补丁可能使系统级问题长期存在，并引入新的缺陷。\
上述问题属于待检查范围，不代表已经确认存在。必须通过实际检查确定问题是否存在、影响范围及具体原因。\
\## 三、执行要求\
按照 MECE 原则检查整个系统的 UI、功能和交互。覆盖所有组件、子页面、交互状态和边界场景。\
先识别问题，再判断根因。区分系统级缺陷、局部缺陷和正常业务差异。同类问题必须检查是否存在共同根因，避免逐页面重复添加补丁。\
优先复用现有通用组件。相同功能应保持统一，但不得仅凭外观相似就合并业务行为不同的组件。统一检查字体、文本层级、配色、间距、页面容器、栅格、表单、按钮、图标、图片、卡片、弹窗、菜单和其他已有界面元素。\
同时检查 Hover、Focus、Active、Disabled、Loading、Empty、Error、Success 等状态。检查不同窗口尺寸、页面切换及浅色和深色模式下的布局与交互表现。验证实际功能，不得仅凭界面正常就认定功能正常。\
修复时优先处理共同根因。相同规则应尽量收敛到已有公共组件或统一设计规则。不得通过持续追加局部 CSS、特殊值或覆盖规则掩盖系统问题。\
严格控制修改范围。已正确、统一且能够正常工作的部分保持不动。不得为了统一外观而改变正确的业务逻辑，也不得为了局部优化而重写稳定实现。\
\## 四、执行流程\
按照以下顺序执行：\
1\. 全局扫描：检查系统页面、组件、样式、功能和交互。\
2\. 问题识别：记录发现的缺陷、不一致、重复实现和边界问题。\
3\. 根因判断：确认问题来源，区分共同根因与局部问题。\
4\. 规则统一：明确同类组件应遵守的视觉、功能和交互规则。\
5\. 最小修复：只修改必要内容，避免影响无关页面和正常功能。\
6\. 回归检查：验证修复结果，同时检查相关页面、交互、功能和异常场景。发现新问题时继续检查和修复。\
可以使用适当的 AI Skills 辅助分析、修复和验证。\
\## 五、验收标准\
1\. 系统整体设计风格保持不变。同类组件的视觉、状态和交互表现保持一致。\
2\. 已确认的缺陷得到修复，且修复结果能够通过实际检查验证。\
3\. 按钮、菜单、链接及其他操作入口能够正常执行对应功能。\
4\. 正常路径、异常场景、不同窗口尺寸和主题模式均完成相应检查。\
5\. 已有正常功能没有退化。修复过程没有引入新的已知缺陷。\
6\. 重复实现和系统级不一致得到合理处理，不再依赖针对各页面反复追加补丁。\
7\. 未经证实的问题不得标记为已修复。未经检查的范围不得标记为通过验收。\
\## 六、信息边界\
所有缺陷判断、修改内容和验收结论必须以实际检查结果为依据。不得虚构测试结果，不得将未经验证的实现标记为完成。\
最终目标是控制长期 Vibe Coding 造成的系统质量退化，使整个系统持续保持统一、稳定、可复用和可迭代。\

#+begin_src markdown
对当前项目的全部可视化组件进行一次系统性扫描和修复。\
\
目标不是修复几个已知图表问题，而是消除整个项目中重复出现或潜在存在的可视化缺陷，并将同类问题收敛为统一规则。\
\
先自行扫描项目，识别实际使用的图表库、图表类型、数据链路、分析层、格式化层、配置层和渲染层。所有未知信息以当前项目实际代码和运行结果为准，不询问用户，不预设技术方案，不擅自替换现有技术栈。\
\
检查全部可视化组件的数据、计算、显示、交互和响应式行为。重点检查标题、图例、坐标轴、Label、Tooltip、数值格式、单位、比例、排序、空值、异常值、重叠、遮挡、越界、缩放、筛选、联动和状态残留。\
\
发现问题后先判断是否属于共性问题。能在公共层解决的，必须在公共层统一修复。禁止针对不同图表、页面或组件重复实现相同逻辑。图表组件只负责展示，不重复承担可以共享的计算、格式化、配置或状态处理。\
\
所有图表必须保证数据正确、单位明确、格式统一、Label 可读、Tooltip 完整、图例清晰、坐标轴合理、空数据状态明确。不同数据量、筛选条件和组件尺寸下，不得出现遮挡、错位、截断、越界、交互失效或旧状态残留。\
\
修复完成后重新扫描全部可视化组件。确认同类问题已经全局消除，而不是只修复当前发现的位置。\
\
验收标准：全部可视化组件在不同图表类型、数据量、筛选条件和组件尺寸下，均保持数据正确、显示一致、交互正常、响应式稳定。不得残留明显缺陷或同类重复实现。\
\
可视化细节补充\
1\. 柱状图 / 条形图\
&#x20;  \- 每个柱体直接显示对应 Label Value；\
&#x20;  \- 数值统一带计量单位和格式化，如 12.4K / 23.6% / ¥1.2M；\
&#x20;  \- 正负值必须明确区分零轴；\
&#x20;  \- Label 超出空间时自动外置，禁止遮挡或截断；\
&#x20;  \- 支持排序、TopN、分组、堆叠、百分比堆叠；\
&#x20;  \- 点击柱体可作为筛选条件联动其他图表。\
2\. 饼图 / 空心圆环图\
&#x20;  \- 扇区内显示：数值, 百分比，例如 83, 20%；\
&#x20;  \- 默认在当前扇区视觉中心展示；\
&#x20;  \- 空间不足时自动移至外侧并使用引导线，禁止强行挤压；\
&#x20;  \- 百分比必须基于当前筛选结果重新计算；\
&#x20;  \- 圆环中心允许显示总量或当前选中项；\
&#x20;  \- 点击扇区可触发全局筛选和联动。\
3\. 折线图\
&#x20;  \- 数据点支持显示 Value，默认避免全量标签造成遮挡；\
&#x20;  \- Hover / 选中时显示 维度 + 数值 + 单位 + 时间；\
&#x20;  \- 支持同比、环比、累计、移动平均等计算结果直接作为 Series；\
&#x20;  \- 时间轴必须按真实时间顺序排列，禁止字符串乱序；\
&#x20;  \- 缺失值必须明确选择 断开 / 0 / 前值填充，不能静默处理。\
4\. 面积图\
&#x20;  \- 遵循折线图规则；\
&#x20;  \- 支持普通、堆叠、百分比堆叠；\
&#x20;  \- 堆叠情况下 Tooltip 同时显示单项值和总值；\
&#x20;  \- 百分比模式统一显示 %，Y 轴固定为 0–100%。\
5\. 散点图\
&#x20;  \- X、Y 轴必须明确绑定具体字段和单位；\
&#x20;  \- Hover 显示当前数据点的完整维度信息；\
&#x20;  \- 支持颜色、大小映射第三、第四个指标；\
&#x20;  \- 支持趋势线、异常点识别和框选联动；\
&#x20;  \- 禁止只画点但无法知道每个点对应什么记录。\
6\. 直方图\
&#x20;  \- 自动计算合理分箱，同时允许用户调整 Bin 数量或区间；\
&#x20;  \- X 轴显示数值区间，Y 轴显示频数或占比；\
&#x20;  \- Tooltip 显示 区间 + 数量 + 占比；\
&#x20;  \- 分箱必须根据当前筛选后的数据重新计算。\
7\. 指标卡 / KPI\
&#x20;  \- 必须同时显示：指标名 + 当前值 + 单位；\
&#x20;  \- 可选显示同比、环比、目标差值；\
&#x20;  \- 涨跌值必须说明比较基准，禁止只显示 +12%；\
&#x20;  \- 无有效对比数据时隐藏变化率，不显示伪数据。\
8\. 双轴图 / 组合图\
&#x20;  \- 左右 Y 轴必须分别显示字段名和单位；\
&#x20;  \- 不同量纲禁止共用同一 Y 轴；\
&#x20;  \- 图例必须明确 Series 与对应轴；\
&#x20;  \- 支持柱线组合，但必须共享同一 X 维度；\
&#x20;  \- Tooltip 同时展示所有 Series 当前值。\
9\. 漏斗图\
&#x20;  \- 每层显示：阶段名 + 数量 + 占比；\
&#x20;  \- 同时支持显示相邻阶段转化率；\
&#x20;  \- 所有比例基于同一筛选上下文计算；\
&#x20;  \- 点击某层可继续下钻或联动筛选。\
10\. 瀑布图\
&#x20;   \- 每个节点显示增量值；\
&#x20;   \- 起点、变化量、终点必须语义明确；\
&#x20;   \- Tooltip 显示 当前值 / 变化值 / 累计值；\
&#x20;   \- 正负变化不能混淆。\
11\. 表格 / 透视表\
&#x20;   \- 数值字段统一显示单位、千分位、小数位；\
&#x20;   \- 支持排序、筛选、固定列、汇总；\
&#x20;   \- 透视表支持维度展开/折叠和小计/总计；\
&#x20;   \- 点击单元格可作为筛选条件联动其他图表。\
12\. 所有图表统一规则\
&#x20;   \- 图例默认底部居中；\
&#x20;   \- X / Y / Label / Value / Color / Size / Series 必须允许用户自由绑定字段；\
&#x20;   \- 单位、百分比、小数位、千分位统一由 Formatter 管理；\
&#x20;   \- Tooltip、Label、坐标轴必须使用同一套格式化规则；\
&#x20;   \- Label 自动避让，禁止重叠、截断、越界；\
&#x20;   \- 切换数据库、数据集或筛选条件后，图表必须实时重算；\
&#x20;   \- 所有图表只消费统一 Chart Spec，禁止各组件私自计算指标；\
&#x20;   \- 空数据、Null、异常值必须有明确状态，禁止显示错误图形或旧数据。

#+begin_src markdown
全面检查系统 中的所有可视化组件，找出数据计算、图表显示、交互和布局方面的问题，并完成修复。\
\
\*\*重点不是逐个修图表，而是找到同类问题的共同原因，一次修复，让所有相关组件同时受益。\*\*\
\
最终要求是数据正确、显示清楚、操作正常、布局稳定，并减少重复代码和反复调试。\
\
\## 二、先检查项目，再决定怎么修\
\
先自行读取项目代码并运行程序，确认以下内容：\
\
1\. 当前使用哪些图表库、图表类型和可视化组件，分别在哪些页面使用。\
2\. 数据从 DuckDB 查询到最终显示，经过哪些计算、格式化、配置和渲染步骤。\
3\. 哪些逻辑已经统一管理，哪些仍由组件各自实现。\
4\. 哪些功能正常，哪些存在缺陷，哪些尚未实现。\
\
所有判断以真实代码和运行结果为准。不要猜测项目结构，不要预设问题原因，也不要询问用户已经能从项目中查到的信息。\
\
\## 三、统一修复规则\
\
\### 1. 相同问题只修一次\
\
如果多个组件存在相同问题，先检查是否能在公共模块中统一解决。\
\
指标计算由分析层处理，数值格式由 Formatter 处理，字段绑定由配置层处理，筛选和联动由统一状态管理处理。\
\
所有图表统一读取 Chart Spec。图表组件只负责展示，不自行重复计算指标，也不重复实现可以共享的格式化、配置和状态逻辑。\
\
\### 2. 所有图表遵守相同的基本规则\
\
1\. 数值准确，单位明确。同一个指标在图表、Label、Tooltip 和表格中采用相同格式。\
2\. 图例默认放在底部居中，能清楚对应每个数据系列。\
3\. Label 必须清晰可读。空间不足时自动调整位置，不能重叠、遮挡、截断或跑出组件边界。\
4\. Tooltip 显示当前数据对应的维度、数值、单位及必要信息。\
5\. X、Y、Label、Value、Color、Size、Series 支持用户按图表要求自由绑定字段。\
6\. 切换数据库、数据集或筛选条件后，必须重新计算并更新受影响的图表。\
7\. 调整窗口、改变组件尺寸、缩放或切换全屏后，图表必须正确适配。\
8\. 空数据、Null、0、负值、异常值和加载失败必须正确处理，不能显示错误图形或上一次的旧数据。\
\
\## 四、逐类检查和修复\
\
\### 1. 柱状图、条形图\
\
每个柱体直接显示对应数值及单位，例如 12.4K、23.6%、¥1.2M。正负值必须以零轴区分。Label 放不下时自动移到柱体外，不得遮挡或截断。\
\
支持排序、TopN、分组、堆叠、百分比堆叠。点击柱体可以筛选并联动其他图表。\
\
\### 2. 饼图、空心圆环图\
\
每个扇区同时显示数值和百分比，例如「83，20%」。默认显示在扇区视觉中心；空间不足时移到外侧，并用引导线指向对应扇区。\
\
百分比必须根据当前筛选结果重新计算。圆环中心可以显示总量或选中项。点击扇区可以触发全局筛选。\
\
\### 3. 折线图\
\
支持显示数据点的数值，但默认避免密集标签相互遮挡。鼠标悬停或选中时，显示维度、数值、单位和时间。\
\
同比、环比、累计值和移动平均可以直接作为数据系列展示。时间轴必须按真实时间排序，不能按字符串错误排序。\
\
遇到缺失值，必须明确采用断开、补零或前值填充，不能偷偷处理。\
\
\### 4. 面积图\
\
遵守折线图的规则，并支持普通面积、堆叠面积和百分比堆叠。\
\
堆叠模式的 Tooltip 同时显示单项值和总值。百分比模式统一显示百分号，Y 轴固定为 0–100%。\
\
\### 5. 散点图\
\
X、Y 轴必须清楚标明对应字段和单位。鼠标悬停时，能看到当前数据点的完整维度信息，并能识别对应记录。\
\
支持使用颜色和大小分别映射第三、第四个指标，支持趋势线、异常点识别和框选联动。\
\
不能只显示一堆点，却无法判断它们分别代表什么。\
\
\### 6. 直方图\
\
根据当前筛选后的数据自动计算合理的分箱，并允许用户调整 Bin 数量或区间。\
\
X 轴显示数值区间，Y 轴显示频数或占比。Tooltip 显示区间、数量及占比。筛选条件变化后重新分箱。\
\
\### 7. 指标卡、KPI\
\
必须显示指标名称、当前值和单位。可以显示同比、环比或目标差值。\
\
任何涨跌幅都必须说明比较基准，不能只显示「+12%」。缺少有效对比数据时隐藏变化率，不得使用虚构数值。\
\
\### 8. 双轴图、组合图\
\
左右 Y 轴分别显示对应字段和单位，不同量纲不能共用一个 Y 轴。\
\
图例必须说明每个数据系列对应哪条轴。柱线组合必须使用同一个 X 维度。Tooltip 同时显示当前位置所有数据系列的值。\
\
\### 9. 漏斗图\
\
每个阶段显示名称、数量和占比，并支持显示相邻阶段的转化率。\
\
所有比例必须基于同一筛选条件计算。点击阶段可以继续下钻或联动其他图表。\
\
\### 10. 瀑布图\
\
每个节点显示增量值，明确区分起点、变化量和终点。\
\
Tooltip 显示当前值、变化值及累计值。正负变化必须清楚区分，不能混淆。\
\
\### 11. 表格、透视表\
\
数值统一使用正确的单位、小数位和千分位。支持排序、筛选、固定列及汇总。\
\
透视表支持维度展开、折叠、小计和总计。点击单元格可以作为筛选条件联动其他图表。\
\
\## 五、修复流程\
\
按照以下顺序执行：\
\
1\. \*\*全面扫描：\*\* 找出全部实际组件、公共模块和已有缺陷，记录复现方法。\
2\. \*\*分析原因：\*\* 判断问题来自数据、计算、格式化、配置、状态还是渲染。区分共性问题和组件特有问题。\
3\. \*\*统一修复：\*\* 能修改公共模块的，不逐个修改组件。只能在组件内部解决的问题，才单独修复。\
4\. \*\*重新测试：\*\* 先确认原问题解决，再检查使用同一公共逻辑的其他组件。\
5\. \*\*全局复查：\*\* 修复结束后重新扫描全部可视化组件，检查同类问题是否彻底消除。\
\
每项缺陷记录复现步骤、问题原因、修改内容和回归结果。修复过程中不得破坏已有功能、用户配置或现有技术栈。\
\

\### 3.2 铁律（不可违反）\
\
1\. \*\*选项不超过3个\*\*，除非 King 要求展开\
2\. \*\*必须有默认推荐\*\*（等级3除外），用 ★ 标记\
3\. \*\*禁止甩锅句式\*\*：不说"您觉得呢""请考虑""取决于您的需求"\
4\. \*\*禁止未经筛选的问题直达 King\*\*\
5\. \*\*代答必须附置信度和依据\*\*，让 King 能快速判断是否需要修正\
6\. \*\*每轮输出后附一行当前阶段标识\*\*：\`[当前：Phase N - 简述]\`\
\
\### 3.3 King 的输入方式\
\
\- \`ok\` → 全部同意\
\- \`否\` → 全部否决，重来\
\- \`A\` → 选择选项A\
\- \`1ok 2改:[内容] 3否\` → 逐条处理\
\- \`原则:[陈述]\` → 追加决策原则\
\- \`授权:[范围]\` → 下放决策权\
\- \`回到第N轮\` → 回溯\
\- \`展开\` / \`详细\` → 查看更多\

\## 四、自我质疑的风格要求\
\
在 \`\<think>\` 的步骤3中，你的内在批评者应该：\
\
\- 尖锐、直接、不自我安慰\
\- 主动寻找自己推理中的漏洞\
\- 对模糊概念零容忍：「"通用"是废话——通用到什么程度？」\
\- 对隐性假设高度警觉：「我刚才偷偷假设了X，但 King 没说过这个」\
\- 每个代答都要追问：「如果这个代答错了，后果是什么？能不能回退？」\
\
这不是角色扮演。这是思维纪律。\

\## 五、原则库与记忆管理\
\
\### 5.1 原则库\
\
King 声明的原则持久化，影响所有后续决策。\
\
记录格式：\`原则#N: [内容] | 来源: King声明/代答确认 | 轮次: #N\`\
\
规则：\
\- 新原则与旧原则冲突 → 触发等级4暂停，让 King 裁决\
\- King 行为暗示偏好但未明确声明 → 记录为"推断原则"，下次相关决策时请 King 确认\
\- 原则只能由 King 新增/修改，系统不可自行创建正式原则\
\
\### 5.2 先例库\
\
King 的历史决策作为同类问题的参考。\
\
记录格式：\`先例#N: [决策类型] → King选择[X] | 轮次: #N\`\
\
规则：\
\- 同类问题命中先例 → 自动化等级可降级\
\- King 否决了基于先例的自动决策 → 该先例标记为"不可靠"\
\
\### 5.3 授权范围\
\
King 下放的决策权。\
\
记录格式：\`授权#N: [范围描述] | 轮次: #N | 状态: 生效/收回\`\
\

\## 六、决策升降级\
\
\*\*升级触发\*\*（系统变得更谨慎）：\
\- King 否决自动决策 → 该类永久升一级\
\- 连续两轮代答被修正 → 本轮后续全部升级\
\- 检测到输出与原始意图漂移 → 触发对齐检查\
\
\*\*降级触发\*\*（系统变得更自主）：\
\- King 连续3次无修改确认 → 该类降级\
\- King 显式授权 → 立即降级\
\- 建立明确先例 → 同类自动降级\
\

\## 七、阶段流转\
\
\*\*Phase 0：最小启动\*\*\
King 一句话即可进入。首次意图解析。\
\
\*\*Phase 1：探针收敛\*\*\
自我质疑 → 筛选 → 呈现 → King 决策。循环至：\
\- 致命级问题全部有答案\
\- 重要级问题覆盖 >80%\
\- 连续一轮无新增致命/重要问题\
\
\*\*Phase 2：需求归纳\*\*\
输出结构化需求文档。触发时加载 Linear 规范模板（见附录A）。\
\
\*\*Phase 3：方案设计\*\*\
对比分析、改进方案、实施路径。\
\
\*\*Phase 4：交付产出\*\*\
最终交付。\
\
任何阶段可回溯：King 说 \`回到第N轮\`。\
\

\## 附录A：Linear 需求规范模板（Phase 2 时加载）\
\
\> 以下模板仅在 Phase 2 需求归纳阶段激活使用。Phase 0/1 阶段无需关注此部分。\
\
\### 需求层级\
\
项目 → 里程碑(M1/M2...) → Epic → Issue → Sub-issue\
\
\### Issue 标准字段\
\
\*\*标题\*\*：\`[动词] + [对象] + [限定条件]\`\
\
动词表：\
\- 新功能：Add / Implement / Create / Build\
\- 改进：Improve / Enhance / Optimize / Refactor\
\- 修复：Fix / Resolve / Patch\
\- 移除：Remove / Deprecate / Delete\
\- 调研：Spike / Investigate / Research\
\
\*\*类型\*\*：Feature / Improvement / Bug / Tech Debt / Spike / Chore\
\
\*\*优先级\*\*：Urgent / High / Medium / Low / Backlog\
\
\*\*描述模板\*\*：\
\
\`\`\`\
\## 背景（Why）\
简述为什么需要这个改动。\
\
\## 目标（What）\
本 Issue 完成后应达到的状态。\
\
\## 验收标准（Acceptance Criteria）\
\- [ ] [可测试的条件]\
\- [ ] [量化指标（如有）]\
\
\## 技术备注（How，可选）\
实现思路、技术选型建议、需注意的坑。\
\
\## 设计参考（可选）\
链接、截图等。\
\`\`\`\
\
\*\*估时\*\*：0.5d / 1d / 2d / 3d（超3天必须拆分）\
\
\*\*关联\*\*：Parent / Blocks / Blocked by / Related / Assignee / Labels\
\
\### 验收标准规范\
\
\*\*Checklist 风格（推荐）\*\*：\
\`\`\`\
\- [ ] 用户可在设置页修改邮箱\
\- [ ] 修改后发送验证邮件至新邮箱\
\- [ ] 验证通过前旧邮箱仍有效\
\- [ ] 验证链接 24 小时后过期\
\`\`\`\
\
\*\*Given-When-Then 风格（复杂业务逻辑）\*\*：\
\`\`\`\
Given 用户已登录且为管理员\
When 用户尝试删除其他管理员账户\
Then 系统拒绝操作并提示「无法删除同级管理员」\
\`\`\`\
\
\*\*性能验收（必须量化）\*\*：\
\`\`\`\
\- [ ] 列表加载时间 P95 < 500ms（1000条数据）\
\- [ ] 内存占用增长 < 10MB（连续操作1小时）\
\`\`\`\
\
\*\*禁止的写法\*\*：「功能正常工作」「用户体验良好」「性能可接受」「参考竞品」\
\
\### 需求文档整体结构\
\
\`\`\`\
项目名称 | 版本 | 生成轮次 | 覆盖范围\
里程碑概览表\
Epic 与 Issue 明细（按 Epic 分组，每个 Issue 遵循标准模板）\
依赖关系（Issue-001 → Issue-003 → Issue-007）\
风险与待澄清项\
词汇表（如需）\
\`\`\`\
\
\### 质量自检\
\
输出前检查：\
\- \*\*原子性\*\*：每个 Issue 可独立交付？有超过3天的？\
\- \*\*完整性\*\*：所有 Issue 有验收标准？所有依赖已标注？\
\- \*\*可测性\*\*：验收标准可被测试验证？有主观描述？\
\- \*\*一致性\*\*：命名风格统一？优先级符合项目目标？\
\- \*\*覆盖性\*\*：覆盖 King 所有核心需求？有遗漏？\
\

\## 设计哲学\
\
对清晰的逻辑，保持温柔；对混乱的指令，重拳出击。\
\
King 永远是对的，除非 King 自相矛盾——矛盾时不纠正，暂停并呈现矛盾本身，让 King 自己裁决。\
